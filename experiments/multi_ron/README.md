# 동시 론(더블론) 흐름 확인 — 합성 사진 (2026-10-27)

실제 사진이 없어(갤러리 B·C·D 는 화료자 한 명씩) 두 손패가 눕혀진 사진을 **합성**해 앱 흐름만 확인했다.
정확도 숫자에는 넣지 않는다(합성). 로컬 서버 8030(`.claude/launch.json` "recognizer", 운영과 같은 master).

## 만든 법 (`compose.py`)

격자 판독은 자리 칸을 따로 잘라 읽으므로, 한 사진의 자리 칸에 다른 사진의 **같은 자리** 칸을 크기 맞춰 붙였다(회전 일치).

| 이름 | 바탕(격자·강·가운데) | 붙인 것 | 앞면 자리 |
| --- | --- | --- | --- |
| CD | D(k16, 아래 화료 18000) | C(k15) 왼쪽 칸 | 왼쪽·아래 |
| DC | C(k15, 왼쪽 화료 16000) | D(k16) 아래 칸 | 왼쪽·아래 |

측정 도구 `field_20261024/read_grid_test.dart` 에 `WINNER=left,bottom`(둘 다 론 선택)과 `pickRonWinners` 병합을 넣었다(앱 `mount_screen` 과 같은 순서).

## 결과 (`scenes/`)

**CD** — 끝까지 됨.
- 픽셀 앞면 판정이 두 자리를 다 올림(`face_up: [bottom, left]`, 무늬 넓이 1989·1818) → 고르기 → 둘 다 론.
- 왼쪽(C 손패) 7판 40부 12000: 손패 14장 정답, 론패 南 은 오른쪽 강 끝. 원본 C 의 16000 과 다른 건 리치뿐 — 리치봉은 바탕(D)의 가운데라 없는 게 맞다.
- 아래(D 손패) 6판 30부 18000 정답(`+함께 론`), 방총자 같은 오른쪽(플레이어 2) → `pickRonWinners` 가 둘 다 남김, 플래그 없음.
- 두 손패가 우연히 같은 南 단기 대기라 같은 강 끝 한 장을 둘 다 론패로 썼다 — 실제 더블론과 같은 모양.
- 17.5초(읽기 16.3초, 자리 2 × 3번 + 강 끝 + 리치봉 + 도라).

**DC** — 합성 한계로 "쯔모로 읽힌 손패가 있어 플레이어 4 만 계산" 플래그가 나고 왼쪽만 남음(3회 같음).
- 원인은 판독이 아니라 병합 규칙: 원본 C 의 왼쪽 론패 南 은 **아래 사람 강 끝**에 있는데, 합성에서는 아래가 화료자라 방총자 후보에서 빠진다(`canDealIn`). 그래서 왼쪽은 13장(론패 없음), 아래(D 손패)는 바탕 C 의 강에 맞는 패가 없어 쯔모로 읽힘 → 규칙대로 첫 사람만.
- 같은 서버로 원본 k15 는 14장·16000 정답(`scenes/orig/k15`) → 서버 회귀 아님.
- 현실에선 화료자가 방총자일 수 없으니 이 조합 자체가 없다. 대신 "화료자끼리는 서로의 강을 방총 후보에서 뺀다" 가 동작함을 보여 준다.

## 확인된 것 / 안 된 것

- 됨: 앞면 두 자리 감지 → 둘 다 론 선택 → 각자 손패 계산 → 방총자 공통 → `pickRonWinners` 둘 유지 → 결과 화면 `otherWins` 로 넘어가는 자료까지.
- 안 됨(실제 사진 필요): 실제 조명·가림, 론패 한 장을 두 화료자가 같이 쓰는 장면의 사진 상태, 화료 시트에서 기록 버튼까지의 화면(웹에서는 전에 확인).
