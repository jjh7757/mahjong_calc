# 설계서 — 패보 리뷰의 LLM 설명 층 (2026-11-18)

패보 리뷰(`docs/paifu_review_plan_1113.md` 4단계 "진행" ~ "진행 3")의 다음 층. **설계만 적는다 — 구현 · 측정 없음.**
형식은 지금까지와 같다: 설계 Fable · 구현 Opus 5.5 높음 · 검토 Fable.

## 0. 요약

- 숫자는 전부 코드가 낸다(이미 있음: 샹텐 · 유효패 · 등급 · 현물). LLM 은 **그 숫자를 말로 풀고 판 전체를 한 문단으로 묶는 일만** 한다. LLM 이 샹텐 · 대기를 스스로 계산하는 길은 막는다.
- LLM 이 쓴 글은 **코드가 사실표와 대조해 검증**한다. 사실표에 없는 패 이름 · 숫자가 나오면 한 번 다시 시키고, 그래도 틀리면 코드가 만든 문장(지금 카드 문구)으로 대체한다.
- 호출은 **서버(`mahjong-recognizer`)의 새 라우트 하나**로. 서버에 이미 Gemini 키 · 인증 · 호출 제한이 있다. 보내는 것은 글(사실표)뿐 — 사진 · 이름은 안 나간다.
- 먼저 만드는 것은 **해설(1단계)** 이고, 묻고 답하는 **복기 에이전트(3단계 — 도구 호출 · 검색)** 는 해설이 평가를 넘은 뒤다.
- **"LLM 해설이 코드 문장보다 나은가" 를 가린 채 재서, 안 나으면 붙이지 않는다**(7절).

## 2. LLM 이 하는 일 / 안 하는 일

| 일 | 누가 | 까닭 |
| --- | --- | --- |
| 샹텐 · 유효패 · 남은 장수 · 순위 · 등급 · 현물 | 코드 | 틀리면 안 되고 매번 같은 답이어야 함 |
| "배울 장면" 고르기 | 코드(등급 → 손실 크기 순) | hero 버림이 판당 10 ~ 18건뿐이라 고를 것이 적다. LLM 에 맡길 까닭이 없음 |
| 지적 수 해설 2 ~ 3문장 | **LLM** | "유효패 10장 대 17장" 을 "3 · 8삭 샤보를 받는 쪽이…" 처럼 사람 말로 |
| 판 총평 3문장 안 | **LLM** | 차례들을 흐름으로 묶기(초반 넓게 → 중반 텐파이 놓침 → …) |
| 질문에 답하기("6만을 버렸으면?") | **LLM + 도구**(3단계) | 무엇을 계산해야 하는지가 질문마다 다름 — 여기가 에이전트 |
| 밀기 · 내리기 · 타점 판단 | **안 함** | 강한 마작 AI 가 있어야 함(계획서 6단계, 라이선스 확인 먼저) |

LLM 에 못 하게 막는 것: 사실표에 없는 숫자 · 패 말하기, 수비 상황(`defense`)을 실수라고 부르기, "반드시 · 무조건" 같은 단정, 결과(누가 화료했나)로 그 순을 평가하기.

## 3. 사실표 — LLM 에 주는 입력

앱(Dart)이 `TurnReview` 에서 만든다. 서버는 계산하지 않고 받은 사실표만 쓴다(엔진을 두 벌 두지 않는다 — 3단계 전까지).

판 머리: 국 · 본장 · hero 자리 바람 · 도라 표시패 · 요약(패효율 · 등급별 개수) · 결과 종류. **이름은 안 보낸다**(자리 바람으로만).

해설할 차례마다(등급이 부정확 · 실수 · 큰 실수인 차례 전부 + `defense` 차례. 최선 · 좋음 · forced 는 총평용으로 한 줄 요약만):

```
{ "turn": 5, "junme": 5, "status": "graded", "grade": "blunder",
  "hand": "33789m334588s23p", "drawn": "4p", "discard": "2p",
  "actual": {"shanten": 1, "total": 10, "kinds": 4, "tiles": [{"tile": "3m", "left": 2}, …]},
  "best":   {"discard": "3s", "shanten": 0, "total": 4, "kinds": 2, "tiles": [{"tile": "3m", "left": 2}, {"tile": "8s", "left": 2}]},
  "others": [위 3개 후보: 버림 · 샹텐 · 장수],
  "only_best": ["…"], "only_actual": ["…"],          // 한쪽에만 있는 유효패
  "shape_hint": {"discard_block": "순자 완성(234p)의 일부", "best_block": "3삭 2장 중 하나"},
  "riichi_seats": [], "genbutsu": null, "safe_tiles": [] }
```

- `shape_hint` 는 **코드가 내는 모양 힌트**다: 버린 패가 손에서 어떤 덩어리에 속했나(또이쯔 · 양면 · 간짱 · 변짱 · 완성 순자 · 뜬 패). LLM 이 패 모양을 스스로 읽다 틀리는 것을 줄이려는 것 — 지금 엔진에는 없어서 새로 만든다(1단계의 코드 일). 덩어리가 여러 가지로 읽히면 후보를 다 적고, 못 정하면 비운다(비면 LLM 은 모양 말을 하지 않는다).
- 패 표기는 `5m` 꼴로 보내고, 사람 말(5만)로 바꾸는 표를 지시문에 넣는다. 응답 검증도 이 표로 한다.

## 4. 흐름

```
앱: 사실표 만들기 ──POST /v2/review/explain──▶ 서버
                                              ① 생성(LLM, JSON 스키마 응답)
                                              ② 검증(코드)
                                              ③ 통과 → 응답 / 실패 → 위반 목록을 붙여 ① 한 번 더 / 또 실패 → 그 차례만 "대체" 표시
앱: 응답을 패보 id + 사실표 해시 + 지시문 판 번호로 저장(다음엔 호출 없음), 대체 표시된 차례는 지금 카드 문구 그대로
```

- **응답 스키마:** `{"summary": "…", "turns": [{"turn": 5, "title": "…(20자 안)", "text": "…(3문장 안)"}]}`.
- **② 검증 규칙(코드, 전부 기계적):**
  1. 요청한 차례가 빠짐없이, 더도 없이 있다.
  2. 글에 나온 패 이름이 그 차례 사실표에 있는 패뿐이다(손패 · 뽑은 패 · 후보 · 유효패 · 현물).
  3. 글에 나온 "N장 · N종 · N샹텐 · N순" 숫자가 그 차례 사실표에 있는 값이다.
  4. `defense` · `complete` 차례에 "실수 · 큰 실수 · 틀렸" 이 없다. 모양 말(양면 · 간짱 · 변짱 · 샤보 · 단기 · 또이쯔)은 `shape_hint` 나 대기 종류로 뒷받침될 때만.
  5. 길이 · 한국어 · 금지어("반드시", "무조건", 플레이어 이름).
- **호출 시점:** 패보를 열었을 때 인터넷이 되고, 지적 · 수비 차례가 있고, 저장된 해설이 없으면 자동으로 한 번(사용자 선호: 터치 없는 자동화). 실패 · 오프라인이면 조용히 카드만. 단 **자동 호출은 7절 평가를 넘은 뒤에 켠다** — 그 전에는 단추.
- **화면:** 카드 아래에 해설 2 ~ 3문장, 요약 줄 아래(또는 끝 걸음)에 총평. LLM 이 쓴 글임을 작은 표시로 밝힌다.
- **비용 · 지연:** 글만 오가므로 한 판에 한 번 호출, 입력은 수천 토큰 수준으로 어림한다 — 실제 토큰 · 초 · 금액은 2단계에서 잰다(지금 숫자 없음).

## 5. 어디에 두나

| 안 | 장점 | 단점 | 판단 |
| --- | --- | --- | --- |
| **서버 라우트(권장)** | 키 · 인증 · 호출 제한이 이미 있음, 지시문을 앱 배포 없이 고침, 검증 · 재시도를 한곳에서 | 서버 master push = 운영 배포라 조심 | ✔ |
| 앱에서 Gemini 직접 | 서버 일 없음 | 키가 앱에 들어감 | ✗ |
| 기기 안 작은 모델 | 오프라인 | 한국어 마작 해설 품질 미지수, 발열 · 용량 | ✗(지금) |

- 서버 쪽 새 파일: `app/review.py`(지시문 · 스키마 · 검증 · 재시도) + `main.py` 에 라우트 하나 + `tests/test_review.py`(LLM 은 가짜로 바꿔 검증 규칙을 단위 시험). 기존 `GeminiRecognizer` 는 사진 전용이라 글 호출 함수를 하나 더한다.
- 앱 쪽: `lib/paifu/review_facts.dart`(사실표 · 모양 힌트) · `RecognizerClient` 에 호출 하나 · 저장 · 카드에 글 붙이기. 평가용으로 `tool/paifu_facts.dart`(패보 JSON → 사실표 JSON, 화면 없이 `dart run`).

## 6. 프레임워크(LangGraph) · 검색(RAG)을 어디에 쓰나

제품에 필요한가와 포트폴리오에서 설명하기 좋은가를 나눠 적는다.

| | 제품 필요 | 포트폴리오 설명력 | 판단 |
| --- | --- | --- | --- |
| 1단계 해설(생성 → 검증 → 재시도 · 대체) | 고정 순서 3칸이라 함수 몇 개면 된다. 운영 서버에 의존성을 늘릴 까닭이 약함 | "근거 있는 생성 + 코드 검증 + 대체" 는 프레임워크 없이도 충분히 설명됨 | **프레임워크 없이** |
| 3단계 복기 에이전트(도구 호출 고리) | 질문마다 부를 도구 · 횟수가 달라 상태 · 분기 · 횟수 제한이 필요 | 도구 호출 에이전트 + 평가 세트 — 가장 설명하기 좋은 자리 | **LangGraph** |
| 검색: 내 지난 패보에서 비슷한 수 찾기 | 평가 건이 구조화돼 있어(`status` · `grade` · `genbutsu` …) **조건 검색이 임베딩 검색보다 정확**하다 | "벡터 검색을 안 쓴 까닭" 을 숫자로 보이면 오히려 설명이 됨 | 조건 검색 먼저, 임베딩은 비교 실험으로만 |
| 검색: 매장 룰 · 역 설명 | 문서가 짧아 통째로 지시문에 넣어도 됨 | RAG 를 보이려면 문서가 길어야 함 — 억지로 늘리지 않는다 | 통째로 넣기 |

3단계 도구(안): `discard_options(turn)` · `what_if(turn, 버림)` · `safe_tiles(turn)` · `find_turns(조건)` · `rule(이름)`. 서버가 계산해야 하므로 그때 엔진을 Python 으로 옮긴다 — 검토 때 쓴 대조 계산(Dart 와 9,000손 일치)이 출발점이고, 두 구현은 같은 기대값 파일로 계속 맞춘다.

## 7. 평가 — 재기 전에 적는 기준(안, 사용자 확정 전)

| 지표 | 재는 법 | 기준(안) |
| --- | --- | --- |
| 사실 일치(자동) | ② 검증 통과율 — 첫 시도 / 재시도 뒤 / 대체 비율 | 재시도 뒤 통과 95% 이상 |
| 검증이 놓친 틀림(사람) | 통과한 해설 표본을 사실표와 나란히 읽어 틀린 문장 세기 | 틀린 해설 5% 이하 |
| **코드 문장보다 나은가(가린 비교)** | 같은 차례의 코드 문장 / LLM 해설을 어느 쪽인지 가리고 사용자가 고름 | LLM 쪽 60% 이상 — **못 넘으면 LLM 해설을 붙이지 않는다** |
| 비용 · 지연 | 판당 토큰 · 초 | 기준 없음, 적기만 |

- 지시문 · 검증 규칙은 개발 판에서 다듬고, **채점은 안 본 판**에서 한다(지금까지 패보 실험과 같은 원칙).
- **자료가 모자란다:** 손패 있는 실제 판이 4판, 해설 대상(지적 + 수비)이 7건뿐이다. 늘리는 길 —
  - (가) 합성 패보(검토 때 만든 300판): 지금 바로 되고 사실 일치는 잴 수 있다. 손 모양이 무작위라 "도움이 되나" 는 못 잰다.
  - (나) 공개 온라인 패보를 받아 이 형식으로 변환: 현실적인 손이 많이 생긴다. 인터넷에서 받아야 하고 이용 조건 확인이 먼저다.
  - (다) 사용자의 온라인 대국 기록이 있으면 그것.
  - (라) 매장 판의 손패 기록 자동화가 풀릴 때까지 기다림: 언제일지 모른다.
- 재면 `docs/metrics.md` 에 새 표(패보 리뷰 해설)를 만든다.

## 8. 단계

| 단계 | 내용 | 끝났다는 것 |
| --- | --- | --- |
| 1 | 사실표 · 모양 힌트(앱) + 서버 라우트(생성 · 검증 · 재시도 · 대체) + 단위 시험 | 가짜 LLM 으로 검증 규칙 시험 통과, 실제 호출로 r19 한 판 해설이 나옴(단추로만) |
| 2 | 평가(7절) | 기준을 넘으면 자동 호출 · 화면 붙임, 못 넘으면 붙이지 않고 기록 |
| 3 | 복기 에이전트(도구 호출 · LangGraph · 조건 검색) | 따로 설계서 |

## 9. 위험과 한계

- **패효율만 본 등급 위에 해설이 얹힌다.** 일부러 물러난 수(수비 · 타점 · 역)도 "큰 실수" 로 찍힌 채 해설이 붙는다. 해설에는 "패효율 기준" 임을 늘 밝히고, 등급 이름 · 문턱(계획서 "설계에서 정할 것")을 먼저 확정하는 편이 낫다.
- **검증은 숫자 · 패 이름만 잡는다.** "이 모양이 더 좋다" 같은 판단 문장이 틀리는 것은 못 잡는다 — 그래서 모양 말을 `shape_hint` 에 묶고, 사람 표본 확인을 기준에 넣었다.
- **운영 서버에 붙는다.** 사진 판독과 호출 제한 · Gemini 한도를 나눠 쓴다. 해설 호출은 따로 세고, 한도에 걸리면 해설 쪽을 먼저 끊는다.
- **모델이 바뀌면 글이 바뀐다.** 저장 키에 지시문 판 번호와 모델 이름을 넣는다.
- hero 손패가 없는 판(지금 10판 중 6판)은 해설도 없다 — 이 층의 병목은 여전히 손패 기록 자동화다.

## 10. 사용자 결정 거리

## 부록 A. 규격 v1 — 사실표 · 응답 · 검증 (2026-11-18, 1단계 구현의 계약)

앱(`lib/paifu/review_facts.dart`)과 서버(`app/review.py`)가 이 절만 보고 따로 만든다. 서로 다른 해석이 나오면 이 절을 고친 뒤 양쪽을 맞춘다.

### A-1. 패 표기

- 사실표의 패는 전부 `1m`~`9m` · `1p`~`9p` · `1s`~`9s` · `1z`~`7z`(동 남 서 북 백 발 중). **적5 는 `5m` 꼴로 보낸다**(`0m` 안 씀).
- 사람 말: `Nm` = N만, `Np` = N통, `Ns` = N삭, `1z`~`7z` = 동 · 남 · 서 · 북 · 백 · 발 · 중.
- **LLM 은 글 안의 패를 대괄호로 쓴다: `[3삭]` · `[중]`.** 자패 이름(동 · 서 · 중 …)이 보통 말("리치 중")과 겹쳐서, 검증은 대괄호 안만 패로 본다. 앱은 보여 줄 때 대괄호를 뗀다.

### A-2. 요청 — `POST /v2/review/explain` (JSON)

```
{ "version": 1,
  "game": { "round": "남4국", "honba": 0, "hero_wind": "서",
            "dora_indicators": ["3z", "2m"],
            "efficiency_pct": 80 | null,
            "grades":  {"best": 5, "good": 0, "inaccuracy": 0, "mistake": 1, "blunder": 1},
            "statuses": {"graded": 7, "forced": 2, "defense": 0, "complete": 0, "unknownHand": 1, "inconsistent": 0} },
  "timeline": [ { "turn": 2, "discard": "1z", "status": "graded", "grade": "best" | null,
                  "shanten_after": 2 | null, "total": 16 | null, "riichi": false } , … ],   // hero 버림 전부, 순서대로
  "turns": [ <차례 사실> , … ] }                                                         // 해설할 차례만
```

- `turns` 에 넣는 차례: `grade` 가 inaccuracy · mistake · blunder 이거나 `status` 가 defense · complete. 없으면 빈 목록(총평만).
- 플레이어 이름 · 패보 id · 제목 · note 는 보내지 않는다. 결과(누가 화료했나)도 보내지 않는다.

차례 사실:

```
{ "turn": 5, "status": "graded", "grade": "blunder" | null,
  "hand": ["3m","3m","7m","8m","9m","3s","3s","4s","5s","8s","8s","2p","3p","4p"],   // 버리기 전 닫힌 패 전부(뽑은 패 포함), 패 번호 순
  "drawn": "4p" | null, "discard": "2p", "melds": 0, "riichi_declared": false,
  "shanten_before": 0,
  "actual": { "discard": "2p", "shanten": 1, "total": 10, "kinds": 4, "tiles": [{"tile": "3m", "left": 2}, …] },
  "best":   { "discard": "3s", "shanten": 0, "total": 4,  "kinds": 2, "tiles": [ … ] },
  "top":    [ {"discard": "3s", "shanten": 0, "total": 4, "kinds": 2}, … ],          // 후보 위에서 3개(첫째 = best)
  "rank": 7, "shanten_loss": 1, "ukeire_loss": -6,
  "only_best": ["…"], "only_actual": ["…"],     // 한쪽 유효패 목록에만 있는 패(남은 장수 0 인 것 제외), 패 번호 순
  "shape": { "discard": [ {"kind": "sequence", "tiles": ["2p","3p","4p"]}, {"kind": "ryanmen", "tiles": ["2p","3p"]}, {"kind": "kanchan", "tiles": ["2p","4p"]} ],
             "best":    [ {"kind": "pair", "tiles": ["3s","3s"]}, … ] },
  "riichi_winds": ["남"], "genbutsu": true | false | null, "safe_tiles": ["6m"] }
```

- `kinds` = 남은 장수가 1장 이상인 종류 수(`liveKinds`). `tiles` 는 남은 장수 0 인 것도 그대로.
- `hand` 의 패 번호 순 = 만 → 통 → 삭 → 자패(엔진의 0~33 순). 위 예시는 설명용이라 순서가 다르다.
- `riichi_winds` = 그때 리치 중인 다른 자리의 바람(동 · 남 · 서 · 북), 자리 번호 순.

### A-3. 모양 힌트 `shape`

버리기 전 손패(`hand`)에서 그 패 한 장이 낄 수 있는 덩어리를 **전부** 적는다(겹쳐도 됨). 한 가지로 정하지 않는다.

| kind | 조건(패 t, 손패 개수 c) | tiles |
| --- | --- | --- |
| `triplet` | c[t] ≥ 3 | t 세 장 |
| `pair` | c[t] ≥ 2 (3장 이상이어도 적음) | t 두 장 |
| `sequence` | 수패이고 (t−2,t−1,t) · (t−1,t,t+1) · (t,t+1,t+2) 가 같은 수트 안에 다 있음 — 되는 것마다 하나 | 세 장, 낮은 순 |
| `ryanmen` | 수패이고 이웃 한 장(t−1 또는 t+1)이 있으며 두 장이 1-2 · 8-9 가 아님 — 되는 것마다 하나 | 두 장 |
| `penchan` | 이웃 한 장이 있고 두 장이 1-2 또는 8-9 | 두 장 |
| `kanchan` | 수패이고 한 칸 건너(t−2 또는 t+2)가 같은 수트에 있음 — 되는 것마다 하나 | 두 장 |
| `isolated` | 위 어느 것도 아님 | t 한 장 |

순서: 위 표 순서, 같은 kind 안에서는 tiles 의 첫 패 번호 순. `shape.discard` 는 버린 패, `shape.best` 는 최선 후보의 패(버린 패와 같으면 같은 목록).

### A-4. 응답

```
{ "version": 1, "model": "gemini-3.8-flash", "prompt_version": "r1",
  "summary": { "text": "…" | null, "source": "llm" | "fallback", "violations": [] },
  "turns": [ { "turn": 5, "title": "…" | null, "text": "…" | null, "source": "llm" | "fallback", "violations": ["…"] } ],
  "attempts": 1 | 2, "input_tokens": 0, "output_tokens": 0, "elapsed_ms": 0 }
```

- `turns` 는 요청의 `turns` 와 같은 차례 · 같은 순서. `source` 가 fallback 이면 `title` · `text` 는 null(앱은 지금 카드 문구만 보여 준다).
- `violations` 는 마지막 시도에서 걸린 규칙(사람이 읽는 한 줄씩). 통과면 빈 목록.

### A-5. 검증 규칙(서버, 기계적)

차례 글(`title` + `text`)마다, 그 차례 사실만 가지고:

1. **패:** 대괄호 토큰 `[…]` 은 A-1 의 사람 말 이름이어야 하고, 그 패가 그 차례의 `hand` · `drawn` · `discard` · `actual.tiles` · `best.tiles` · `best.discard` · `top[].discard` · `safe_tiles` 중에 있어야 한다. 대괄호 밖에 `N만 · N통 · N삭`(N = 1~9) 꼴이 있으면 위반(대괄호를 안 씀).
2. **숫자:** `N장` 은 {`actual.total`, `best.total`, `top[].total`, |`ukeire_loss`|, 유효패 각 `left`, 손패에서 한 종류의 장수(1~4)} 안. `N종` 은 {`actual.kinds`, `best.kinds`, `top[].kinds`} 안. `N샹텐` 은 {`shanten_before`, `actual.shanten`, `best.shanten`, `top[].shanten`} 중 1 이상인 값. `N순` · `N번째` 는 `turn`. `점` 이 붙은 숫자는 위반(점수 말 금지).
3. **모양 말:** `양면 · 간짱 · 변짱 · 또이쯔 · 커쯔 · 순자 · 뜬 패 · 고립` 은 그 kind 가 `shape.discard` 나 `shape.best` 에 있을 때만(양면 = ryanmen, 간짱 = kanchan, 변짱 = penchan, 또이쯔 = pair, 커쯔 = triplet, 순자 = sequence, 뜬 패 · 고립 = isolated). `샤보 · 단기 · 노베탄 · 다면` 은 늘 위반(대기 모양 힌트가 없음).
4. **상태:** `status` 가 defense · complete 인 차례에 `실수 · 잘못 · 틀렸 · 틀린` 이 있으면 위반.
5. **금지어:** `반드시 · 무조건 · 절대`.
6. **길이:** `title` 1~20자, `text` 1~200자 · 문장 3개 이하(`. ! ?` 와 `다.` 로 셈). 한글이 한 글자 이상.

총평(`summary.text`): 대괄호 패는 요청 전체(`turns` + `timeline[].discard`)에 나온 패, `N장 · N종 · N샹텐` 은 모든 차례 허용값의 합집합(+ `timeline` 의 `total` · `shanten_after`), `N순 · N번째` 는 `timeline` 의 `turn`, 금지어 · `점` 같음, 1~300자 · 문장 4개 이하. `패효율 N` 을 쓰면 N = `efficiency_pct`.

### A-6. 생성 · 재시도

- 한 번의 LLM 호출로 `summary` 와 모든 `turns` 를 JSON 스키마 응답으로 받는다 → 검증 → 걸린 항목만(차례 · 총평) 위반 목록을 붙여 한 번 더 받는다 → 또 걸리면 그 항목은 fallback.
- 응답에 요청하지 않은 차례가 있으면 버리고, 빠진 차례는 위반 "빠짐" 으로 다시 받는다.
- LLM 호출이 실패(시간 초과 · 5xx · 429)하면 라우트는 502/429 로 답하고 앱은 카드만 보여 준다.

### A-8. 규격 v1.1 — 첫 실제 호출(metrics 표 15-1) 뒤 고침 (2026-11-18, 배포 전이라 `version` 은 1 그대로)

**사실표(앱)에 더하는 칸 — 차례 사실마다, 둘 다 필수:**

- `shanten_prev`: **뽑기 전** 닫힌 패(`hand` 에서 `drawn` 한 장을 뺀 `13 − 3 × melds` 장)의 샹텐. `drawn` 이 null 이거나(울기 뒤 버림 · 뽑은 패 모름) `hand` 에 `drawn` 이 없으면 null.
  - 뜻: `shanten_before`(뽑은 패 포함 `14 − 3 × melds` 장, 가장 좋은 버림을 했을 때의 샹텐)가 `shanten_prev` 보다 작으면 "뽑은 패로 한 걸음 나아갈 수 있었다", 같으면 "그대로".
- `shape.drawn`: 뽑은 패가 `hand` 에서 낄 수 있는 덩어리(A-3 과 같은 계산). `drawn` 이 null 이면 빈 목록.

**검증(서버) 고침:**

1. **숫자 `N장`:** |`ukeire_loss`| 는 `shanten_loss == 0` 이고 `ukeire_loss > 0` 일 때만 허용값에 넣는다(샹텐이 뒤로 간 차례의 유효패 차이는 손실이 아니다 — "대기 6장" 이 통과한 빈틈).
2. **숫자 `N샹텐`:** 허용값에 `shanten_prev`(1 이상)를 더한다.
3. **영어:** 대괄호 토큰을 지운 글에 영문자 2자 이상이 이어지면 위반(`best` · `blunder` · `shanten` 같은 칸 이름이 샘). 차례 글 · 총평 모두.
4. **"유지":** 글에 `텐파이를 유지` · `텐파이 유지` · `텐파이를 지키` 가 있으면 `shanten_prev == 0` 일 때만 통과. `N샹텐을 유지` · `N샹텐 유지` 는 N = `shanten_prev` 일 때만 통과. (`shanten_prev` 가 null 이면 위반.)
5. **모양 말:** 근거 kind 를 `shape.discard` · `shape.best` · `shape.drawn` 에서 찾는다.
6. **패:** 허용 패 집합은 그대로(`drawn` 은 이미 `hand` 에 있다).

**지시문 r2(서버) 방향:**

- 차례 글의 뼈대: ① 무엇이 문제였나 — 샹텐이 뒤로 갔나(`shanten_loss` > 0), 같은 샹텐에서 받는 패가 줄었나 ② 최선과 숫자 비교(버린 뒤 샹텐 · 유효패 장수) ③ **모양으로 본 까닭** — `shape` 에 근거가 있을 때만: 예) 뽑은 패가 `shape.drawn` 의 sequence 에 있고 버린 패가 그 sequence 에 끼어 있으면 "뽑은 패로 완성된 순자를 헐었다".
- `shanten_prev` 설명과 "유지" 규칙. 샹텐이 뒤로 간 차례에서는 유효패 장수가 늘어난 것을 손실 · 이득으로 말하지 않는다(`ukeire_loss` 가 음수일 수 있다).
- 순위(`rank`)는 굳이 쓰지 않는다. `only_best` · `only_actual` 은 까닭을 말하는 데 도움이 될 때만, 버린 패 자신이 유효패 목록에 있어도 언급하지 않는다.
- 등급 · 상태는 한국어 이름만(영어 칸 이름 금지). 존댓말을 쓰지 않는다(해라체 "…다" 로 통일 — 카드 문구와 맞춤).
- `REVIEW_THINKING` 기본값을 low 로. `PROMPT_VERSION = "r2"`.
