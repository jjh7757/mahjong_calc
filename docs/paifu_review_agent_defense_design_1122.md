# 설계서 — 복기 에이전트가 수비 질문에 답하게 하기 (2026-11-22)

**설계만 — 구현 · Gemini 호출 없음.** 사용자 "그쪽으로 설계"(새 에이전트 대신 있는 복기 에이전트의 범위를 넓히는 쪽). 바탕: `docs/paifu_review_agent_design_1121.md`(지금 에이전트 — 도구 7 · plan/act/verify/fallback · 지시문 a2, metrics 표 15-3 · 15-4), `docs/push_fold_design_1122.md`, `docs/record_consistency_design_1122.md`.

## 0. 요약

- 지금 에이전트는 수비 질문("리치 받고 뭘 버렸어야 했어?" · "이 패 위험했어?")에 **현물인지 아닌지까지만** 답한다(그 설계서 9절 한계 1, 지시문도 "밀기 · 내리기는 판단하지 않는다").
- 앱 엔진은 이미 패마다 방총 위험을 계산한다(`reviewPaifu(withEngine: true)` 의 `riskByKind` · `minRiskTile`). 이것을 **사실표와 도구에 더하면** 에이전트가 "버린 패가 손에서 몇 번째로 위험했나 · 가장 안전한 패는 무엇이었나 · 효율대로 버리려면 얼마나 위험한 패를 내야 했나" 를 말할 수 있다.
- **에이전트는 판정하지 않는다.** 위험의 크기와 순서(사실)를 찾아 말로 푼다. "접었어야 했다" 는 밀기 · 접기 판정이 통과해 사실표에 들어온 뒤에, 그 사실을 옮겨 말하는 것만 허용한다.
- **먼저 잰 것(1절):** 엔진의 "위험 %" 는 순서는 맞지만 값이 1.5배쯤 크다. 그래서 에이전트는 % 대신 **다섯 단계 말**로 말한다.
- 평가 재료가 문제다: 매장 예시 11판에 수비 차례가 **4개뿐**이다. 천봉 판을 같은 사실표 꼴로 만들어 쓴다(3절).

## 1. 먼저 잰 것 — 엔진의 위험 % 는 믿을 만한가 (metrics 표 16-11)

개발 200판, 남이 리치한 차례의 내 버림 14,711개(실제 방총 332 = 2.26%). `experiments/paifu_review/pushfold/risk_calibration.py`.

| 엔진 위험 % | 버림 | 실제 방총률 | 구간 안 엔진 평균 |
| --- | --- | --- | --- |
| 0 | 7,398 | 0.14% | 0.00% |
| 0 ~ 1 | 1,152 | 0.61% | 0.46% |
| 1 ~ 3 | 1,554 | 1.29% | 2.02% |
| 3 ~ 5 | 1,160 | 3.53% | 3.89% |
| 5 ~ 8 | 1,205 | 3.32% | 6.41% |
| 8 ~ 12 | 1,076 | 7.81% | 9.78% |
| 12 ~ 18 | 768 | 9.38% | 14.52% |
| 18 이상 | 398 | 14.57% | 23.36% |

- **순서는 맞다:** 엔진 위험 순 5분위의 실제 방총률 0.03 → 0.17 → 0.58 → 2.28 → 8.22%.
- **값은 크다:** 5% 위로는 실제의 1.3 ~ 1.9배. 엔진 평균 3.19% 대 실제 2.26%.
- "모두에게 안전패" 로 표시된 2,499개 중 방총 0. 위험 0 이지만 그 표시가 없는 패는 0.2%(10/4,899) — "0%" 가 "절대 안 쏘인다" 는 아니다.
- 고수의 버림이라 같은 위험 구간 안에서도 더 안전한 패를 골랐을 수 있다(고른 탓에 실제가 낮게 나오는 몫을 가르지 못함). 엔진 값에는 상대 타점 보정도 섞여 있다(`fixWithPoint`).

**그래서:** 에이전트는 엔진의 % 를 확률처럼 말하지 않는다. 단계 말로 바꾸고, 단계마다 위 표의 관측 비율을 `rule` 도구에 적어 둔다.

| 단계 | 조건(엔진 값) | 개발 200판에서 실제 방총 |
| --- | --- | --- |
| 안전 | 모두에게 안전패 표시 | 0 / 2,499 |
| 낮음 | 그 밖의 3% 미만 | 37 / 7,605 (0.5%) |
| 보통 | 3 ~ 8% | 81 / 2,365 (3.4%) |
| 높음 | 8 ~ 18% | 156 / 1,844 (8.5%) |
| 매우 높음 | 18% 이상 | 58 / 398 (14.6%) |

덧붙여 앱 화면의 "이 패 방총 위험 약 1.7%" 문구도 같은 숫자다 — 문구를 "어림" 이나 단계로 바꿀지는 따로 결정할 거리로 올린다.

## 2. 사실표에 더할 것 (앱, Dart — `lib/paifu/agent_facts.dart`, `version` 2)

엔진 리뷰가 있고 남이 리치한 차례에만 `defense` 칸을 채운다(없으면 `null`).

```
"defense": {
  "threat_winds": ["서"],
  "tiles": [                         // 손에 있는 패 종류 전부, 안전한 순
    { "tile": "7z", "level": "안전", "genbutsu": true },
    { "tile": "2s", "level": "낮음", "genbutsu": false },
    { "tile": "5p", "level": "높음", "genbutsu": false }
  ],
  "actual":    { "tile": "5p", "level": "높음", "rank": 9, "of": 10 },   // rank 1 = 가장 안전
  "safest":    ["7z"],
  "efficient": { "tile": "5p", "level": "높음" },   // 효율대로 버릴 패(엔진 추천 첫째)와 그 위험
  "stance": "pushed",                // pushed / folded / between — 버린 패가 가장 안전한 패보다 얼마나 위험했나의 사실(판정 아님)
  "fold_spot": null                  // 밀기 · 접기 판정이 통과한 뒤에만 true / false(4절)
}
```

- 단계는 1절 표의 조건을 Dart 상수로(3 · 8 · 18). `stance` 는 `docs/push_fold_design_1122.md` 3절의 정의(위험 차 5%p 이상 = pushed, 2%p 미만 = folded).
- **엔진의 % 값 자체는 사실표에 넣지 않는다**(에이전트가 옮겨 말할 수 없게).
- 사실표를 만들 때 `reviewPaifu(withEngine: true)` 가 필요하다(한 판 2 ~ 6초 — 앱은 이미 뒤에서 계산한다). 크기는 수비 차례 × 패 종류 13 안팎이라 60KB 목표에 영향 없음(시험에서 다시 잼).

## 3. 평가 재료 — 천봉 판을 사실표로

- 매장 예시 11판의 수비 차례는 L16 2 · r11 2 = **4개, 2샹텐 이상은 0.** 이것으로는 질문 세트를 못 만든다.
- `tool/tenhou6_features.dart` 가 천봉 한 국을 hero 시점 `Paifu` 로 바꾸는 길을 이미 갖고 있다(매장 4판 교차 검증 통과). 그 `Paifu` 로 `agentFacts` 를 내는 도구 `tool/tenhou6_agent_facts.dart` 를 만든다.
- 판: 맞추기 실험의 **검증 40판**(개발 판)에서 고른다. 시험 판은 열지 않는다. 고르는 조건(미리 적음): 남이 리치한 뒤 hero 버림이 3번 이상인 국 · 자리, 그중 hero 가 방총한 것과 끝까지 안 쏘인 것을 섞음.
- 천봉 판은 남의 쯔모기리 · 점수가 진짜라 매장 판보다 조건이 좋다. 매장 판에서의 품질은 4개로 눈으로만 본다(한계).

## 4. 도구 · 지시문 · 검증 (서버 — `app/review_agent.py`)

### 도구

| 도구 | 바뀌는 것 |
| --- | --- |
| `defense_info(turn)` (새) | 그 차례의 `defense` 칸 + 상태 + 알림(리치한 자리 없음 / 엔진 값 없음 / 손패 모름) |
| `what_if(turn, tile)` | 리치한 자리가 있으면 그 패의 위험 단계 · 가장 안전한 패와의 순서를 덧붙임 |
| `find_turns(...)` | 조건 `stance?`(pushed / folded) · `min_level?`(그 단계 이상 위험한 패를 버린 차례) 추가, 줄마다 버린 패의 단계 |
| `rule(name)` | "방총 위험"(다섯 단계의 뜻 · 1절의 관측 비율 · 고수 판에서 잰 값이라는 것 · 리치 없는 상대는 범위 밖) · "밀기 접기"(stance 의 뜻) |
| `safe_tiles` | 그대로(현물) |

도구 수 7 → 8. 한도(도구 6회 · 재시도 1회 · LLM 8회 · 60초)는 그대로 두고, 넘치는지 평가에서 본다.

### 지시문 a3

- 범위 문장을 바꾼다: "패효율과, **리치한 자리에 대한 방총 위험의 크기**까지 말한다. 밀지 접을지의 옳고 그름 · 타점 · 상대 대기 읽기는 판단하지 않는다."
- 위험은 다섯 단계 말로만 말한다. % 를 지어내지 않는다(검증이 막는다).
- 수비 질문은 `defense_info` 로 그 차례를 확인한 뒤 답한다. 여러 차례는 `find_turns` 의 `stance` · `after_riichi` 로.
- "접었어야 했다 · 밀어도 됐다" 같은 말은 `fold_spot` 사실이 있는 차례에만, 그 값 그대로. 없으면 "이 도우미는 밀지 접을지를 판정하지 않는다" 고 밝히고 사실(단계 · 순서 · 가장 안전한 패)까지만.

### 검증에 더할 것

1. 답 속 단계 말이 그 답의 evidence 에 있는 단계인가(evidence 에 "높음" 이 없는데 "높음" 이라고 쓰면 위반).
2. 판정 말(접었어야 · 접는 게 맞 · 밀면 안 · 밀어도 됐 …)은 evidence 에 `fold_spot` 이 `null` 이 아닌 차례가 있을 때만.
3. `N%` 는 지금 규칙 그대로(evidence 에 없으면 위반) — 사실표에 % 가 없으니 수비 답에서 % 는 `rule` 의 관측 비율을 읽었을 때만 통과한다.

## 5. 평가 (재기 전에 적는 안 — 표 15-4 와 같은 틀)

- **기계 시험(가짜 LLM, 돈 0):** 새 도구가 사실표 값 그대로 돌려주는가, 검증의 새 규칙 둘, `fold_spot` 이 null 일 때 판정 말이 막히는가.
- **사실표 대조(Dart 시험):** `defense.tiles` 의 순서 · 단계가 `reviewPaifu(withEngine)` 의 `riskByKind` 와 같은가, `actual.rank` · `safest` · `stance` 의 경계.
- **실제 호출(Gemini — 사용자 허락 뒤):** 질문 세트를 돌리기 전에 파일로 적는다.
  - 본 판 12(지시문을 다듬는 데 씀) + **안 본 판 12**(판정용). 세 종류 4개씩: 한 차례("9순에 버린 5통 위험했어?") · 대안("그때 뭘 버리면 안전했어?") · 판 전체("리치 받은 뒤 위험하게 버린 곳 있어?").
  - 기대 답은 사실표를 보고 미리 적는다. 판정을 유도하는 질문("접었어야 했지?")을 4개 넣어, 판정하지 않고 사실만 말하는지 본다.
  - **기준(안 본 12개):** 검증 통과(재시도 뒤 포함) ≥ 11 · 대체 답 ≤ 1 · 사람이 읽어 틀림 있는 답 ≤ 1 · **근거 없는 판정 0.**
  - **되돌아가지 않았나:** 표 15-4 의 질문 24개를 a3 로 다시 돌려 새 틀림 0.
- 기록: 검증 첫 통과 · 재시도 · 대체, 도구 호출 수, 시간(중앙 / p90 / 최대), 토큰. metrics 표 15-5 부터.

## 8. 한계

- **위험 단계의 관측 비율은 고수 판 · 리치 상대에서 잰 것**이다. 매장 손님 · 울기 상대 · 다마 텐파이에는 그대로 안 옮겨진다.

- 검증은 여전히 숫자 · 패 · 단계 말 · 판정 말의 유무만 본다. "이 패가 왜 위험한가" 같은 풀이 문장의 틀림은 사람이 읽어야 잡힌다.
- 질문은 세션이 쓴다 — 남이 쓴 질문으로는 아직 못 잼(표 15-4 와 같은 흠).
- 에이전트는 사실을 말로 옮길 뿐이다. 표 16-9 처럼 에이전트에게 고르게 하면 가중치보다 못했다 — 그래서 고르는 일은 끝까지 코드에 둔다.
