# 판 상태 추적 설계 — 고정 카메라로 게임 중 울기를 미리 읽어 두기 (2026-10-27)

전제가 되는 측정은 `problem_log.md` 29번이다: 화료 사진에서 울기 모서리를 잘라 내고 **손패 전용 문구**로 읽으면 자리 판독 정답은 그대로(120/120)이고 p90 14.1 → 9.2초, 긴 생각 11 → 0. 이 이득을 실전에서 얻으려면 화료 전에 울기를 이미 알고 있어야 한다. 그 "미리 알기"가 이 문서의 주제다.

평가 규칙은 그대로: 숫자는 B·C·D 6장(손패 전용 경로의 회귀 확인)과 **새로 찍을 고정 카메라 사진**(추적 자체의 평가)으로 따로 낸다. 자리 판독은 같은 요청 3개 + 만장일치 유지, 경주·출력 상한 없음, 판독은 Gemini 만(YOLO11 은 위치 검출만).

## 1. 결정 사항

| 항목 | 결정 | 근거 |

## 2. 해상도 게이트 (가장 먼저 잴 것)

울기를 읽을 사진을 어디서 얻느냐가 이 설계의 첫 갈림길이다. 실기기 없이 정할 수 없어 **측정 → 선택**으로 둔다.

| 경로 | 장점 | 단점 | 조건 |
| --- | --- | --- | --- |
| (가) 고해상 미리보기 `/preview?w=2000` | 셔터음 없음, 언제든 받음 | 이미지 스트림 해상도는 기기·플러그인이 정한다(에뮬레이터 640×480). S25 에서 1920 이상이 나와도 모서리 패가 70px 이 될지 미지수 | 헤드에 `w` 파라미터와 응답 헤더 `X-Frame-Size`(원 프레임 크기) 추가 → S25 거치 높이에서 모서리 패 폭 px 측정 |
| (나) 변화 확정 시 `/capture` 한 장 | 12MP, 지금 화료 사진과 같은 품질 | 한국 단말은 셔터음 강제. 판당 울기 이벤트 수(대개 2~6)만큼 소리 | 항상 가능. 소리가 매장에서 용인되는지는 사용자 판단 |
| (다) 헤드에서 스트림 최대 해상도 강제 | (가)와 같음 | camera 플러그인이 ImageAnalysis 해상도를 노출하지 않음 → 플러그인 수정/포크 | (가)가 모자랄 때만 검토 |

게이트: **S25 헤드 + 집 패 + 거치 높이 60~90cm 에서 `/preview?w=2000` 의 모서리 패 폭이 100px 이상이면 (가), 아니면 (나).** 두 경로 모두 아래 흐름은 같고, "읽기 사진을 어디서 받나" 만 다르다.

## 3. 흐름

### 게임 중 (추적)

```
헤드 /preview (3초마다, 긴 변 960)                     ← 이미 있음(테이블 배경)
  │
  ▼ 기기(순수 Dart, API 호출 없음)
변화 감지: 격자 cornerCell(4자리) 안의 흰 패 면 마스크 통계(넓이·무게중심·덩어리 수)
  ├─ 직전 프레임과 크게 다름 → "움직이는 중"(손·팔) → 기다림
  ├─ 두 프레임 연속 같음 + 기준(마지막 확정 때 통계)과 패 1장 넓이 이상 차이 → 이벤트(자리 s)
  └─ 같음 → 아무것도 안 함
  │
  ▼ 이벤트(자리 s)
읽기 사진 확보: (가) /preview?w=2000  또는  (나) /capture
  → cornerCell(s) 크롭 → /v2/corner → {melds, loose}
  → 정합성: 묶음 수는 줄지 않음(가깡은 3→4장), 한 자리 ≤ 4묶음, loose 는 도라 표시패 후보로만
  │
  ▼ 확정
직전 확정값과 같음 → 확정(confirmed), 통계를 새 기준으로
다름 → 다음 프레임에서 한 번 더 → 두 번 같으면 확정, 셋 다 다르면 unconfirmed(지금 방식으로 넘김)
  │
  ▼ 화면
테이블 화면 자리 칩: 울기 그림 + "미리 읽음" 표시. 누르면 다시 읽기 / 지우기
```

- 판이 바뀌면(점수판 이벤트: 화료·유국 기록) 네 자리 추적을 **전부 리셋**한다. 사진으로 판 전환을 알아내지 않는다(가운데 강 비움 감지는 2단계 후보).
- 카메라가 움직였으면(`FixedTable` 의 펠트 IoU 검사 재사용) 추적을 리셋하고 안내한다.
- 호출 예산: 울기 이벤트당 `/v2/corner` 1~3회. 판당 이벤트 2~6개면 판당 2~18회 — 지금 화료 1회(자리 3 + 강 1 + 리치 1 + 도라 1 = 6회)와 같은 자릿수. 기기 쪽 변화 감지는 호출 0.

### 화료 때

```
화료 촬영(지금과 같음) → 화료자 자리 판정(앞면 무늬, 18번)
  │
  ├─ 추적 상태[화료자] == confirmed && 마지막 확정 뒤 변화 이벤트 없음
  │     → handCell 크롭 → /v2/hand (손패 전용 문구, 3번 동시 + 만장일치)
  │     → 손패 + 추적 울기 병합 → 장수 검사(14 − 3 × 울기)
  │           통과 → 지금 merge 그대로
  │           실패 → /v2/seat 로 자리 전체 다시 읽기(지금 방식) → 그래도 실패면 확인 질문
  │
  └─ 그 밖(unconfirmed / 변화 뒤 미확정 / 추적 꺼짐 / 카메라 움직임)
        → 지금 방식(/v2/seat 자리 전체)
```

강 끝·리치봉·도라 호출은 지금 그대로 동시에 나간다. 변하는 것은 자리 판독 한 가지뿐이라 다른 측정값은 흔들리지 않는다.

## 6. 2단계 후보 (같은 틀로)

- **리치봉 자동 기록:** `sticksZone` 변화 → `/v2/sticks` → 어느 자리의 리치봉이 새로 보이면 점수판에 리치 자동 기록(이미 있는 "리치봉 자동 반영" 의 실시간판). 되돌리기 10초 창과 함께.
- **판 전환 감지:** 가운데 강이 비고 네 자리 모서리가 비면 새 판 → 추적 리셋을 사진으로. 점수판 기록이 늦을 때 보조.
- **강 추적(순목·후리텐):** 23번의 YOLO11 틀 + 줄별 읽기(패 단위 97.5%)가 올라오면. 지금은 안 함.

| **합계(중앙)** | 에뮬레이터 약 12.4초 | **약 9~10초** | 대부분 디코딩 제거, 일부 자리 판독 |
| **합계(p90)** | 약 30초 | **약 20초** | 자리 판독 꼬리가 줄고, 남는 꼬리는 강 끝 등 작은 호출의 생각 폭주 |

솔직한 요약: **중앙값은 2~3초(20~25%), 꼬리는 약 1/3 줄어드는 정도**다. 한 자릿수 초로 내려가는 큰 전환은 아니고, 남는 시간의 주인은 Gemini 의 생각(사진이 정함)과 3번 읽기의 가장 늦은 답이다. 이 설계의 진짜 값은 (1) 울기 읽기가 **화료 때의 임계 경로에서 게임 중으로 빠지는 것**, (2) 태블릿·파이의 요구 사양이 낮아지는 것, (3) 울기 학습 데이터가 쌓이는 것이다. 빨라지지 않는 것: 헤드 전송 1.2초, 3번 읽기 대기, 울기 없는 판의 자리 판독.

느려질 수 있는 곳: 매장 인터넷 업로드가 느리면(5Mbps 이하) 원본 3MB 가 5초 — 그때는 헤드 촬영 해상도를 낮추거나(패 100px 만 지키면 됨) 지금처럼 태블릿이 자르는 길을 설정으로 남긴다.

## 6-2. 비용 — 울 때마다 호출이 는다 (사용자 지적)

맞다. 판당 호출이 는다. 다만 **얼마나** 가 중요하다 — 토큰으로 세면 모서리 읽기는 자리 판독의 1/5~1/7 이다.

| 호출 | 입력 토큰(어림) | 판당 횟수 | 판당 토큰 |
| --- | --- | --- | --- |
| 지금 화료 1회: 자리 /v2/seat × 3(ULTRA_HIGH + 확대 토막 3 + 참고표) | 약 10.6k × 3 | 1 | 약 32k |
| 지금 화료 1회: 강 끝 /v2/last3(YOLO 조각 + 참고표)·리치봉·도라 | 약 2~4k × 3 | 1 | 약 8k |
| **추적: 모서리 /v2/corner**(작은 크롭 한 장, 토막·참고표 없음) | 약 1.5~2k | 울기 수 × 1~2(픽셀 지름길이면 1) | 울기 4개 기준 약 6~16k |
| 추적 화료: /v2/hand(울기 뺀 손패 칸, 토막·참고표 그대로) | 약 9~10k × 3 | 1 | 약 28k(−10%) |

판당 토큰 약 40k → 42~56k, **+5~40%**(울기 수에 따라). 울기가 없는 판(절반쯤)은 +0. 판당 요금으로 치면 지금의 1.1~1.4배.

줄이는 장치(코드에 넣음, `TrackerConfig`):
- **픽셀 지름길:** 읽은 패 장수가 픽셀 어림과 맞으면 두 번째 읽기를 생략(울기 하나당 1회). 틀린 종류를 잡는 힘은 줄지만 화료 때 장수 검사·3번 읽기가 남아 있고, 이 지름길은 "장수가 맞는 오독" 만 통과시킨다.
- **같은 자리 읽기 간격 5초, 한 변화에 최대 3번**, 세 번 다 다르면 포기(지금 방식으로).
- 손이 지나가는 동안은 읽지 않음(두 프레임 안정 조건), 패 1장 미만 변화는 무시.
- 확정보다 적게 읽히면(가림) 버림 — 헛 호출은 있지만 틀린 확정은 없음.

그래도 비싸면: 추적을 "울기가 많은 사람" 에게만(모서리에 처음 변화가 생긴 자리만 계속), 또는 설정으로 끄기. 이득(자리 판독 p90 −35%)과 비용(+5~40%)의 저울질은 7절 측정 뒤 사용자가 정한다.

## 7. 평가 계획

측정은 세 겹이다. 사진 없이 할 수 있는 것부터.

1. **노트북(에뮬레이터 헤드 + Windows 앱)** — HANDOFF "노트북만으로 키오스크 시험하기". `fake_head.py` 에 **시간순 사진 폴더 재생**(울기 전 → 손 들어옴 → 울기 후 → 화료)을 더해 상태 기계·호출 수·fallback 을 확인. 숫자는 흐름 확인용.
2. **집 패 + S25 헤드 고정 촬영(새 사진, 추적 평가의 본 세트):** 거치 60·75·90cm, 자리 4곳 × {퐁, 치, 대명깡, 가깡(3→4장), 안깡, 울기 2개, 도라 표시패를 손패 옆에 둔 경우} 를 손으로 재현, 각 20회. 지표:
   - 울기 확정 정확도(묶음 종류·장수 모두 맞음), 확정까지 프레임 수·초, 헛 이벤트(변화 없는데 읽음)·놓친 이벤트
   - 판당 `/v2/corner` 호출 수
   - **해상도 게이트 값:** `/preview?w=2000` 모서리 패 폭 px vs 확정 정확도
3. **화료 경로(B·C·D 6장 + 2의 화료 사진):** 추적 있음(`/v2/hand`) vs 지금(`/v2/seat`)을 같은 시각에 나란히 60회씩 두 회차 — 정답, p50/p90/최대, 생각 횟수, 틀린 채 반영 0 유지, fallback 비율. 29번 숫자(p90 −35%)가 앱 흐름에서도 나오는지.

채택 기준: 틀린 채 반영 0 유지, 확인 질문 비율이 지금보다 늘지 않음, 자리 판독 p90 이 두 회차 모두 줄어듦.

### 매장에서 두 버전을 같이 재는 법 (사용자 질문: "지금 버전과 이전 버전 둘 다 실험하고 싶다")

같은 APK·같은 서버로 된다. 서버는 경로가 하나 늘었을 뿐 `/v2/seat` 경로는 그대로라 "이전 버전" 은 추적을 끈 상태다.

| 방법 | 무엇 | 언제 |
| --- | --- | --- |
| **토글** (거치 화면 더보기 "판 상태 추적") | 끄면 지금 흐름(`/v2/seat`) 그대로, 켜면 추적 + `/v2/handonly`. 촬영 기록 `setup.tracking` 에 모드가 남는다 | 판 단위로 번갈아. 쉽지만 두 모드가 다른 사진·다른 시각이라 비교가 거칠다(27번: 같은 조건도 시각 따라 뒤집힘) |
| **그림자 모드** (실험 플래그, 기본 꺼짐) | 추적이 확정된 자리의 화료 때 `/v2/handonly` 와 `/v2/seat` 를 **같은 사진으로 동시에** 보내고, 결과는 설정한 한쪽을 쓰되 둘 다(답·시간·agreement·생각 여부)를 기록 | 한 화료가 곧 한 쌍의 비교. 비용은 그 화료만 자리 호출 2배. **매장 실험은 이 모드로** — 짝 비교라 60회 × 2회차 없이도 결론이 선다 |

그림자 모드의 기록은 `experiments/speed` 의 측정 표와 같은 열로 남겨 바로 problem_log 30번 표가 되게 한다. 주의: 추적은 첫 프레임을 기준으로 삼으므로 **판이 시작되기 전에 켜 둔다**(판 중간에 켜면 이미 놓인 울기는 "변화 없음" 이라 그 자리는 지금 방식으로 간다 — 틀리진 않지만 비교 대상이 안 됨).

## 10. 기기 부하와 역할 분담 (2026-10-27 사용자 지적 두 가지: "태블릿 성능이 더 중요해진다", "헤드는 나중에 성능 낮은 라즈베리파이")

| --- | --- | --- | --- |
| 미리보기 받기·배경에 그리기(3초마다, 960px JPEG 30~200KB) | 태블릿 | 플랫폼 디코더, 수십 ms | 지금 이미 돌고 있음 |
| 모서리 칸 4개 변화 통계(960px 프레임) | 태블릿, isolate | 중급 폰 약 100~150ms / 3초 → 한 코어의 3~5% | 모서리 칸만 디코딩 범위로 자르면 더 준다. 밀리면 그 프레임은 버림(큐 없음). 태블릿이 너무 약하면 프레임을 서버에 보내 서버가 통계(테이블당 1MB/분) — 예비 |
| 이벤트 때 고해상 모서리 크롭 | **서버** | 디코딩 + 자르기 0.3초 | 태블릿은 헤드에서 받은 바이트를 `/v2/upload` 로 그대로 넘기고 `image_id` + 상자로 `/v2/corner`. 디코딩 없음 |
| `/v2/corner`·`/v2/hand` 읽기 | 서버(Gemini) | — | 태블릿은 HTTP 만 |
| 화료 때 12MP 원본 디코딩·5구역 자르기 | 태블릿(지금, isolate) → **서버로 옮김(2단계)** | 에뮬레이터 2.9초 → 서버 0.3초 + 업로드 1~3MB(Wi-Fi 0.5~1초) | 지금 가장 무거운 태블릿 일. 같은 `/v2/upload` + `image_id` 로 옮기면 사라진다. 앱의 `readGrid` 조율과 merge(점수 규칙)는 그대로 태블릿에 둔다 — 바뀌는 건 "자르기를 어디서 하나" 뿐 |
| 키오스크 화면(점수판·칩·연출) | 태블릿 | 보통 UI | 가볍다 |

왜 헤드가 아니라 서버인가: 헤드에서 자르면 S25 에선 되지만 파이에선 12MP 디코딩만 1초 넘게 걸리고 메모리도 빠듯하다. 서버는 이미 사진을 받아 Gemini 로 넘기는 자리라 자르기가 한 단계 더 붙을 뿐이고, 기기 종류와 무관하게 같은 속도가 난다. 전송량은 지금(크롭 5~7장, 합계 1~2MB)과 원본 1장(1~3MB)이 같은 자릿수라 Wi-Fi 에서 체감 차이가 작다 — 실측으로 확인할 항목.

결론: 추적이 태블릿에 더하는 것은 "3초마다 960px 프레임 통계" 하나뿐이고, 파이 헤드에 더하는 것은 없다. 오히려 `/v2/upload` 를 넣으면 지금 태블릿에서 가장 무거운 화료 때 12MP 처리까지 서버로 보낼 수 있어 태블릿·헤드 둘 다 요구 사양이 낮아진다. 실제 태블릿 기종이 정해지면 `integration_test/read_grid_timing_test.dart`(기기 처리 시간)를 그 기기에서 한 번 돌려 숫자를 남긴다.

### 사진이 지나가는 길 (사용자 질문: "파이 → 서버 → 태블릿이고 파이 → 태블릿은 없나?")

아니다. **파이 → 태블릿은 그대로 있고, 큰 사진은 태블릿이 디코딩 없이 서버로 중계한다.**

```
(A) 지금 설계 — 태블릿이 조율, 헤드는 LAN 만
  파이 ──LAN, 3초마다 960px──▶ 태블릿  (배경 + 변화 통계, 서버 안 거침)
  파이 ──LAN, 12MP 1~3MB────▶ 태블릿 ──인터넷, 같은 바이트 그대로──▶ 서버(/v2/upload → image_id)
                               태블릿 ──image_id + 상자──▶ 서버(/v2/corner·/v2/seat…) ──읽은 결과(JSON)──▶ 태블릿

(B) 대안 — 헤드가 서버에 직접 올림
  파이 ──LAN, 960px──▶ 태블릿                      (미리보기는 그대로 LAN)
  태블릿 ──"찍어서 올려"──▶ 파이 ──인터넷, 12MP──▶ 서버 ──image_id──▶ 파이 ──image_id(수십 바이트)──▶ 태블릿
  태블릿 ──image_id + 상자──▶ 서버 ──결과──▶ 태블릿
```

| | (A) 태블릿 중계 | (B) 헤드 직접 업로드 |
| --- | --- | --- |
| 큰 사진이 지나는 횟수 | LAN 1번 + 인터넷 1번 | 인터넷 1번 |
| 더 드는 시간 | LAN 1~3MB 약 0.2~0.5초(지금 화료 촬영도 같은 길) | 없음 |
| 헤드에 필요한 것 | LAN 서버 하나(지금 그대로) | 인터넷 연결 + 서버 API 키 + HTTPS 클라이언트 + 재시도. 파이 펌웨어가 커지고 키가 기기에 들어감 |
| 서버에 필요한 것 | `/v2/upload` | `/v2/upload` + 헤드·태블릿 짝 맞추기(세션) |
| 매장 Wi-Fi 가 기기 간 통신을 막을 때(AP isolation, HANDOFF 위험 항목) | LAN 이 막히면 미리보기도 촬영도 안 됨 → 핫스팟 | 촬영은 되지만 미리보기(LAN)는 같이 막힘 → 결국 핫스팟이거나 미리보기도 서버 경유 |

선택: **(A)로 시작.** 태블릿이 큰 사진을 디코딩하지 않는 한 "지나가는" 비용은 LAN 0.2~0.5초뿐이고, 지금 화료 촬영도 이미 그 길이다. 헤드는 끝까지 "카메라 + LAN" 만 알면 되어 파이로 바꿀 때 할 일이 가장 적다. `/v2/upload` 는 올리는 쪽이 누구든 같게 만들어 두어, 매장 Wi-Fi 사정으로 (B) 가 필요해지면 헤드에 "찍어서 올려" 한 가지만 더하면 되게 한다. 미리보기는 어느 안이든 LAN 이다(서버를 거치면 3초마다 왕복 비용과 지연이 붙는다).

파이 하드웨어 메모(사용자 질문 "인터넷 연결하려면 와이파이 모듈이 따로 필요하지 않나"): 헤드 후보인 Pi Zero 2 W·3B+·4·5 는 **Wi-Fi(2.4GHz, 3B+ 이후 5GHz 도)·블루투스 내장**이라 모듈이 따로 필요 없다. 없는 것은 옛 Pi 1/2·Zero(W 아님)·Pico(W 아님) 뿐. (A) 의 LAN 통신(파이 ↔ 태블릿)도 같은 Wi-Fi 를 쓰므로 어느 안이든 추가 부품은 없다. 매장 Wi-Fi 가 기기 간 통신을 막으면 **태블릿 핫스팟**에 파이를 붙이는 쪽이 가장 단순하다(파이는 인터넷이 필요 없고 태블릿만 밖으로 나간다 — (A) 의 장점이 여기서도 유지).

부하가 문제로 보일 때의 손잡이: 폴링 간격 3 → 5초, 변화 통계를 두 프레임에 한 번, 추적 끄기(더보기), 배경 미리보기 해상도 960 → 640, 변화 통계를 서버로.
