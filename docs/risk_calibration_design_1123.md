# 설계서 — 엔진 "방총 위험 %" 를 실제 방총률에 맞추기 (2026-11-23)

계기: 사용자 "위험 % 바로잡기"(논문 정리 `docs/opponent_reading_papers_1123.md` 의 "우리 쪽에 쓸 것" 1번). 栗田 · 保木(2017)는 추정 방총 확률을 0 ~ 8% 사이 1%p 구간마다 실측과 맞대어, 차이가 약 1%p 임을 보였다. 우리 엔진(`lib/engine/risk.dart` 의 `mixed34`)은 순서는 맞지만 값이 5% 위로 실측의 1.3 ~ 1.9배다(metrics 표 16-11, 개발 200판). 앱은 이 값을 그대로 "이 패 방총 위험 약 6.4%" 로 보여 준다.

**상태: 설계 · 기준 적음 → 1단계(측정) 맡김.** 앱 · 서버 코드는 1단계 결과를 보고 고친다.

## 0. 하는 일

엔진 값 하나를 받아 실제 방총률 쪽 값을 돌려주는 **보정표**(단조 증가 꺾은선)를 만든다. 엔진 계산 자체는 건드리지 않는다. 표시할 때만 보정표를 거친다. 그러면 위험한 패의 순서는 그대로 두고 숫자만 바뀐다.

## 1. 자료 (결과 전 고정)

- **맞춤(개발):** `experiments/paifu_review/results/mxfit/stage1/joined.jsonl.gz`. 천봉 鳳凰卓 개발 200판에서 앱과 같은 Dart 엔진(`tool/tenhou6_features.dart`)으로 뽑은 차례별 후보 위험이다. 표 16-11 과 같은 자료다.
- **시험:** `experiments/paifu_review/results/mxfit/stage2/joined.jsonl.gz`. 시험 200판(mxfit 2단계, 표 16-7)이다. S42 버림 맞춤에는 썼지만, **위험값을 실제 방총과 맞댄 적은 없다.** 이번 보정의 시험 판으로 쓰고 한 번만 연다.
- **대상 차례:** 위협 자리가 있고(`riskSeats` 가 비지 않음) 내가 리치 중이 아닌 내 버림. 앱이 "방총 위험" 줄을 보여 주는 조건과 같게 맞춘다. 위협의 종류로 나눈다.
  - **R:** 리치한 자리가 하나 이상
  - **C:** 리치는 없고 울기 위협만
- **방총의 정의(표 16-11 과 같음):** 그 버림이 그 국에서 내 마지막 버림이고, 결과가 론이며, 방총자가 나다. 리치하지 않은 자리에게 쏘인 것도 센다.
- 값은 실제 버린 패의 엔진 값(`risk` of actual)이다.

## 2. 보정 방법 (결과 전 고정)

1. **모두에게 안전패**(`safeAll`)로 표시된 버림은 따로 둔다. 표 16-11 에서 2,499개 중 방총 0이었다. 보정값은 0 이고 앱에는 "안전" 으로 보인다.
2. 나머지에 엔진 값 → 방총 여부로 **단조 회귀(PAV, isotonic)** 를 맞춘다.
3. 이웃 덩어리를 합쳐 덩어리마다 버림이 **200개 이상**이 되게 한다. 덩어리가 작으면 값이 흔들리기 때문이다.
4. 덩어리마다 (엔진 값 평균, 실제 방총률) 점을 찍고, 점 사이를 **직선으로 잇는다.** 끝은 다음과 같이 처리한다.
   - 엔진 0 → 엔진 0 덩어리의 실측
   - 마지막 점 위 → 마지막 점 값에 고정
   - 결과는 줄어들지 않는(비감소) 꺾은선이다.
5. 보정표는 R 과 C 따로 만든다. C 가 개발 판에서 200개 덩어리를 셋도 못 만들 만큼 적으면 R 표를 C 에도 쓰고, 그 사실을 적는다.
6. 보정표는 점 목록(JSON)으로 낸다. 앱은 같은 점으로 직선 보간만 한다.

## 3. 시험 판에서 잴 것

R 과 C 를 따로, 보정 전(엔진 값 그대로)과 보정 후를 나란히 잰다.

- **구간 표:** 엔진 값 구간 0 · 0 ~ 1 · 1 ~ 3 · 3 ~ 5 · 5 ~ 8 · 8 ~ 12 · 12 ~ 18 · 18+ 마다 다음을 적는다. 버림 수, 실제 방총률, 엔진 평균, 보정 평균, 판 단위 부트스트랩 95% 구간.
- **ECE:** 같은 개수로 나눈 10 구간에서, 구간마다 (예측 평균 − 실측) 절댓값을 버림 수로 가중 평균한 값.
- **Brier 점수:** (예측 − 실제)² 의 평균. 작을수록 좋다.
- **전체 평균:** 예측 평균 대 실측.
- **순서:** 보정은 단조 증가라 순서가 바뀌지 않는다. 직선 보간이라 동률도 새로 생기지 않는다. 다만 엔진 값 동률은 그대로 남으니 확인만 한다.

## 4. 채택 기준 (결과 전)

**R(주 판정)** 은 셋 모두 맞아야 채택한다.

1. 시험 판 ECE 가 0.5%p 이하이고, 보정 전보다 작다.
2. 버림이 300개 이상인 엔진 값 구간마다 |보정 평균 − 실측| ≤ 1.0%p 다. 栗田 · 保木와 같은 문턱이다.
3. Brier 점수가 보정 전보다 작다.

**C** 도 같은 기준으로 따로 판정한다.
- C 가 못 미치면 앱에서는 울기 위협만 있는 차례의 % 를 보정하지 않는다. 대신 "(울기 상대, 어림)" 을 붙이는 안을 사용자에게 묻는다.
- C 표본이 적어 판정할 수 없으면 그렇게 적는다.

**R 이 못 미치면** 보정표를 앱에 넣지 않는다. 원인(시험 판과 개발 판의 차이, 덩어리 크기 등)을 적고 사용자에게 묻는다. 시험 판을 보고 방법을 고쳐 다시 재지 않는다. 고친다면 새 시험 판이 필요하다.

## 5. 한계 (미리 적음)

- **고른 패만 본다.** 실측은 鳳凰卓 고수가 **실제로 버린 패**만으로 센 것이다. 같은 엔진 값이어도 고수는 엔진이 못 보는 근거로 더 안전한 쪽을 골랐을 수 있다. 그래서 사용자가 버리지 않은 다른 패에 보정값을 쓰면 조금 낮게 나올 수 있다. 栗田 · 保木도 같은 방식으로 쟀다.
- **鳳凰卓 기준이다.** 매장 손님은 대기 모양 · 리치 습관이 달라 실제 방총률이 다를 수 있다. 매장 판은 몇 판 안 되어 잴 수 없다.
- **방총 하나만 본다.** 점수(얼마나 비싼가)는 이번 범위가 아니다.

## 6. 앱 쪽 (채택되면 2단계 — 사용자 확인 뒤)

- `lib/engine/` 에 보정표와 보간 함수를 하나 둔다. 엔진 계산(`riskOf`) 은 그대로 둔다.
- 다음 표시들이 보정값을 쓴다.
  - `review_view.dart` 의 "이 패 방총 위험 약 X%"
  - "가장 안전: … (X%)"
  - 엔진 표의 "방총 위험" 칸
  - 모두에게 안전패는 "안전" 으로 표시한다.
- **복기 에이전트 사실표 · 다섯 단계 · 서버 지시문(a5)은 이번에 바꾸지 않는다.** 단계는 엔진 값 문턱으로 정해져 있고, 바꾸면 통과한 평가를 다시 해야 한다. 단계 설명(`rule` 도구)의 관측 비율을 시험 판 값으로 바꿀지는 따로 묻는다.
- 시험: 보정 함수 단위 시험(점 위 · 사이 · 끝, 비감소)과 기존 복기 화면 시험의 기대 문구 갱신.

## 8. 다시 재기 — 고친 기준 · 새 시험 판 (2026-11-23, 사용자 "새 판으로 재 봐") — 결과 전에 적음

**왜:** 1단계의 기준 ② 는 높은 구간에서 표본 흔들림을 무시했다. 보정이 완벽해도 R 80% 확률로 떨어지는 문턱이었다(problem_log 79). 첫 시험 판(mxfit 시험 200판)은 이미 결과를 봤으니, 고친 기준은 새 판에서만 판정한다.

**자료:**
- 새 시험 판은 천봉 1,000판 중 **남은 599판**이다. `split.test_games()` 의 ID 순 뒤 599판이며, mxfit 은 "나머지 599판은 안 엶"(표 16-7). 대기 수트 실험(표 17-2)의 시험 판에는 들어 있었지만, 그 실험은 엔진 위험값을 쓰지 않았다.
- 엔진 값은 1단계와 같은 도구(`tool/tenhou6_features.dart`)로 새로 뽑는다. 차례 고르기(내가 리치 중인 차례 빼기, 깡 든 국 빼기 등)도 stage2 와 똑같이 한다.

**보정표:** 1단계에서 개발 200판으로 만든 `results/riskcal/table.json` 을 **그대로** 쓴다. 다시 맞추지 않는다.

**기준(R · C 각각):**
1. ECE ≤ 0.5%p 이고 보정 전보다 작다. (1단계와 같음)
2. **고침:** 버림이 300개 이상인 엔진 값 구간마다 |보정 평균 − 실측| ≤ max(1.0%p, 2 × SE) 다. SE 는 √(p(1 − p) / n) 이고, p 는 그 구간의 보정 평균, n 은 버림 수다.
3. Brier 점수가 보정 전보다 작다. (1단계와 같음)

**시험 판을 열기 전 확인:** 고친 ② 가 흔들림에 버티는지 본다. 개발 행에서 보정값을 참 확률로 두고 방총을 1,000번 뽑아, ①②③ 을 모두 통과하는 비율을 R · C 따로 적는다. 80% 미만이면 시험 판을 열지 않고 사용자에게 묻는다.

**채택:**
- R 과 C 가 **모두** 통과하면 앱 2단계(6절)로 간다.
- 하나만 통과하면 화면 숫자의 뜻이 섞이므로 사용자에게 묻는다.
- 둘 다 못 미치면 접는다.
- 이 판도 한 번만 채점하고, 결과를 본 뒤 기준 · 표를 바꾸지 않는다.

**참고로만 적을 것(판정에 안 씀):** 첫 시험 200판 + 새 599판을 합친 799판에서의 같은 지표. 1단계 기준 ②(고정 1%p)를 새 판에 적용한 결과.
- (2026-11-23) **8절 열기 전 점검에서 멈춤:** ①②③ 통과율 R 79.8%(< 80%) · C 84.6%. 고친 ② 가 다중 비교를 무시했다(2×SE 구간 넷 → 약 20% 가 떨어짐). 599판은 열지 않았다. 참고로 599판 크기로 돌리면 R 88.2 · C 87.0%. 다음 기준은 사용자 결정 뒤 이 아래에 결과 전에 적는다.

## 9. 다시 고친 기준 — 3×SE · 시험 크기 점검 (2026-11-23, 사용자 "3×SE · 시험 크기 점검") — 결과 전에 적음

8절과 같은 것과 다른 것을 나눠 적는다.

**그대로:** 새 시험 599판, 1단계 `table.json` 그대로, 기준 ① · ③, 채택 규칙(R · C 모두 통과해야 앱 2단계, 하나만이면 사용자에게, 둘 다 못 미치면 접음), 한 번만 채점.

**② 를 고침:** 버림이 300개 이상인 엔진 값 구간마다 |보정 평균 − 실측| ≤ max(1.0%p, **3** × SE) 다. SE = √(p(1 − p) / n), p 는 그 구간의 보정 평균, n 은 그 구간의 시험 판 버림 수다.

**열기 전 점검을 고침:**
- 개발 200판에서 **판 단위로 599판을 복원 추출**(같은 판이 여러 번 뽑혀도 됨)해 시험 크기의 가짜 자료를 만든다.
- 그 자료의 차례마다 보정값을 참 확률로 두고 방총을 뽑는다.
- 이것을 1,000번 되풀이해 ①②③ 을 모두 통과하는 비율을 R · C 따로 낸다.
- **둘 다 90% 이상**일 때만 599판을 연다. 못 미치면 멈추고 사용자에게 묻는다.
- 씨는 8절 시뮬레이션과 다른 고정값을 쓰고 적는다. 한 번만 돌린다.

**알고 있는 빈틈:** 방총은 국마다 한 번뿐이라 같은 국 안의 차례끼리 묶여 있는데, 시뮬레이션과 SE 식은 이를 무시한다. 3×SE 로 넓힌 것이 이 몫도 일부 덮는다. 판 단위 부트스트랩 구간도 함께 적는다.

- (2026-11-23 저녁, 9절 결과 — metrics 표 16-14) 열기 전 점검 통과율 R 98.8% · C 98.7% → 599판을 한 번 채점 → **R · C 둘 다 통과.** R 은 ECE 1.015 → 0.216 · 평균 3.16 → 2.25%(실측 2.27%), C 는 ECE 0.623 → 0.234. C 의 18+ 구간은 +3.79%p(문턱 5.44)로 아슬아슬하다. 6절 앱 2단계는 사용자 확인 뒤.
- (2026-11-23 밤, 6절 앱 2단계 — 사용자 "앱에 넣어 줘") 구현 Opus 5.5 높음 하위 에이전트, 검토 세션. 새 `lib/engine/risk_calibration.dart`(R 13점 · C 17점, `tool/gen_risk_calibration.py` 가 `table.json` 에서 생성 · `--check` 로 바이트 · 값 대조), `TurnReview.riskThreat` · `riskSafeForAll`(getter 만, 엔진 원래 값 · 사실표 그대로), `review_view.dart` 의 "이 패 방총 위험" · "가장 안전" · 엔진 표 칸 · 도움말이 보정값 · "모두에게 안전" 을 씀. "가장 안전" 은 원래 값 동률 묶음 안에 모두에게 안전패가 있으면 그 패를 보여 줌(화면만 — `minRiskTile` 그대로, 예시 22판 116차례 중 8차례가 바뀜). 세션이 다시 돌림: analyze 0 · `flutter test` 1,651 통과 · 생성 대조 같음. 웹 빌드로 예시 동1국 4만 버림 차례에서 "약 9.6%"(엔진 15.1) · 표 칸 9.6% 확인. 남은 것: 내가 리치한 뒤 차례는 보정표 범위 밖(펼침은 원래 숨김), 커밋 · 태블릿 확인 안 함.
