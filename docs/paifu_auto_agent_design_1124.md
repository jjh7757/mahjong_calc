# 대국 뒤 자동 패보 에이전트 — 설계서 (2026-11-24)

사용자: "대국 끝나고 자동으로 패보 만들어주는 에이전트 어떻게 생각하니" → "사용자에게 묻는건 나머지 할거 다하고 따로 확인이 필요한 부분만 묻는걸로 설계 시작해".

**한 줄:** 11-23 에 사람(세션)이 손으로 이어 붙였던 "헤드 녹화 → 한 반장 패보" 흐름(HANDOFF "2026-11-23 아침" 절 · metrics 표 12-115 · 12-116 · problem_log 77)을 **한 번 시작하면 끝까지 사람 없이 도는 흐름**으로 묶는다. 도는 동안에는 아무것도 묻지 않는다. 확신이 없는 곳은 가장 그럴듯한 답으로 채우고 "확인 필요" 표시를 붙인 채 계속 간다. 끝나면 **확인이 필요한 것만 모아 한 페이지(영상 + 고르기)로 한 번** 묻고, 답이 오면 자동으로 다시 조립한다.

이 설계서에는 코드와 측정이 없다. 구현은 Opus 5.5 높음 하위 에이전트에 맡기고, 이 세션이 검토한다(기억 `feedback-stepwise-delegation`).

## 2. 범위

**한다**
- 입력: 헤드 녹화 폴더 하나(`f_<epoch ms>.jpg`, 1496², 초당 약 10장) + 날짜. 앱 대국 기록이 있으면 같이 받는다(선택).
- 출력: 반장의 판마다 패보 JSON(지금 형식 — 네 자리 버림 · 울기 · 리치 · 결과 · 손패 주인의 매 순 손패 · 국 시작 점수) + **확인 꾸러미**(아래 5절) + 실행 보고서.
- 시작 방식: PC 에서 명령 하나. 대국이 끝난 뒤 녹화를 PC 로 옮겨 놓고 시작한다.

**하지 않는다**
- 앱 · 서버에 넣지 않는다. 앱의 "손패 복원 (Claude API)" 버튼(11-21, 실제 호출 0)은 건드리지 않는다.
- Claude API 를 부르지 않는다(기억 `no-claude-api-credits`). 읽기는 Claude Code 하위 에이전트로 한다.
- 매장 실시간은 하지 않는다. 대국 뒤 몇 시간 안에 결과를 받는 것이 목표다.
- 점봉 이동은 하지 않는다(11-23 에도 못 읽음). 남의 쯔모기리 채우기(B4)는 2단계 이후에 붙일지 따로 정한다.

## 3. 흐름 — 묻지 않고 끝까지

전체를 상태 기계 하나(`paifu_auto.py`, 새 파일)가 돈다. 단계마다 결과 파일을 남기고, 그 파일이 있으면 건너뛴다. 그래서 사용량 한도나 노트북 종료로 끊겨도 같은 명령으로 이어 갈 수 있다(11-23 에 5시간 한도로 한 번 멈춤).

```
S0 준비 ─ S1 판 경계 ─ S2 프레임 ─ S3 버림 기록 ─ S4 판 결과 ─ S5 대조·고침 ─ S6 손패 차례 ─ S7 앞뒤 검사·다시 읽기 ─ S8 조립 ─ S9 확인 꾸러미
                └──────────────── 어느 단계든 "확신 없음" → 최선 답으로 채우고 질문 목록(questions.jsonl)에 한 줄 더함, 멈추지 않음 ────────────────┘
```

**LLM 이 판단하지 않는 것:** 단계 순서, 다시 읽을지, 무엇을 확정할지는 모두 코드가 정한다(11-17 "LLM 은 동작만, 코드가 굴림"). 하위 에이전트는 주어진 프레임을 읽고 정해진 꼴의 답 파일 하나만 쓴다(`opusread.py` TASK 의 "다른 파일 열지 말 것" 그대로).

## 4. 하위 에이전트를 어떻게 띄우나

Python 은 Claude Code 하위 에이전트를 직접 부를 수 없다. 두 방식이 있다.

- **(가) 세션이 지휘(권장, 11-23 과 같은 방식):** 이 세션이 `paifu_auto.py next` 를 부른다. 스크립트는 "다음에 읽을 꾸러미 목록"(폴더 + TASK.md)을 내놓고, 세션은 그 수만큼 하위 에이전트(Opus · effort high)를 병렬로 띄운다. 끝나면 다시 `next` 를 부른다. 목록이 비면 끝이다. 세션이 하는 일은 띄우고 기다리는 것뿐이다. 판단은 스크립트가 한다. 이 순서를 스킬 하나(`/paifu-auto <녹화 폴더>`)로 적어 두면 새 세션도 같은 순서로 돈다.
- **(나) 스크립트가 `claude -p` 를 직접 부름:** 완전 무인이 되지만 Claude Code 를 새 방식으로 쓰는 일이라 사용자 허락이 필요하다(기억: 새로 쓰려면 먼저 묻기). 7절 질문 ①.

(가)로 만들고, 꾸러미 꼴이 같아서 나중에 (나)로 바꾸기 쉽다.

병렬 수: 한 번에 8개. 한도에 걸리면 `state.json` 에 남은 꾸러미가 그대로 있으니 다시 시작하면 된다.

## 5. 끝난 뒤 한 번 묻기 — 확인 꾸러미

**질문 한 줄**(`questions.jsonl`)에 넣는 것:
- `id` · 판 · 순 · 종류(`turn_slot` 차례 칸 / `pick` 패 고르기 / `yesno` / `boundary` 판 경계)
- 지금 채운 답과 다른 후보(최대 3)
- 근거 영상 구간(시작 · 끝 시각) — 자른 mp4 를 같이 둔다(기억 `give-video-for-user-check`)
- **영향:** 이 답이 다른 후보로 바뀌면 바뀌는 순 손패 수 · 결과 점수가 바뀌는지. 계산은 S8 조립을 후보마다 한 번씩 더 돌려서 한다.

**고르기 규칙**
- 영향이 0(어느 후보든 패보가 같음)이면 묻지 않고 보고서에만 적는다. 11-23 n06 6순(버린 칸 12 ↔ 13, 같은 패라 손패 같음)이 이 경우다.
- 영향이 큰 것부터 늘어놓는다. 결과 점수가 바뀌는 것(뒷도라 · 해저 · 화료자) → 바뀌는 손패 순이 많은 것 순서.
- 목표: 한 반장에 질문 10개 이하. 넘으면 보고서 맨 위에 "질문이 많음 — 원인" 을 적는다. 이것은 실패 신호다.

**확인 페이지:** `han3_truthserver.py` 와 `han3_checkserver.py` 를 하나로 합친 `auto_checkserver.py`(실행 설정 하나). 질문 종류별 입력(칸 정답 입력 · 패 고르기 · 예/아니오), 영상, "지금 답" 은 **안 보여 줌**(11-16 부터 지켜 온 가린 확인). 답은 `answers_user.json`.

**답이 오면:** `paifu_auto.py apply` 가 답을 넣고 S7 → S8 을 다시 돈다(앞뒤 검사가 다시 걸리면 그 차례는 질문 목록에 다시 올라감). 그다음 `han3_install.py` 꼴로 앱 예시 폴더에 복사하고 `flutter test` 를 돌린다. 앱 예시에 올릴지는 사용자가 정한다(7절 질문 ③).

**실행 보고서**(`report.md`): 판마다 확정 / 질문 / 영향 0 숨김 / 기록 불확실 칸 수, 다시 읽기 횟수, 하위 에이전트 수 · 토큰, 걸린 시간, 끊긴 적이 있으면 그 시각. 끝에 "정답 없음 — 읽기끼리의 일치와 앞뒤 검사" 를 적는다.

## 6. 평가 — 만들고 나서 어떻게 재나

**재료 문제:** 헤드 녹화가 있는 반장은 11-14 의 셋뿐이다. 1반장은 연출용이라 패보 정답에서 뺐고(기억 `visit-1114-hanchan1-staged`), 2 · 3반장은 이미 본 판이다. **안 본 반장이 없다.**

그래서 두 번에 나눠 잰다.

1. **재현 시험(본 판, 통과 판정 아님):** 2반장 · 3반장을 처음부터 무인으로 다시 돌린다.
   - 끝까지 사람 개입 0 으로 도는가(끊김 → 재개는 허용, 그 횟수를 적음)
   - 사람 정답이 있는 차례(2반장의 확인 정답 · 3반장 사용자 확인 여섯)에서 틀림 수가 손으로 했을 때보다 늘지 않는가
   - 반장당 질문 수 · 토큰 · 시간
   - 확인 꾸러미가 11-23 에 사람이 고른 여섯 차례를 포함하는가(영향 0 인 n06 6순은 빠져야 맞음)
2. **안 본 반장(통과 판정):** 다음 매장 방문 녹화 한 반장. 기준은 측정 전에 적는다.
   - 조용한 틀림(질문에 안 올랐는데 틀린 차례): 사용자가 영상으로 표본 확인 — **0** 이어야 통과
   - 질문 ≤ 10 / 반장
   - 사람 개입 0(확인 페이지 말고는)
   - 조용한 틀림을 재려면 질문에 안 오른 차례 중 일부(예: 판마다 2차례 무작위)를 사용자가 따로 확인해야 한다. 그 수는 7절 질문 ②.

측정을 하면 metrics.md 에 표를 하나 새로 만들고(앱 흐름 · 자리 판독과 조건이 다름) problem_log 에 항목을 연다(CLAUDE.md 규칙).

1단계는 LLM 을 부르지 않는다. 이미 있는 3반장 답 파일을 꾸러미 자리에 넣어 흐름만 시험한다. 돈과 토큰은 3단계부터 든다.

**비용:** 3반장 손 작업은 약 1,500만 토큰이었다(하위 에이전트). 무인 흐름은 S4 결과 읽기를 둘로 나눠 읽고 S7 에서 다시 읽기가 더해지므로 더 많을 수 있다. 반장 하나에 5시간 한도를 한 번 넘길 수 있다고 보고 시작 전에 사용자에게 물량을 알린다.

## 8-2. 질문 고르기 보강 (11-24, 사용자 "그렇게 보강")

1단계에서 질문은 답의 `unsure` 한 칸으로만 골랐다. 그래서 11-23 사람이 고른 n04_d09 · n05_d09 가 빠졌다. 신호를 둘 더한다. **규칙은 3반장 결과를 보기 전에 여기 적은 그대로 고정한다.** 3반장은 이 규칙을 만들 때 본 판이므로, 결과는 "본 판에서 몇 개를 잡나" 일 뿐 통과 판정이 아니다.

**신호 1 — 확신 말(코드, 토큰 0).** 차례 답의 글 칸(`why` · `events_used` · 그 밖 문자열 칸 모두)에서 아래 중 하나라도 나오면 질문으로 올린다. 질문 줄의 `signal` 에 `hedge:<걸린 말>` 을 적는다.
- 숫자 확신: `확신`, `확률`, `%` 앞뒤 20자 안의 숫자가 90 미만
- 짐작 말: `아마`, `추정`, `짐작`, `보인다`, `보임`, `듯`, `것 같`, `가능성`, `애매`, `불확실`, `확실하지`, `확실치`, `단정`, `어렵`, `못 봤`, `안 보`, `가려`, `또는`, `혹은`, `아니면`
- 다른 답 말: `다른 후보`, `대안`, `둘 중`
- 부정으로 지우는 꼴(예: "가려지지 않아 확실")은 따로 거르지 않는다. 헛 경보는 개수로 보고한다.

**신호 2 — 영향 큰 차례 표본(코드, 토큰 0).** 질문에 안 오른 차례 모두에 영향을 계산한다. 후보는 1단계 규칙 그대로다(답에 적힌 다른 후보, 없으면 `k` · `j` ±1). 그중 가장 큰 "바뀌는 순 수" 로 줄을 세워 **판마다 위에서 2차례**를 표본으로 올린다(`signal: sample:impact`, 같으면 순이 이른 차례). 표본은 질문 수와 따로 센다. 6절의 "판마다 2차례 표본" 을 이것으로 바꾼다. 무작위가 아니므로, 4단계에서 조용한 틀림 비율을 잴 때는 무작위 표본을 따로 둔다.

**보고할 것(3반장, 사용자 확인 전 답 = `…_before_user` 실행)**
- 신호별 질문 수: `unsure` · `hedge` · 둘 다. 차례 97 중 몇 개가 올랐나, 표본 수.
- 11-23 사람이 고른 여섯 차례가 각각 어느 신호로 잡혔나 / 안 잡혔나. n05_d09 처럼 안 잡히면 그대로 적는다 — 규칙을 그 차례에 맞춰 고치지 않는다.
- `hedge` 로 오른 것 중 11-23 사람이 안 고른 것의 목록과 걸린 말. 헛 경보 후보다.
- 질문 + 표본 합이 한 반장에 몇 개인지. 사용자가 실제로 볼 양이다.

## 8-5. 앱 기록 우선 — 확인 결과와 구현 명세 (11-24 오후, 사용자 "처음에 녹화영상만 에이전트 넘기는건 아니지?" — 구현 전 · 사용자 확인 대기)

**8-4 의 확인 셋 — 결과:**
- **시계:** 다른 시계다. 앱 시각은 태블릿, 녹화 `f_<epoch ms>` 는 헤드 폰이다. 11-14 에 잰 차이는 −0.88 / −0.33초(HANDOFF 11-15 절 `pair`). 더 큰 어긋남은 따로 있다:
  - 화료 폴더 시각 · `meta.json` 의 `time` 은 찍은 때가 아니라 저장한 때다(대개 6 ~ 18초, 최대 43초 뒤).
  - 버림 사건 `at` 은 겹쳐 보기가 끝난 때다(3초 미리보기 간격 + 판독 시간만큼 늦음).
  - → 앱 시각은 "여기 근처" 를 가리키는 닻으로만 쓰고, 정확한 시각은 영상에서 맞춘다.
- **PC 로 옮기는 길:** 이미 있다. 촬영 기록 저장이 켜져 있으면 `paifu.json` 이 태블릿 `Download/mahjong_calc/<시각>/`(유국은 `<시각>_draw/`)에 같이 남고, `supervise.py pull` 이 `experiments/visit_<날짜>/captures/` 로 가져온다. `PaifuStore`(SharedPreferences)를 꺼낼 필요가 없다.
  - 단, `paifu.json` 은 "판 중 버림 기록" 을 켰을 때만 남는다(기본 끔 — 발열 · 배터리).
  - 촬영 기록 사본은 `'frames': 장수` 가 녹화 정보(`PaifuFrames` — 폴더 · 자리 구역)를 덮는다. 앱을 고칠지는 따로 정한다(아래 "앱 고침").
- **2반장(11-14):** `paifu.json` 이 **없다**(저장 기능은 11-17 뒤에 생김). 있는 것은:
  - 화료 폴더 `label.json` — "대국에 반영" 때 확정한 값(화료자 · 방총자 · 끝 손패 · 화료패 · 울기 · 도라 · 뒷도라 · 리치 자리)
  - 유국 폴더 `chosen.json`(텐파이 자리) · `reveal.json`(국 · 본장 · 공개한 자리)
  - `meta.json` 의 국 · 본장 · 선 · 아래 자리
  - `_track/frames_##.zip`(3초 프레임 전부) — 11-17 에 기록기로 재생한 `results/h1x_*/paifu_rec.json` 이 앱 버림 기록의 대역이다(처음 보는 9판 421/421, 표 12-29).

**그래서 앱 기록을 두 층으로 받는다:**

| 층 | 있는 때 | 앱에서 오는 것 | 영상에서 읽는 것 |
|---|---|---|---|
| A `paifu.json` | 촬영 기록 + 판 중 버림 기록 켬 | 강 · 울기 · 리치 · 판 결과 전부 | 손패 주인의 매 순 손패, 버림 맞춰 보기 |
| B `label.json` · `chosen.json` | 촬영 기록만 켬(2반장이 이 층) | 판 결과(화료 전부 · 유국은 텐파이 자리), 판 목록 · 국 · 본장 · 선 | 강 · 울기 · 리치(지금 흐름), 매 순 손패 |
| 없음 | 3반장, 도중 유국 | — | 지금 흐름 그대로 |

**단계별로 넘기는 것:**
- **새 입력 단계(S0 안):** `app_record.py`(새 파일)가 촬영 기록 폴더에서 이 반장 구간의 판을 모아 `app_rounds.json` 을 쓴다. 판마다 층 · 국 · 본장 · 선 · 아래 자리 · 닻 시각 · 결과 · (층 A 면) 사건. 반장 설정에 `app_record: {captures, from, to}` 칸을 더한다.
- **S1 판 경계:** 판 수 · 순서 · 국 이름은 앱에서 온다(LLM 이 세지 않음). 꾸러미는 "세 시간 녹화에서 판을 찾아라" 가 아니라 "판마다 닻 시각 − 60초 ~ + 3초 창에서 공개 시각을, 앞 판 끝 ~ 이 판 닻 사이에서 시작 시각을 맞춰라" 로 줄인다. 층 A 는 첫 버림 `at` 이 시작 닻이 된다.
- **S3 버림 기록:** 층 A 면 앱 사건이 1차, 영상 기록기는 맞춰 보기다. 다른 칸만 `record` 질문으로 올린다. 시계 차이는 맞은 버림들의 (앱 `at` − 영상 첫 봄) 중앙값으로 재서 보고서에 적고, 퍼짐이 크면 질문에 올린다. 층 B 는 지금처럼 영상 기록기다.
- **S4 판 결과:** 화료 판은 앱 결과를 쓰고 읽기 꾸러미를 내지 않는다(판마다 하위 에이전트 둘이 빠짐, 뒷도라 · 해저 질문도 빠짐). 유국 판은 텐파이 자리를 꾸러미에 적어 주고 공개 손패만 읽게 한다.
- **S5 대조:** 앱 결과의 끝 손패 · 울기 ↔ 영상 기록기 강 · 공개 프레임. 어긋나면 질문에 올린다(앱 값을 채운 채로).
- **S6 · S7:** 그대로다. 사건 목록만 위에서 확정한 기록으로 바뀐다.

**끝 조건(LLM 0):**
1. 앱 기록이 없는 3반장 두 실행 폴더의 패보 14/14 가 지금과 바이트 같다.
2. `app_record.py` 가 2반장 촬영 기록에서 낸 판 결과가 `assets/paifu/r11 ~ r20` 의 `result` 와 같다. 닻 시각이 `v1114rec` `rounds.json` 의 공개 시각과 창 안에서 맞는다.
3. 새 설정 `hanchan/h2_1114.json` 으로 `init` → `next` 하면 화료 판의 S4 꾸러미가 0 이고 유국 판만 남는다. S1 꾸러미에 판 목록과 창이 들어 있다.
4. 층 A 는 대역(`results/h1x_*/paifu_rec.json`)으로 꼴만 시험한다. 진짜 층 A 시험은 다음 매장 녹화다.

**앱 고침(따로 정함):** 촬영 기록 `paifu.json` 사본에서 장수를 `frame_count` 로 옮겨 `frames`(녹화 폴더 · 네 자리 구역)가 살아남게 한다. `mount_screen.dart` 한 곳이다. 다음 매장 방문 전에 하면 자리 띠를 사람이 정하지 않아도 된다.

## 8-6. 원래 방식대로 짠 흐름 (11-24 오후, 사용자 "우리가 원래 패보 만들었던 방식대로 워크플로우 짜봐" → "네, 진행" — W1 ~ W5 구현 맡김)

8-5 의 "두 층" 표를 이 절이 대신한다. 본은 3반장 복구(영상에서 전부 다시 읽기)가 아니라 **2반장 예시를 만든 순서**(`paifu_examples.py` 머리말 · HANDOFF "2026-11-20 오후" 절)다.

**끝 조건:** 8-5 의 넷 그대로. W2 ② 는 2반장으로 진짜 시험이 된다(`results/h1x_*/paifu_rec.json` 이 이미 그 출력).

## 8-7. 나중에 API 실행기로 바꿀 때의 읽기 도구 (11-24 오후, 사용자 "그걸로 하자" — 결정만, 구현 · 측정 안 함)

지금은 세션이 하위 에이전트를 띄운다(Claude API 금지). 꾸러미(`pending.json`) · 답 파일 형식을 그대로 두면 나중에 "세션이 띄운다" 만 "실행기가 API 로 에이전트 고리를 돈다" 로 바꾸면 된다. 그때 읽기 에이전트에게 줄 도구는 **고정 도구를 기본으로, 코드 실행은 비상구로** 한다. 근거는 지난 읽기 기록 198개를 센 것(metrics 표 12-123).

| 도구 | 하는 일 | 근거 |
|---|---|---|
| `strip` | 같은 영역을 프레임 구간(시작 · 끝 · 걸음)에서 잘라 프레임 번호를 붙여 격자로. 배율 · 열 수 선택 | 차례 읽기 180개가 모두 스스로 짬(sheet). `claudeagent.py` 에 이미 있음 — 배율 · 열 수 · 번호가 붙는지 확인할 것 |
| `zoom` | **고른 프레임 여러 장**을 같은 영역으로 잘라 **고른 배율**로 키워 쌓기, 가로 눈금 | 지금 고정 도구는 한 프레임 · 3배 고정. 에이전트는 4 ~ 12프레임 · 1.4 ~ 2.6배로 씀 |
| `view` | 프레임 여러 장을 그대로 | 있음. 원본을 그대로 여는 것은 에이전트당 1번꼴 |
| `look` | 시각을 골라 한 자리(또는 영역)를 잘라 **돌려** 키우기 | 판 결과 · 유국 공개 손패 읽기에서 실행의 89 ~ 91%. 고정 도구에 없음 |
| `run_python` | 비상구 — 꾸러미 폴더 안에서만 도는 코드 실행, 만든 그림을 결과로 바로 돌려줌 | 차이 그림 · 밝기 조절은 4/180. 미리 도구로 만들 값은 아님 |
| `answer` | 답을 내고 끝 | 있음 |

- 한 번에 여러 장을 청하는 일이 실행의 35% 다. 실행기는 한 호출 안의 도구 여러 개를 받아야 한다.
- 도구는 그림을 **결과로 바로** 돌려줘야 한다. 지금 하위 에이전트는 만든 그림을 따로 Read 로 여는데 이 호출이 전체의 43% 다. 코드를 쓰는 값 자체는 전체의 약 1% 다.
- 재지 않은 것: 고정 도구만으로 정확도가 유지되는지(API 고정 도구 16/17 대 하위 에이전트 17/17 은 한 차례 차이라 까닭을 모름). API 를 다시 쓸 수 있을 때 재거나, 하위 에이전트를 "이 명령만 써라" 로 묶어 잰다(읽기 토큰이 드니 사용자에게 먼저 묻기).

8-8 의 준비 읽기는 값을 한 번 적고 끝이라 3반장 차례 목록 7/11 에 그쳤다(표 12-125). 11-23 에 손 설정을 만들 때는 값을 넣고 판별을 돌려 보고 결과를 보며 고쳤다(손 설정 메모에 band 를 세 번 옮긴 흔적 등). 그 고리를 뺀 것이 세션의 설계 잘못이다. 고리를 돌려준다.

**바뀌는 것 — 에이전트가 쓰는 도구 하나(`try`):**

| 걸음 | 누가 | 하는 일 |
|---|---|---|
| 값 정하기 | 준비 에이전트(판당 하나, Opus 높음) | 8-8 과 같은 꾸러미로 영역 · t_ready · 공개를 정해 초안 답을 씀 |

| 결과 보기 | 에이전트 | 보고서: ① 차례 목록(번호 · 버린 패 · 리치 · 창 시작 ~ 끝) ↔ 기록의 손패 주인 버림(어느 버림이 t_ready 앞 · 빠짐 · 남음) ② 활동 구간 수 · 길이(판 전체가 한 덩어리로 붙었는지) · 가만한 프레임의 피부 비율 ③ 공개 프레임에서 읽은 끝 손패 장수 · 떼어 둔 패 ↔ 기대 장수(판 결과가 손패를 알면 같은지) ④ 적용 검사. 첫 두세 차례 창을 프레임으로 열어 정리 동작이 섞였는지 본다 |
| 고치기 | 에이전트 | 이상하면 값을 고쳐 다시 `try`. 시도는 판당 5번까지 |
| 답 | 에이전트 | 마지막 값 + 시도 기록(무엇을 보고 무엇을 고쳤나) |

- `try` 는 판별 흐름 자체라 그 안에서 검출기 · 분류기가 돈다. 에이전트에게 허용되는 모델 호출은 이것뿐이다. 그 밖의 금지(폴더 밖 · 손 설정 · 정답 · 옛 차례 목록 열기)는 8-8 그대로다.
