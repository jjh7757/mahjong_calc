# 대국 뒤 자동 패보 에이전트 — 설계서 (2026-11-24)

사용자: "대국 끝나고 자동으로 패보 만들어주는 에이전트 어떻게 생각하니" → "사용자에게 묻는건 나머지 할거 다하고 따로 확인이 필요한 부분만 묻는걸로 설계 시작해".

**한 줄:** 11-23 에 사람(세션)이 손으로 이어 붙였던 "헤드 녹화 → 한 반장 패보" 흐름(HANDOFF "2026-11-23 아침" 절 · metrics 표 12-115 · 12-116 · problem_log 77)을 **한 번 시작하면 끝까지 사람 없이 도는 흐름**으로 묶는다. 도는 동안에는 아무것도 묻지 않는다. 확신이 없는 곳은 가장 그럴듯한 답으로 채우고 "확인 필요" 표시를 붙인 채 계속 간다. 끝나면 **확인이 필요한 것만 모아 한 페이지(영상 + 고르기)로 한 번** 묻고, 답이 오면 자동으로 다시 조립한다.

이 설계서에는 코드와 측정이 없다. 구현은 Opus 5.5 높음 하위 에이전트에 맡기고, 이 세션이 검토한다(기억 `feedback-stepwise-delegation`).

## 2. 범위

**한다**
- 입력: 헤드 녹화 폴더 하나(`f_<epoch ms>.jpg`, 1496², 초당 약 10장) + 날짜. 앱 대국 기록이 있으면 같이 받는다(선택).
- 출력: 반장의 판마다 패보 JSON(지금 형식 — 네 자리 버림 · 울기 · 리치 · 결과 · 손패 주인의 매 순 손패 · 국 시작 점수) + **확인 꾸러미**(아래 5절) + 실행 보고서.
- 시작 방식: PC 에서 명령 하나. 대국이 끝난 뒤 녹화를 PC 로 옮겨 놓고 시작한다.

**하지 않는다**
- 앱 · 서버에 넣지 않는다. 앱의 "손패 복원 (Claude API)" 버튼(11-21, 실제 호출 0)은 건드리지 않는다.
- Claude API 를 부르지 않는다(기억 `no-claude-api-credits`). 읽기는 Claude Code 하위 에이전트로 한다.
- 매장 실시간은 하지 않는다. 대국 뒤 몇 시간 안에 결과를 받는 것이 목표다.
- 점봉 이동은 하지 않는다(11-23 에도 못 읽음). 남의 쯔모기리 채우기(B4)는 2단계 이후에 붙일지 따로 정한다.

### 3-2. 길 — 기본 길 하나와 옆길 둘

- **기본 길:** 앱 기록 `paifu.json` 이 있는 판(촬영 기록 저장 + 판 중 버림 기록을 켠 대국). 버림 · 울기 · 리치 · 판 결과가 앱에서 온다. 에이전트가 하는 일은 묶음 3(준비) · 묶음 4(차례 읽기)와 유국 판의 공개 손패 읽기뿐이다.
- **옆길 가(`paifu.json` 없음 · `label.json` 과 추적 프레임만):** 11-14 2반장이 이 길이다. 버림은 추적 프레임 zip 을 앱 기록기로 재생해 얻고, 나머지는 기본 길과 같다.
- **옆길 나(복구 — 앱 기록 없음):** 11-14 3반장 · 도중 유국 판. 판 경계와 판 결과를 에이전트가 영상에서 읽고(S1 · S4, 결과는 둘이 따로), 버림은 헤드 녹화 재생으로 얻는다.
- 길은 판마다 정해진다(예: 기본 길 반장 안의 도중 유국 판만 복구 길). 반장 설정에 `app_record` 칸이 있을 때만 앱 길을 탄다 — 코드는 이미 그렇다.
- **기본 길의 전제 · 구멍:**
  - 판 중 버림 기록은 앱 기본이 꺼져 있다(발열 · 배터리). 매장에서 켜야 기본 길이 된다.
  - 기본 길은 꼴 시험만 했다(대역 `results/h1x_*/paifu_rec.json`). 진짜 시험은 다음 매장 녹화다.
  - 촬영 기록 `paifu.json` 사본에서 장수가 녹화 정보(`frames`)를 덮는 앱 고침(8-5 "앱 고침")이 방문 전에 필요하다. → 3-7 에서 바뀜: 앱 자리 구역은 쓰지 않기로 해(쪽만 받음) 이 고침은 전제가 아니다.

### 3-3. 누가 무엇을 정하나

- **코드(`paifu_auto.py`):** 반장 안의 묶음 순서, 꾸러미 실행 · 병렬, 재개, **검사 문**(무엇이 통과인지), 영향 계산. 단계마다 결과 파일을 남기고 그 파일이 있으면 건너뛴다(끊겨도 같은 명령으로 이어 감). 묶음 1 · 2 · 5 에서는 무엇을 확정하고 질문에 올릴지도 코드가 정한다.
- **판 supervisor(3-5):** 묶음 3 ~ 4 에서 작업자 결과와 검사 보고서를 보고 다음 행동을 고른다. 고른 결과는 코드 검사 문을 통과해야 받아들여진다.
- **작업자 에이전트:** 눈으로 봐야 하는 것만. 꾸러미 폴더 안에서 읽고 정해진 꼴의 답 파일 하나를 쓴다. **한 번 답하고 끝내는 꼴로 줄이지 않는다 — 결과를 스스로 돌려 보고 고칠 도구를 준다**(묶음 3 의 `try`, 8-9. 11-24 사용자 지적).
- **세션:** `next` 가 낸 꾸러미 수만큼 하위 에이전트를 띄우고 기다린다(4절 (가)). 판단하지 않는다.
- **사용자:** 끝에 한 번(5절). 도는 동안에는 묻지 않는다.

### 3-4. 11-25 에 정한 것(사용자 "네, 그대로" — 세션 권장안 넷)

1. **기본 길은 앱 기록이 있는 판이다.** 없는 판은 옆길로 둔다(3-2).
2. **묶음 4 는 차례당 에이전트를 유지한다.** 다시 읽기 꾸러미에는 "어느 검사에 어떻게 걸렸는지" 를 넣는다(구현 전). 판 단위 에이전트 하나에 검사 도구까지 주는 안은 하지 않는다 — 차례당 약 15만 토큰 어림(반장 약 1,500만 ÷ 차례 약 100, 재지 않음 — 3-10 에서 고침: 3반장 기록은 차례 읽기 115개 약 1,200만 · 차례당 8 ~ 19만, 표 12-116)이라 한 에이전트에 담기지 않는다. 어긋난 내용을 알려 주면 앞 답에 끌려갈 수 있다 — 3단계 재현 시험에서 본다. 앞 답 자체를 보여 줄지는 묶음 4 세부에서 정한다. **→ 같은 날 이어서 고침: 다시 읽을지 · 무엇을 주의시킬지는 코드 규칙이 아니라 판 supervisor 가 고른다(3-5). 차례당 작업자 에이전트는 그대로다.**
3. **쉬움 거르기(W7)는 묶음 4 맨 앞에 자리만 두고 기본은 끈다.** 넣을지는 3단계 재현 시험에서 나란히 재고 정한다.
4. **손패 주인은 화료자 1명이다(유국은 텐파이 공개자 1명).** 텐파이가 둘인 유국(w16)은 한 명만 만들고 질문에 올린다(→ 3-8 에서 고침: 질문이 아니라 보고서의 "못 한 것"). 누구를 고를지 · 조립(S8)이 멈추는지는 묶음 3 · 5 세부에서 정한다.

### 3-5. 판 supervisor (11-25, 사용자 "위에 에이전트를 총괄하는 관리자 에이전트 하나 있는게 좋지 않니" → "supervisor패턴이 좋지 않니" → "네, 판 단위로" — 설계만, 구현 · 측정 없음)

**왜:** 11-23 3반장 복구가 됐을 때는 세션이 판마다 이 역할을 했다 — 읽기가 이상하면 준비 값을 고치고, 기록기와 엇갈리면 프레임을 보고 `recorder_fix.json` 을 썼다. 뒤 단계 결과를 보고 앞 단계로 되돌아가는 길이 있었다. 자동화하면서 그 판단을 코드 규칙으로 바꿨고, 규칙이 못 정하는 곳은 모두 사용자 질문이 된다(볼 양 31 ~ 40). 지금 코드에는 되돌아가는 길이 없다 — w17 은 준비가 줄이 선 때를 이르게 잡았는데(표 12-126) 그것을 준비로 돌려보낼 주체가 없다. 11-24 의 "돌려 보고 고치는 고리를 뺐다"(8-9)와 같은 꼴의 구멍이 판 수준에도 있다.

| `reprep` | 준비를 다시(줄이 선 때 · 영역) + 까닭 | 준비 에이전트 → 판별 · 차례 나누기부터 다시 |
| `fix_record` | 탁자 기록 고침 제안(칸 · 근거 프레임) | 차례 규칙 엮기 검사를 통과할 때만 적용하고 `recorder_fix.json` 에 이유를 적음 |
| `look` | 문제 차례의 프레임을 직접 열어 봄 | 꾸러미 안 프레임 도구(8-7 의 `strip` · `zoom` · `look`) |
| `set` | 프레임을 보고 그 차례 답을 직접 정함(3-10 에서 더함) — 근거 프레임 시각 필수 | 검사 다시. 표시해 사용자 표본 확인에 먼저 넣음 |
| `accept` | 이 판 확정 | 검사 문 통과를 확인하고 묶음 5 로 |
| `ask` | 사용자 질문으로 올림(후보 · 근거 구간) | 질문 목록에 한 줄, 최선 답으로 채움 |

**지킬 것:**
- **검사 문은 코드에 있다.** supervisor 가 `accept` 해도 코드 검사를 통과하지 못하면 질문으로 올라간다. supervisor 의 "해결" 은 정답이 아니다(같은 모델의 판정).
- supervisor 가 손댄 것(다시 읽혀 답이 바뀐 차례 · 기록 고침 · 준비 다시)은 표시해 사용자 표본 확인에 먼저 넣는다. 질문은 줄고 조용한 틀림이 느는 쪽으로 가는지 보기 위해서다.
- 결정 기록을 라운드마다 파일에 남긴다(본 것 · 고른 행동 · 까닭). 끊기면 새 supervisor 가 그 파일로 이어 가고, 재생(LLM 0)도 그 파일로 한다.
- 금지는 작업자와 같다 — 꾸러미 폴더 밖 · 정답 · 옛 손 설정 · 다른 판을 열지 않는다.
- 11-17 의 "LLM 은 동작만, 코드가 굴림" 은 반장 수준과 검사 문에 그대로 남는다. 판 안에서 "다음에 무엇을 할지" 만 supervisor 로 옮긴다. 3-6 표의 S7 "어긋나면 그 구간만 다시 읽음(한 판 2회까지)" 과 표 아래 "LLM 이 판단하지 않는 것" 문단은 묶음 3 ~ 4 에 한해 이 절이 대신한다.

**띄우는 방식(둘 중 하나 — 아래 "확인" 줄):**
- (가) supervisor 하위 에이전트가 작업자를 직접 띄운다.
- (나) supervisor 가 "다음 행동" 을 파일에 쓰고 멈춘다 → 코드(`next`)가 꾸러미로 바꾸고 세션이 작업자를 돌린다 → 세션이 같은 supervisor 를 이어 부른다(SendMessage). 지금의 꾸러미 구조에 그대로 맞고, 나중에 API 실행기(8-7)로 옮기면 supervisor 그래프 꼴이 된다.
- **확인(11-25, 탐침 한 번):** 하위 에이전트(general-purpose · Haiku)에게 "하위 에이전트를 하나 띄워 정해 준 글자를 돌려받아라" 를 시켰더니 됐다 — 도구 목록에 `Agent` 가 있고 `SendMessage` 도 있다고 보고했다. 그래서 (가)도 (나)도 길은 있다. 안 본 것: Opus 높음에서 같은지(도구 목록은 에이전트 종류가 정하므로 같을 것으로 봄 — 추정), 하위 에이전트 안에서 여럿을 나란히 띄울 때의 한도, 두 겹 아래의 읽기 기록을 감사(`subagents/*.jsonl`)에서 찾을 수 있는지. 탐침 하나가 약 7.4만 토큰이었다 — 에이전트 하나를 띄우는 밑값이 작지 않다는 뜻이라 supervisor 라운드 수를 정할 때 본다.
- **어느 쪽으로 할지는 아직 안 정함.** 세션 생각: (가)는 supervisor 가 한 번 도는 동안 고리를 스스로 끝까지 돌 수 있어 8-9 의 교훈과 맞다. 다만 꾸러미 만들기 · 검사는 supervisor 가 `paifu_auto.py` 명령으로 부르게 해 코드 문을 지나게 해야 하고, 감사 · 끊김 뒤 재개가 되는지 먼저 봐야 한다.

**버린 안:**
- 반장 전체 supervisor — 묶음 1 · 2 · 5 는 순서가 정해진 코드라 고를 것이 없다. 몇 시간짜리 맥락을 들고 가야 하고 한도로 끊기면 이어 가기 어렵다.
- 차례 읽기 뒤 조정만 하는 좁은 안 — 되돌아갈 곳이 차례 읽기뿐이라 준비 · 기록이 틀린 경우를 못 고친다.

**아직 안 정한 것(묶음 3 · 4 세부에서):** 판당 라운드 한도, `reprep` 횟수, 검사에 안 걸린 판에도 supervisor 를 띄울지, supervisor 가 받는 답 요약의 꼴, 다시 읽기 작업자에게 앞 답을 보여 줄지. → 3-9 · 3-10 에서 정함(모든 판에 띄움 · 라운드 3 · `reprep` 1회 · 앞 답은 안 보여 줌).

**모르는 것(3단계 재현 시험에서 잼):** 질문 수가 실제로 주는지, 조용한 틀림이 느는지, 판당 토큰.

## 4. 하위 에이전트를 어떻게 띄우나

Python 은 Claude Code 하위 에이전트를 직접 부를 수 없다. 두 방식이 있다.

- **(가) 세션이 지휘(권장, 11-23 과 같은 방식):** 이 세션이 `paifu_auto.py next` 를 부른다. 스크립트는 "다음에 읽을 꾸러미 목록"(폴더 + TASK.md)을 내놓고, 세션은 그 수만큼 하위 에이전트(Opus · effort high)를 병렬로 띄운다. 끝나면 다시 `next` 를 부른다. 목록이 비면 끝이다. 세션이 하는 일은 띄우고 기다리는 것뿐이다. 판단은 스크립트가 한다. 이 순서를 스킬 하나(`/paifu-auto <녹화 폴더>`)로 적어 두면 새 세션도 같은 순서로 돈다.
- **(나) 스크립트가 `claude -p` 를 직접 부름:** 완전 무인이 되지만 Claude Code 를 새 방식으로 쓰는 일이라 사용자 허락이 필요하다(기억: 새로 쓰려면 먼저 묻기). 7절 질문 ①.

(가)로 만들고, 꾸러미 꼴이 같아서 나중에 (나)로 바꾸기 쉽다.

병렬 수: 한 번에 8개. 한도에 걸리면 `state.json` 에 남은 꾸러미가 그대로 있으니 다시 시작하면 된다.

## 8-1. 1단계 명세 (11-24, 사용자 "1단계 진행")

**명령**(`experiments/paifu_frames/paifu_auto.py`)
- `init --hanchan <json> --run <실행 폴더>`: `state.json` 을 만든다. 실행 폴더 기본값은 `results/auto_<설정 id>/`.

- `replay --run … --from <3반장 자리>`: 재생 읽기다. `pending.json` 의 꾸러미에 이미 있는 답을 넣는다.
  - S1 판 경계: `results/han3_1123/rounds_p.json`
  - S4 판 결과: 판마다 `result_read.json` — 읽기 a · b 둘 다 같은 답이 된다.
  - S6 손패 차례: `_work/rawread_han3_1123/<id>/answer.json`
  - 답이 없는 꾸러미는 비워 두고 보고한다. `next` → `replay` 를 번갈아 돌리면 끝까지 간다.
- `apply --run … --answers <파일>`: 사용자 답을 넣고 S7 → S8 → S9 를 다시 돈다. 1단계에서는 11-23 `review/answers_user.json` · `review2/answers_user.json` 의 **사본**으로 시험한다.

## 8-2. 질문 고르기 보강 (11-24, 사용자 "그렇게 보강")

1단계에서 질문은 답의 `unsure` 한 칸으로만 골랐다. 그래서 11-23 사람이 고른 n04_d09 · n05_d09 가 빠졌다. 신호를 둘 더한다. **규칙은 3반장 결과를 보기 전에 여기 적은 그대로 고정한다.** 3반장은 이 규칙을 만들 때 본 판이므로, 결과는 "본 판에서 몇 개를 잡나" 일 뿐 통과 판정이 아니다.

**신호 1 — 확신 말(코드, 토큰 0).** 차례 답의 글 칸(`why` · `events_used` · 그 밖 문자열 칸 모두)에서 아래 중 하나라도 나오면 질문으로 올린다. 질문 줄의 `signal` 에 `hedge:<걸린 말>` 을 적는다.
- 숫자 확신: `확신`, `확률`, `%` 앞뒤 20자 안의 숫자가 90 미만
- 짐작 말: `아마`, `추정`, `짐작`, `보인다`, `보임`, `듯`, `것 같`, `가능성`, `애매`, `불확실`, `확실하지`, `확실치`, `단정`, `어렵`, `못 봤`, `안 보`, `가려`, `또는`, `혹은`, `아니면`
- 다른 답 말: `다른 후보`, `대안`, `둘 중`
- 부정으로 지우는 꼴(예: "가려지지 않아 확실")은 따로 거르지 않는다. 헛 경보는 개수로 보고한다.

**신호 2 — 영향 큰 차례 표본(코드, 토큰 0).** 질문에 안 오른 차례 모두에 영향을 계산한다. 후보는 1단계 규칙 그대로다(답에 적힌 다른 후보, 없으면 `k` · `j` ±1). 그중 가장 큰 "바뀌는 순 수" 로 줄을 세워 **판마다 위에서 2차례**를 표본으로 올린다(`signal: sample:impact`, 같으면 순이 이른 차례). 표본은 질문 수와 따로 센다. 6절의 "판마다 2차례 표본" 을 이것으로 바꾼다. 무작위가 아니므로, 4단계에서 조용한 틀림 비율을 잴 때는 무작위 표본을 따로 둔다.

**보고할 것(3반장, 사용자 확인 전 답 = `…_before_user` 실행)**
- 신호별 질문 수: `unsure` · `hedge` · 둘 다. 차례 97 중 몇 개가 올랐나, 표본 수.
- 11-23 사람이 고른 여섯 차례가 각각 어느 신호로 잡혔나 / 안 잡혔나. n05_d09 처럼 안 잡히면 그대로 적는다 — 규칙을 그 차례에 맞춰 고치지 않는다.
- `hedge` 로 오른 것 중 11-23 사람이 안 고른 것의 목록과 걸린 말. 헛 경보 후보다.
- 질문 + 표본 합이 한 반장에 몇 개인지. 사용자가 실제로 볼 양이다.

## 8-3. 질문 고르기 v2 (11-24, 사용자 "v2로 다시")

8-2(v1)를 3반장에 적용했더니 볼 양이 65 였다. 헛 경보 대부분은 묘사 말이었다(진행 절). v2 는 **3반장 결과를 보고 고친 규칙**이다. 그래서 3반장 숫자는 통과 판정이 아니고, 판정은 4단계 안 본 반장에서 한다. 아래는 적용 전에 고정한다.

- **신호 1 말 목록:** v1 에서 `보인다` · `보임` · `듯` 셋만 뺀다. 나머지 짐작 말 · 다른 답 말은 그대로 둔다(`안 보` · `가려` 포함 — n05_d09 에 맞춰 남기는 것이 아니라 v1 에서 손대지 않은 것).
- **숫자 확신:** v1 의 "앞뒤 20자 안 숫자 < 90" 을 버리고, 아래 둘 중 하나일 때만 건다.
  - (a) `확신` 의 뒤 10자 안에 `낮` · `중간` · `약하` · `없` 이 있다.
  - (b) 글 어디든 `숫자 %`(숫자와 % 사이 빈칸 0 ~ 1개)가 있고, 그 숫자가 90 미만이다.
- **신호 2 표본:** 바뀌는 순 수가 **0 인 차례는 표본에서 뺀다**. 판마다 많아야 2. 나머지는 v1 그대로다.
- 판 결과 · 기록 질문 규칙은 그대로다.

**보고할 것:** 8-2 의 보고 항목을 v2 로 다시 낸다. 숫자마다 v1 과 나란히 놓는다.

## 8-4. 앱 기록 우선 (11-24 사용자 지적 — 설계만, 구현 전 · 사용자 확인 필요)

사용자: "녹화영상만 넣는건 아니지? 울기 감지, 리치감지, 강에 있는 패들, 최종 화료패 같은 정보도 넣지?" → "유국 저장하는걸로 바꿨을 텐데?". 지금 흐름은 앱 기록이 없던 3반장을 본으로 만들어, 앱 기록을 판 경계에만 쓰고 나머지를 영상에서 다시 뽑는다. 앱 기록이 있으면 그것이 1차 입력이어야 한다.

**앱이 남기는 것(코드 확인 11-24):**
- **화료** — `mount_screen.dart` `_savePaifu`:
  - 판 중 버림 기록기 사건: 네 자리 강 · 울기 · 리치(눕힌 패)
  - `result`: 화료자 · 방총자 · 화료패 · 끝 손패 · 울기 묶음 · `flags`(해저 등)
  - 도라 · 뒷도라 표시패, 국 시작 점수
  - 헤드 녹화를 받아 저장 중이면 `frames`(폴더 · 화료자 자리 구역)
- **보통 유국** — `lib/paifu/draw_paifu.dart`, 커밋 `6adc46a`(11-24):
  - 버림 사건 · 텐파이 자리 · 판 중 확정한 도라 표시패
  - 손패 · 뒷도라는 없다.
  - 도중 유국 · 트리플론은 저장하지 않는다.

**바뀌는 흐름(앱 기록이 있는 판):**
- **S1 판 경계:** 앱 기록 시각을 쓴다. 3절에 이미 있다.
- **S3 버림 기록:** 앱 사건을 그대로 쓴다. 영상 재생 기록기는 **맞춰 보기용**이고, 둘이 다른 칸만 `record` 질문으로 올린다. 태블릿 기록기는 미리보기 프레임으로 돌았으니 갈림이 생길 수 있다(실시간 재생 9판 420/421, metrics 표 12-42).
- **S4 판 결과:** 화료 판은 앱 `result` 를 쓰고 LLM 읽기를 건너뛴다. 테이블에서 확인받은 값이라 뒷도라 · 해저 질문이 사라진다. 유국 판은 텐파이 자리만 앱에서 오고, 공개 손패는 영상에서 읽는다(앱의 공개 손패 판정 기록 폴더를 쓸 수 있는지 먼저 확인).
- **S6 손패 차례:** 그대로 영상 + Opus. 앱이 모르는 유일한 것(뽑은 패가 들어간 칸)이다.
- **앱 기록이 없는 판:** 도중 유국 · 녹화만 있는 반장은 지금 흐름 그대로 간다.

**확인할 것(구현 전):**
- 앱 패보 JSON 의 시각(`at`)과 헤드 녹화 시각(`f_<epoch ms>`)이 같은 시계인지. 태블릿 · 헤드 폰 시계 차이는 11-21 손패 복원 버튼 때 위험으로 적혀 있었다.
- 앱 기록을 PC 로 옮기는 길(대국별 `PaifuStore` · 촬영 기록 `paifu.json`).
- 2반장(11-14)에 앱 기록이 어디에 얼마나 있는지. 재현 시험(3단계)은 이 경로를 먼저 시험할 수 있는 2반장으로 한다.

## 8-5. 앱 기록 우선 — 확인 결과와 구현 명세 (11-24 오후, 사용자 "처음에 녹화영상만 에이전트 넘기는건 아니지?" — 구현 전 · 사용자 확인 대기)

  - `meta.json` 의 국 · 본장 · 선 · 아래 자리
  - `_track/frames_##.zip`(3초 프레임 전부) — 11-17 에 기록기로 재생한 `results/h1x_*/paifu_rec.json` 이 앱 버림 기록의 대역이다(처음 보는 9판 421/421, 표 12-29).

**그래서 앱 기록을 두 층으로 받는다:**

| 층 | 있는 때 | 앱에서 오는 것 | 영상에서 읽는 것 |

| A `paifu.json` | 촬영 기록 + 판 중 버림 기록 켬 | 강 · 울기 · 리치 · 판 결과 전부 | 손패 주인의 매 순 손패, 버림 맞춰 보기 |

**단계별로 넘기는 것:**

## 8-6. 원래 방식대로 짠 흐름 (11-24 오후, 사용자 "우리가 원래 패보 만들었던 방식대로 워크플로우 짜봐" → "네, 진행" — W1 ~ W5 구현 맡김)

## 8-7. 나중에 API 실행기로 바꿀 때의 읽기 도구 (11-24 오후, 사용자 "그걸로 하자" — 결정만, 구현 · 측정 안 함)

지금은 세션이 하위 에이전트를 띄운다(Claude API 금지). 꾸러미(`pending.json`) · 답 파일 형식을 그대로 두면 나중에 "세션이 띄운다" 만 "실행기가 API 로 에이전트 고리를 돈다" 로 바꾸면 된다. 그때 읽기 에이전트에게 줄 도구는 **고정 도구를 기본으로, 코드 실행은 비상구로** 한다. 근거는 지난 읽기 기록 198개를 센 것(metrics 표 12-123).

| 도구 | 하는 일 | 근거 |
|---|---|---|
| `strip` | 같은 영역을 프레임 구간(시작 · 끝 · 걸음)에서 잘라 프레임 번호를 붙여 격자로. 배율 · 열 수 선택 | 차례 읽기 180개가 모두 스스로 짬(sheet). `claudeagent.py` 에 이미 있음 — 배율 · 열 수 · 번호가 붙는지 확인할 것 |

**바뀌는 것 — 에이전트가 쓰는 도구 하나(`try`):**
