# 설계서 — 대국 뒤 복기 대화 ("그때 어떻게 봤어?") (2026-11-24, 초안)

> **🗑 접음(2026-11-24, 사용자 "챗봇은 접었어").** 1단계 t1 불채택(metrics 표 15-19 · problem_log 83) 뒤, 사용자가 복기 챗봇을 접었고 이 기능도 챗봇이라 같이 접었습니다. 서버 브랜치 `feat/review-table` · 측정 도구는 지우지 않고 둡니다. 남는 것은 0단계의 탁자 사실표(LLM 없음)와 보통 유국 패보 저장(10절 ②)입니다.

계기: 사용자 "복기 에이전트 강화 방안 브리핑" → "속도 원인부터" → "굳이 챗봇일 필요가 있나" → "LLM 추론이 필요한 질문" → 상대 손패 추정 재검토 → "우리 서비스만의 차별점을 에이전트로" → **"대국 뒤 복기 대화"**.

형식: 설계와 검토는 이 세션이 하고, 구현은 Opus 5.5 높음 하위 에이전트에 맡깁니다. 실제 Gemini 호출, 매장 시험, 커밋, 배포는 사용자가 말한 뒤에 합니다. 이 문서는 **초안**입니다. 10절의 정할 것이 정해지면 고칩니다.

## 0. 요약

- **무엇:** 매장 대국이 끝난 뒤, 탁자에 앉았던 사람 한 명이 태블릿으로 자기 장면 몇 개를 돌아봅니다. 에이전트가 장면을 보여 주고 "그때 어떻게 봤어?"라고 묻습니다. 사용자가 이유를 말하면 에이전트는 그 이유를 **그때 탁자에 보이던 사실**과 맞춰 봅니다. 예: "현물이라 생각했어" → "남의 강에 [5통]은 없었다".
- **왜 우리만:** 온라인 복기 서비스는 실물 탁자 대국을 받지 못하고, 내 판만 봅니다. 우리는 매장 대국의 네 자리 버림 · 리치 · 울기 · 결과를 이미 기록하고, 장면에 실제 탁자 그림을 붙일 수 있습니다.
- **LLM 이 하는 일:** 사용자의 말에서 "확인할 수 있는 주장"을 뽑고, 그 주장을 맞춰 볼 도구를 부르고, 대화 답을 씁니다. 이 셋은 틀(템플릿)로 만들 수 없는 부분입니다. **장면 고르기와 사실 계산은 코드가 합니다.**
- **손패 없이 되는 범위로 시작합니다.** 매장 판에는 판 중 손패가 없습니다. 그래서 수비 · 리치 · 울기 · 방총 장면과 공개 정보로 맞춰 볼 수 있는 주장만 다룹니다. "효율상 뭘 버렸어야 했나"는 다루지 않습니다.
- **판정은 하지 않습니다.** "밀었어야 / 접었어야" 같은 말은 지금 복기 에이전트와 같은 규칙으로 막습니다. 에이전트는 "그 생각의 전제가 사실과 맞았나"만 말합니다.

## 3. 탁자 사실표 (앱, Dart — 새 파일 `lib/paifu/table_facts.dart`)

판 하나 → JSON. 플레이어 이름 · 패보 id 는 넣지 않습니다(지금 사실표와 같은 원칙).

```
{ "version": 1,
  "game": { round, honba, dealer_wind, dora_indicators, scores(있으면), result{type, winner, loser, win_tile} },
  "seat": "남",                       // 사용자가 고른 자리(바람)
  "events": [                         // 네 자리 사건 전부, 순서대로
    { "step": 23, "wind": "서", "kind": "discard", "tile": "5p", "turn_of_seat": 7,
      "riichi": false, "after_riichi_of": ["남"],      // 이 버림 전에 리치한 자리
      "vs": [ { "wind": "남", "genbutsu": false, "level": "높음",
                "type": "suji_none" | "suji19" | "no_chance" | … ,   // 엔진 RiskTileType 을 정해진 말로
                "visible": 2 } ] },                    // 그 패의 보인 장수(강 · 울기 · 도라 표시)
    { "step": 30, "wind": "남", "kind": "riichi", "tile": "3s", ... },
    { "step": 41, "wind": "서", "kind": "call", "call": "pon", "tiles": [...] } ],
  "scenes": [ { "id": "s1", "step": 23, "why": "deal_in" | "risky_after_riichi" | "own_riichi" | "call" } ]
}
```

- `vs` 의 위험은 **버린 사람 시점**(`riskOf(selfSeat = 그 자리)`)으로, 그 사람 손패 없이 계산합니다. 남은 장수에 그 사람 손패가 빠지므로 조금 덜 정확합니다. 지금 hero 손패 없는 차례와 같은 처지입니다.
- 위험은 지금 규칙대로 **다섯 단계 말**만 씁니다(% 는 쓰지 않음). 단계 경계는 지금 복기 에이전트 사실표와 같은 `riskLevel`(엔진 원값 3 · 8 · 18) 입니다.
- 크기: 판당 버림 약 70장 × 리치 상대 0~2 → 지금 에이전트 사실표보다 작을 것으로 봅니다(구현 때 잼).

## 4. 장면 고르기 (코드)

사용자가 고른 자리 X 에 대해 다음 순서로 최대 5개를 고릅니다. 같은 걸음은 한 번만 씁니다.

1. **방총:** X 가 론을 맞은 버림(`result.loser == X`). 있으면 늘 첫 장면입니다.
2. **리치 뒤 위험 단계 '높음' 이상:** X 가 남의 리치 뒤에 버린 패 중 현물이 아니고 단계가 '높음' · '매우 높음'인 것. 단계가 높은 순, 같으면 앞 걸음 순으로 둘까지.
3. **X 의 리치 선언:** 선언 순 · 선언패(사실만).
4. **X 의 울기:** 첫 울기 하나.

장면이 하나도 없으면 "이 판에서 돌아볼 장면이 없다"고 하고 끝냅니다. 고르는 규칙은 결과를 보기 전에 정한 것이고, 매장 시험 뒤에 고칠 때는 새 판으로 다시 잽니다.

## 5. 대화 흐름 (서버 — 새 그래프 `app/review_table.py`, 라우트 `POST /v2/review/table`)

장면마다:

1. **열기(LLM 없이):** 코드가 장면 글을 만듭니다. 예: "11순에 서 자리 리치 뒤 [5통]을 버렸다. 그때 어떻게 봤어?" 앱은 재생 화면을 그 걸음에 맞춥니다.
2. **사용자 말:** 자유 글(300자 안). "넘어가기" 단추도 있습니다.
3. **주장 뽑기(LLM 1회):** 사용자 말을 JSON 주장 목록으로 바꿉니다. 종류는 정해진 것만 씁니다.
   - `genbutsu`(현물이라 봄) · `suji`(스지라 봄) · `wall`(벽 · 노찬스라 봄) · `visible`(N장 보였다고 봄) · `not_tenpai`(그 사람이 텐파이가 아니라 봄) · `unaware_riichi`(리치를 몰랐음) · `dora`(도라라서) · `no_safe`(안전패가 없었음) · `pushed_on_purpose`(일부러 밀었음) · `other`(그 밖)
   - 각 주장에 `tile` · `wind` 가 있으면 함께 적습니다.
4. **맞춰 보기(도구, 코드):** 주장 종류마다 정해진 도구를 코드가 부릅니다. LLM 이 고르지 않습니다.
   - `genbutsu` · `suji` · `wall` · `visible` → `tile_facts(step, tile, wind)`: 현물 여부 · 엔진 꼴 · 보인 장수 · 단계
   - `not_tenpai` → 그 사람이 리치했으면 "리치는 텐파이 선언이다". 울기만 했으면 엔진 텐파이율의 단계 말. 아니면 "확인할 수 없다"
   - `unaware_riichi` → 리치 걸음과 이 버림 걸음의 차(몇 걸음 전에 리치했나)
   - `dora` → 도라 표시패와 맞나
   - `no_safe` · `pushed_on_purpose` · `other` → **확인할 수 없음**(손패가 없거나 판정 영역). 답에서 그렇다고만 말합니다.
5. **답(LLM 1회):** 주장마다 "맞았다 / 달랐다 / 확인할 수 없다"를 근거와 함께 3~5문장으로 씁니다. 마지막에 열린 물음 하나를 둘 수 있습니다(예: "그때 서 자리 강에서 무엇을 봤어?"). 사용자가 다시 말하면 3~5를 되풀이하고, 장면마다 최대 3번 오갑니다.
6. **끝:** 장면을 다 보면 코드가 요약 카드를 만듭니다. 장면마다 사용자가 말한 이유 한 줄과 맞음/다름/확인 불가 표시가 들어가고, LLM 은 쓰지 않습니다.

LLM 호출은 장면 한 번 오갈 때 2회(주장 뽑기 + 답)입니다. 표 15-15 의 호출당 약 2.7초로 보면 한 번 오가는 데 약 6초입니다. 대국 뒤 대화라 지금 질문 창보다 기다림이 덜 문제가 됩니다.

## 6. 검증 (코드)

- 지금 a8 검사를 그대로 씁니다. 패 · 숫자 · 단계 말은 근거 안에서만, 판정 말 금지, 영어 · 존댓말 금지 등입니다.
- **새 검사 — 맞장구 금지:** 답에 "현물이었다 · 스지였다 · 노찬스였다 · N장 보였다 · 몰랐을 수 있다" 같은 긍정이 있으면, 근거에 그 값이 참으로 있어야 합니다. 사용자의 틀린 전제에 맞장구치는 것이 이 기능의 가장 큰 위험이라 따로 검사합니다.
- **새 검사 — 확인 불가를 확인한 척 금지:** 주장 종류가 `no_safe` · `pushed_on_purpose` · `other` 이면, 답에 그 주장을 맞다 / 틀렸다고 하는 말이 없어야 합니다.
- 주장 뽑기 결과도 검사합니다. 종류가 목록 밖이거나 `tile` 이 패 코드가 아니면 한 번 다시 시키고, 그래도 안 되면 `other` 하나로 봅니다.

## 7. 앱 화면

- **들어가는 곳:** 패보 목록의 매장 판(버림만 있는 판)에 "대화로 복기" 단추를 둡니다. 누르면 자리를 고르고 대화 화면으로 갑니다.
- **대화 화면:** 위에는 재생 화면(그 걸음, 강 네 자리), 아래에는 대화가 있습니다. 장면 사이 이동은 "다음 장면" 단추로 합니다.
- **개인정보:** 질문 · 답은 서버 로그에 남기지 않습니다(지금과 같음). 대화 기록은 기기 안에만 둡니다. 탁자의 다른 사람 장면도 그 자리를 고르면 볼 수 있으므로, 공용 태블릿이면 **누가 어느 자리를 보는가**는 매장 운영 규칙으로 정합니다(10절 ③).
