# 개선 계획서 — 새 매장 사진 없이, 과적합 없이 (2026-11-05)

이 문서는 다른 세션이 그대로 따라가도록 쓴 계획이다. 새 세션은 `HANDOFF.md` 맨 위 두 절과 이 문서를 읽고 시작한다.
진행 상황은 이 문서의 각 단계 끝 "진행" 줄에 날짜·결과·metrics 표 번호를 덧붙인다.

## 0. 왜 이 순서인가 — 진단

- **개발 세트가 포화됐다.** hybrid(`/v2/localroles`) 경로가 개발 /32 에서 32/32 다(표 1-78·1-79). 어떤 변경도 이 세트에서는 차이를 못 낸다.
- **운영 모델이 전부 개발 세트를 학습했다.** 8회차 final 검출기, 분류기 `tile-cls-mnv3s.onnx`, 역할 모델 `tile-roles-rot.onnx` 모두 개발 25장면 전부로 학습·미세 조정했다. 운영에서 잰 32/32 는 낙관적이다.
- **테스트 15장(10/24 삼각대)은 판별력이 0 이다.** 탁자가 약 25° 기울어 격자·틀이 안 잡혀 2회차도 8회차도 장면 0/15 (표 1-69). "학습 전에 테스트 세트의 판별력을 확인하지 않은 것이 빈틈" 이라고 거기 적혀 있다.
- 따라서 지금 모델을 더 학습하면 **개발 34장의 실패 사진을 하나씩 고치는 일**이 된다(표 1-70 주의 줄). 그게 과적합이다.

순서는 **① 잴 수 있게 만든다 → ② 사진과 무관한 검증·안전장치를 넣는다 → ③ 그 다음에 학습한다 → ④ 속도**. ①②는 GPU 없이 노트북에서 된다.

## 0-1. 모든 단계에 적용하는 원칙

1. **채택 근거는 홀드아웃 숫자만.** 나눔 모델(`det_r8_fold_*`·`det_fold_*`·`cls_<part>`·역할 모델 교차 검증)과 테스트 15장 숫자만 채택 근거다. final(전부 학습) 모델 숫자는 "배포 확인" 이지 근거가 아니다.
2. **합격 기준은 학습·실험 전에 적는다.** 표 1-69 방식. 결과를 본 뒤 기준·세트를 바꾸지 않는다. 학습은 설정당 한 번.
3. **테스트 15장으로 규칙을 고치지 않는다.** 실패 사진을 보고 고친 규칙은 개발 세트에서만 만든다. 테스트 15장은 단계가 끝날 때 한 번 잰다(사용자 결정 10-27).
4. **같은 시각에 나란히 잰 것만 전·후로 적는다.** metrics.md 규칙 그대로. 끝나면 **같은 턴 안에** `docs/metrics.md` 에 한 줄.
5. **장면 단위 /32 의 ±2 는 잡음이다.** 패 단위(개발 상자 1,046·테스트 패 211)와 "경고 없는 틀린 자동" 을 같이 본다.
6. 평가 제외는 `experiments/speed/seat_grow.py` `EXCLUDED`(5장) 그대로. 새 사진 없음.
7. 실행 조건: `flutter drive` 는 한 번에 하나. 측정 서버는 내가 띄운다(launch.json `recognizer-r8rot-{bcd,am,pm}` = 나눔 모델, `recognizer-prodlike` = 운영 모델).

## 2단계. 채택 잣대를 "나눔 모델 + 패 단위 + 신뢰구간" 으로 (노트북, 반나절)

**목적.** 32/32 포화 위에서도 차이를 볼 수 있게 한다.

**할 일.**
1. **분류기 나눔.** `experiments/tile_classifier/train.py` 는 `cls_{bcd,am,pm}.pt` 세 나눔이 이미 있다. 역할 모델은 `role_set.py` 교차 검증(3겹) 숫자가 있다. 검출기는 `det_r8_fold_{a,b}`. **셋 다 "그 사진을 안 배운 모델" 조합으로만 개발 세트를 잰다** — `run_local_server.py --local-fold <a|b>,<part> --seat-det det_r8 --role-model …` 가 이미 그 조합이다. 역할 모델만 fold 별 ONNX 가 없으니 `role_set.py` 3겹 가중치를 `role_export.py` 로 fold 별 ONNX 로 내보낸다(`tile-roles-rot_fold_{bcd,am,pm}.onnx`).
2. **패 단위 채점을 앱 흐름에도.** `experiments/speed/flow_visit.py score` 에 손패+울기 다중집합 교집합(패 단위, `field_bench.py` 와 같은 정의)을 더한다. 개발 32회 분모 = 정답 손패·울기 장수 합.
3. **부트스트랩 구간.** 장면 단위 n=32·패 단위 n≈430 에 대해 부트스트랩 1,000회로 전·후 차이의 95% 구간을 찍는 작은 함수(`flow_visit.py` 나 `experiments/speed/stats.py`). 구간이 0 을 포함하면 "같음" 으로 적는다.
4. **기준선 한 벌.** 위 조합으로 개발 32회 + 테스트 15장(펴기) + 색 바꾼 15장을 한 번 재서 "2단계 기준선" 으로 metrics 에 적는다. 이후 모든 변경은 이 기준선과 같은 시각 나란히.

**합격 기준.** 없음(잣대 만들기). 단 기준선의 나눔 모델 개발 /32 가 final 32 보다 낮을 것이 예상된다 — 그 차이가 "낙관 편향" 의 크기이고 그걸 적는 것이 목적.

**기록.** metrics "지금 기준값" 절에 "홀드아웃 기준선" 줄 추가. 진행: 2026-11-05 21:00~21:21 **끝, metrics 표 1-90 + "지금 기준값" 홀드아웃 기준선 줄.** (1) 역할 모델 3겹 가중치가 저장돼 있지 않아 같은 설정으로 한 번 다시 학습(`role_set.py --save-folds` 새 옵션, 1,026/1,046 으로 fold 별까지 기존과 같음) → `server_bench/models/tile-roles-rot_fold_{am,pmA,pmB}.onnx`. 역할 나눔이 오전/오후A/오후B 셋이라(검출기·분류기는 둘) 서버도 launch.json `recognizer-fold-{bcd,am,pmA,pmB}` 넷(B·C·D 는 역할 라벨에 없어 final), 대응표 `experiments/tile_classifier/README.md` 끝 절, `run_local_server.py --role-model` 이 fold 이름을 받음. (2) `flow_visit.py score` 패 단위 열(/436)·합계 줄·`records`, `summarize_field.py` 패 단위(/211)·장면 단위(/5, 사진 과반)·경고 없는 틀린 자동·`records`, `field_bench.py` 장면 단위·사진별 `seat_hit`. ## 4단계. 마작 규칙 검증기 (앱 Dart, 하루)

**규칙(순수 함수 `lib/table/hand_rules.dart` 로, 단위 테스트 포함).**
- V1 **5장 초과**: 손패+울기+화료패+표시패(+추적 강이 있으면 강)에 같은 패가 5장 이상 → 오독 확정, 자동 반영 막고 "같은 패 5장" 경고.
- V2 **적5 중복**: 0m·0p·0s 각 1장 초과 → 경고.
- V3 **화료형 아님 + 한 장 바꾸면 됨**: 읽은 손패가 화료형이 아닐 때, 분류기 2순위 후보(서버 응답에 `alt`·`conf2` 를 더해야 함 — `app/local_read.py` 분류 결과에 상위 2개 넣기)로 한 장만 바꿔 화료형이 되는 조합이 **정확히 하나**면 "후보" 로 띄운다. 자동 반영은 하지 않는다(노란 테두리 + 확인).
- V4 **울기 구성**: 치=같은 색 연속 3, 퐁=같은 패 3, 깡=4. 안 맞으면 경고(지금은 서버가 conf 0 으로 돌려주는 것과 합침).

## 8b단계. 탁자 독립 격자 — 기준점을 탁자가 아니라 마작에 둔다 (앱+서버, 2~3일, 7-2 판정 뒤)

**배경(2026-11-06 사용자 결정).** 카메라 거치는 **가장 최근 방식(탭 거치대, 위에서 반듯하게)으로 고정**하고, 대신 **다른 탁자에서도 그대로 되는 격자**를 만든다. 기울기 보정(펴기)은 더 키우지 않는다.

**지금 구조의 문제.** 격자 = 사진 좌표의 축 평행 선 4개(`GridZones` x1·x2·y1·y2) + 리치봉 상자 + 비율 상수 열 개(`lib/table/grid_zones.dart`). 만드는 길이 셋(선 끌기, `/v2/setup`, `felt_grid.dart` 펠트 모서리)이고 서버 `localroles` 도 같은 선을 받아 따로 자른다(`crop_seat`·`hand_frac`). 거치 기하(카메라가 탁자를 보는 법, 거치할 때 한 번)와 탁자 지식(어디가 손패·울기·강·왕패·기기 자리인지, 늘 같음)이 한 자료에 섞여 있어 카메라가 조금 돌아가면 탁자 지식까지 다시 맞춘다. 상수는 장면(C·D·10-31 오후)을 보고 맞춘 값이라 기하 수준의 과적합이다. 무엇보다 **펠트 색(초록 고정)·기기 크기·테두리**에 기대므로 탁자가 바뀌면 깨진다 — 색 바꾼 15장 0/15, 회귀 `wb_tung` 0/32 가 그 증거.

**탁자마다 달라지는 것 / 안 달라지는 것(카메라가 위에서 반듯할 때).** 달라짐: 펠트 색·크기, 테두리 색·폭, 가운데 기기 모양·크기, 손패 줄이 펠트 안인지 테두리 위인지. 안 달라짐: 패 한 장 크기는 사진에서 잴 수 있음, 배패 직후 **패산 4줄이 기기 둘레에 정사각형**으로 섬(자동탁 기구), 손패는 가장자리·울기는 오른쪽 모서리·강은 기기 옆·왕패는 패산 위(규칙). 지금 격자는 앞쪽에, 새 격자는 뒤쪽에 기댄다.

**설계.**
- (가) **기준점 = 가운데 기기 + 배패 직후 패산 사각형.** 패산 네 변에서 중심·방향·패 한 장 크기(u)를 얻는다. 이것이 거치 상태의 전부이며 카메라가 고정이니 한 판 내내 유효하다. 패산 찾기는 서버 `read_wall`·`wall_score`·왕패 위치 실험(`dora_wall_locate`)을 쓴다. 저장값은 중심·방향·u 와 기기 상자뿐.
- (나) **구역표는 패 단위(u)로 한 벌.** 손패 줄 14u×1u(가장자리, 넉넉히 ±1u), 울기 모서리 4u 묶음, 강 6u 폭 3~4줄(기기 옆), 왕패는 패산 위, 리치봉은 기기 가장자리 홈. 규칙이 정하는 값이라 탁자와 무관. 탁자마다 다른 것(패산에서 손패 줄까지 거리 = 테두리 폭)은 구역을 넉넉히 잡고 세부는 검출기·역할 모델이 가린다(지금도 역할 모델이 그 일을 한다). 구역표는 JSON 한 파일로 두고 **앱(Dart)·서버(Python)가 같은 파일을 읽는다** — 구역 논리 두 벌을 없앤다. `grid_zones.dart` 의 사진 좌표 상수는 전부 이 표로 옮기거나 지운다.
- (다) **펠트 모서리는 보조.** 배패 전(대국 시작 직후 자동 맞추기)에는 기기 위치 + 펠트로 임시 격자를 잡고 첫 배패에서 패산 사각형으로 확정한다. 펠트 색은 초록 고정 대신 **기기 둘레 띠에서 사진마다 잰다**(색 바꾼 탁자 대응). 패산이 안 보이면(가림, 패산을 미리 가져가는 집, 수동 탁자) 펠트 보조 격자로 받는다. 자동이 다 실패하면 사용자가 기기 상자·모서리를 **한 번** 찍는 길을 남긴다(편집은 on/off 토글, 환경 바뀔 때 한 번).
- (라) **서버가 기준점을 잡는다** — 앱은 사진(+ 알고 있으면 기준점)만 보내고 서버가 패산·기기로 기준점을 잡아 구역표대로 자른다. 8단계 P5(서버 펴기)와 선 4개 질의(`rolesQuery`)는 이 단계가 흡수한다. 거치 화면 선 끌기 편집기는 "기기·모서리 확인" 으로 바뀐다.
- (마) 더 나가면 역할 모델 토큰을 선 기준에서 u 좌표 기준으로 바꿔 재학습해 구역 자체를 모델에 맡긴다(7단계 원칙: 기준 선행·한 번). 이 단계의 범위 밖, 후보로만.
