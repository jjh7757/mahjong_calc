## 0. 요약

- 지금 패보에는 **국 시작 점수 · 공탁이 없고**, 버림의 `tsumogiri` 칸은 **hero 한 자리만** 채워져 있다(예시 r19: hero 10번 채움, 나머지 세 자리 30번 null. 남의 것은 리치 뒤 규칙으로만 참).
- 둘 다 알아낼 수 있는 정보다. **점수는 앱이 이미 안다**(연결만 하면 됨). **쯔모기리는 녹화 프레임에 있다**(hero 자리에서는 "종류" 판정이 여러 번 거의 다 맞았다 — 2절).
- 쓰임은 셋: ① 우리 엔진의 방총 위험 계산에서 가정을 뺌 ② 복기 에이전트 사실표 ③ Mortal 로컬 채점을 수비 · 순위가 걸린 순까지 넓힘. **Mortal 을 제품에 넣는 것은 11-18 결정(채점자로만)대로 범위 밖이다.**
- 순서는 "먼저 값어치를 재고, 싼 것부터 만든다":
  - **0단계(돈 0):** 정보가 다 있는 천봉 판에서 점수 · 쯔모기리를 지워 넣으면 답이 얼마나 바뀌나. 작으면 비싼 쪽(쯔모기리)은 접는다.
  - **A(점수 · 공탁):** 형식 칸 + 앱 저장 + 변환. 코드만, 작다.
  - **B(남의 쯔모기리):** 정답 만들기가 가장 큰 일. 코드 거르기 → 남은 차례만 읽기.

## 3. 0단계 — 값어치 재기 (돈 0, 천봉 개발 200판)

만들기 전에 "이 두 정보가 없으면 답이 얼마나 달라지나" 를 잰다. 천봉 패보는 둘 다 들어 있으니 지워 보면 된다.

- 자료: 맞추기 실험의 **개발 200판**(`experiments/paifu_review/mxfit/split.py`). 시험 판은 열지 않는다.
- 세 가지로 바꿔 넣는다: (가) 점수를 네 자리 25000 · 공탁 0 으로 (나) 남의 쯔모기리 표시를 모두 "손에서 냄" 으로(지금 변환의 기본) (다) 둘 다.
- 재는 것:
  - **Mortal-S42 첫째 버림이 바뀌는 비율**(원래 입력 대 바꾼 입력), 그리고 바뀐 곳에서 원래 Q 기준 손해. 국별(동장 / 남1 ~ 3 / 오라스), 위협(남 리치) 유무로 나눔.
  - **우리 엔진**(mahjong-helper 이식): 남이 리치한 차례에서 패의 위험 단계가 바뀌는 비율, 가장 안전한 패가 바뀌는 차례 비율.
  - 판 단위 부트스트랩 신뢰구간.
- 도구는 있는 것(`mxfit/s42_batch.py` · `tool/tenhou6_features.dart`)에 "지워 넣기" 선택지만 더한다. CPU 시간만 든다.
- **판정(재기 전):**
  - 쯔모기리: 위협 있는 차례에서 S42 첫째 버림이 바뀌는 비율이 **5% 이상이면 "값어치 있음"**, 2% 미만이면 "작음", 그 사이는 "사이". 엔진의 "가장 안전한 패가 바뀌는 차례" 도 같은 문턱으로 따로 적는다.
  - 점수: 오라스 · 남3국에서 바뀌는 비율이 5% 이상이면 "값어치 있음", 전체에서 1% 미만이고 오라스에서도 2% 미만이면 "작음".
  - "작음" 이면 그쪽은 만들지 않고 사용자에게 접을지 묻는다. A 는 싸서 "사이" 여도 진행, B 는 "값어치 있음" 일 때만 B1 로 간다.

### 0단계 명세 (11-22 오후, 사용자 "0단계 시작" — 아래는 구현 · 재기 전에 적음)

- **기준 입력은 이미 있다:** 맞추기 실험 1단계의 개발 200판 결과(`results/mxfit/stage1/s42.jsonl` 84,762결정 · `features/`). 새로 도는 것은 바꿔 넣은 세 벌뿐.
- **바꿔 넣기의 뜻(매장 패보가 아는 만큼만 남긴다):**
  - 점수 가림: 국 시작 `scores` 를 네 자리 25000, `kyotaku` 0 으로. 본장은 그대로(패보에 있다).
  - 쯔모기리 가림: **hero 아닌 자리의 버림만.** 그 자리가 리치를 선언한 **뒤**의 버림은 참 그대로(기록기가 규칙으로 안다), 그 밖(리치 선언패 포함)은 S42 에는 "손에서 냄"(지금 변환의 기본), 우리 엔진에는 null(모름 → 엔진 기본 정책이 손에서 낸 것으로 셈). hero 의 버림은 그대로.
- **S42 쪽 셈:** 결정(`game · kyoku · seat · k`)마다 기준과 바꾼 쪽의 첫째 버림(`s42Discard`)이 다른가. 바뀐 곳의 손해 = 기준 Q 에서 (바꾼 쪽이 고른 버림의 Q − 기준 첫째 버림의 Q). 대상은 뽑고 버리는 결정(`trigger == tsumo`)으로 두 쪽 다 답이 있는 것.
  - 나눔: 위협 유무(다른 자리가 리치 선언한 뒤인가 — 맞추기 실험의 구간 정의와 같은 칸), 국(동장 / 남1 · 남2 / **끝 묶음 = 남3국 + 남4국 + 연장** / 그중 **오라스 = 남4국 이후**), 점수 가림은 국 시작 순위(1등 / 2 · 3등 / 4등)로도.
- **엔진 쪽 셈(쯔모기리 가림만 — 엔진이 점수를 안 쓰는지는 구현 때 코드로 확인해 적는다):** 다른 자리가 리치한 차례의 후보 패마다 위험 단계(문턱 3 · 8 · 18 + 모두에게 안전패)가 바뀌는 비율, **가장 안전한 패(위험이 가장 낮은 패 묶음)가 바뀌는 차례 비율**, 실제 버린 패의 단계가 바뀌는 비율.
- 비율마다 판 단위 부트스트랩 95% 구간(2,000번, 씨 20261122).
- **판정에 쓰는 숫자(위 3절 문턱 그대로, 뜻만 못 박음):** 쯔모기리 = "위협 있는 차례의 S42 첫째 버림 바뀜 비율", 점수 = "끝 묶음의 S42 첫째 버림 바뀜 비율"(5% 이상이면 값어치 있음), 점수 "작음" = 전체 1% 미만이고 오라스 2% 미만. 엔진의 "가장 안전한 패 바뀜" 은 같은 문턱으로 따로 적되 B 를 갈지는 S42 쪽 숫자로 정한다(둘이 갈리면 그대로 적고 사용자에게 묻는다).
- 자기 확인: 아무것도 가리지 않고 돌린 2판이 1단계 결과와 같아야 한다.
- **덧붙임(구현 뒤 · 200판을 돌리기 전에 못 박음):** 위 "위협" 을 적을 때 "다른 자리가 리치 선언한 뒤" 와 "맞추기 실험의 구간 칸" 을 같은 것으로 잘못 알고 썼다. 구현자가 확인하니 맞추기 칸(`riskSeats`)은 울어서 텐파이가 짙은 자리도 넣어 더 넓다(2판 연습에서 결정 1,133 중 554 대 남 리치 222). **판정에는 글자대로 "남이 리치 선언한 뒤"(`riichiSeats`)를 쓰고**, `riskSeats` 기준 숫자는 나란히 적는다. 두 정의의 판정 등급이 갈리면 그대로 적고 사용자에게 묻는다. 국 묶음은 `kyokuNum`(동1 = 0 … 남4 = 7, 서장 8 ~)으로 나눈다. 엔진 쪽 대상은 울기 뒤 버림까지 포함한 hero 버림 전부다(S42 쪽은 뽑고 버리는 결정만).
- 구현하며 확인한 것: **우리 엔진은 국 시작 점수 · 공탁 · 본장을 쓰지 않는다**(`DiscardContext` · `RiskContext` 에 그 칸이 없음) → 점수 가림은 S42 쪽만 잰다. 엔진의 기본 정책에서 null 은 "손에서 냄" 과 같은 셈이라 엔진 가림은 S42 가림과 같은 뜻이다.

**결과(11-22 오후, metrics 표 16-12 · problem_log 75):**
- 구현 Opus 5.5 높음 하위 에이전트(`mxfit/s42_batch.py --mask` · `tool/tenhou6_features.dart --mask-tsumogiri` · `mxfit/input_value.py`), 가림 없는 2판 재현(Q 차이 0 · 값 뽑기 1,265/1,265줄). 개발 200판 81,229결정.
- **점수: 끝 묶음(남3국 이후) 8.86% (8.28 ~ 9.49) → "값어치 있음".** 전체 4.22%, 오라스 10.98%, 국 시작 1등 6.50% · 4등 5.77% · 2 · 3등 2.31%.
- **쯔모기리: 남 리치 뒤 1.43% (1.23 ~ 1.64) → "작음".** 넓은 위협 정의로도 1.87%, 전체 1.06%. 엔진의 가장 안전한 패 바뀜 0.54%(남 리치 뒤) · 0.93%(넓은 정의) → 같은 등급.
- 따로 볼 것: 엔진의 위험 단계 말은 넓은 위협 정의에서 후보의 7.1% · 버린 패의 5.3% 가 한 칸 위로 바뀐다(남 리치 뒤는 1.7 ~ 1.8%).
- **다음(사용자 결정):** 미리 적은 대로면 A 는 진행, B 는 만들지 않는다. B 를 접을지 묻는다.

## 4. A — 국 시작 점수 · 공탁

- **형식:** 패보 머리에 `start_scores`(자리 순 4개 — 이 국에서 리치봉을 내기 전 점수)와 `kyotaku`(국 시작 때 걸려 있던 리치봉 수)를 더한다. 둘 다 없어도 되는 칸(옛 파일은 null = 모름).
- **저장:** `_savePaifu` 가 `Game` 에서 채운다. "국 시작" 을 정확히 정하는 것이 구현의 핵심 — 저장 시점에는 이 국의 리치로 점수가 이미 빠졌을 수 있으니 `riichiSeats` · `checkpoints` 로 되돌려 계산한다. 구현자가 `Game.declareRiichi` 와 화료 반영 순서를 읽고 정한다.
- **쓰는 곳:** `toTenhou6` 가 패보 값을 기본으로 쓰고(인자가 있으면 인자 우선) 공탁도 넣는다. `paifu.check()` 에 "네 점수 + 공탁 × 1000 = 시작 점수 합" 경고.
- **시험:** 리치 0 · 1 · 2명, 앞 국에서 넘어온 공탁, 본장, 사진으로 리치를 뒤늦게 적은 경우, 되돌리기 뒤 다시 저장. 한 반장을 대국 기록으로 흉내 내 국마다 저장된 값이 손계산과 같은가. 옛 패보 파일 읽기 · 예시 재생 화면은 그대로.
- **예시 11판:** 11-14 점수 기록은 저장소에 없다(촬영 기록 `meta.json` 에 점수 없음). 채우지 않고 null 로 둔다. 화면 녹화(`visit_20261114/screen/`)에서 읽어 넣을지는 7절.
- 사실표(`agent_facts`)에 점수 · 순위를 넣는 것은 A 가 끝난 뒤 따로 정한다(에이전트 지시문 · 검증이 같이 바뀌므로).

### A 명세 (11-22 오후, 구현 전에 적음 — 코드 확인: `lib/game/game.dart` · `lib/ui/mount/mount_screen.dart`)

- 패보를 저장하는 때(`_savePaifu`)는 화료 사진을 읽은 직후, **"대국에 반영" 전**이다. 그때 `Game` 의 상태: `scores` 는 이 국에 점수판으로 적은 리치의 1000점이 이미 빠진 값, `riichiSeats` 는 이 국에 그렇게 리치한 자리, `riichiSticks` 는 탁자 위 리치봉(넘어온 것 + 이 국 것). 사진에서 읽은 리치는 아직 반영 전이다.
- 그래서 **국 시작 점수 = `scores[s]` + (s 가 `riichiSeats` 에 있으면 1000)**, **국 시작 공탁 = `riichiSticks` − `riichiSeats` 수**. 이 식이 `Game` 의 실제 동작과 맞는지는 구현자가 `declareRiichi` · 국 넘김 · 유국 뒤 넘어온 봉(`carriedStickSeats`) · 되돌리기 코드를 읽고 시험으로 못 박는다(다르면 멈추고 보고).
- 형식: `Paifu.startScores`(`List<int>?`, 자리 순 4개) · `Paifu.kyotaku`(`int?`), JSON 열쇠 `start_scores` · `kyotaku`. 없으면 null(옛 파일 그대로 읽힘 · 다시 쓸 때 열쇠를 더하지 않음). `copyWith` 로 보존(손패 복원이 패보를 다시 쓸 때 사라지면 안 됨).
- `paifu.check()`: 있으면 4개 · 100의 배수 · 공탁 0 이상. 합계 검사는 패보가 시작 점수 설정을 몰라서 넣지 않는다.
- `toTenhou6`: 점수는 인자 → 패보 `startScores` → 25000 순, 공탁은 (새 인자) → 패보 `kyotaku` → 0 순. 가정 목록(assumptions) 글도 어디서 온 값인지 적는다. 패보에 값이 없을 때의 출력은 지금과 바이트까지 같아야 한다.
- 앱 화면 · 사실표 · 예시 11판은 안 바꾼다(예시는 null 그대로).
- 시험: 국 시작 값 계산(리치 0 · 1 · 2명, 유국 뒤 넘어온 봉, 본장, 시작 점수 30000 설정, 리치 뒤 되돌리기), 패보 JSON 왕복(있음 / 없음), `toTenhou6` 세 순서, 옛 예시 파일 읽기. `flutter analyze` 0 · 전체 시험 통과.
