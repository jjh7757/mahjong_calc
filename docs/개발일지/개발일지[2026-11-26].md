## 문제 1: 실행기로 2반장 아홉 판을 끝까지 — 차례 답 69/70, 그러나 세션 손 두 곳 · 메모 색인이 읽기 에이전트에 샘

- **해결방안:** `start --visit … --game 4` 1번 + `go` 5번. Claude Code 하위 에이전트 Opus 5.5 높음 · API 0(표 12-135).
  - 판 결과 읽기 6 → 준비 읽기 9 → 차례 읽기 78 → 판 supervisor(판마다 의심 차례를 다시 읽히는 에이전트) 9 · 다시 읽기 18 → 조립 · 질문 목록.

## 문제 3: 조용한 틀림의 길 — 확신 숫자 칸 `p`(8-18), 효과는 15/16 이었으나 "꺼" 로 기록만(8-22)

## 문제 4: 볼 양 26 가운데 16 이 준비 읽기 알림 — 다른 후보 값 칸 `alt`(8-19)로 26 → 17

- **원인:** 준비 에이전트가 `unsure` 에 적은 글이 판마다 1 \~ 3개씩 그대로 질문이 되고, 영향을 잴 수 없어 숨김 규칙에도 안 걸림. 사용자는 16 가운데 하나도 답하지 않음. 세션이 열어 보니 결과를 바꿀 수 있던 것은 넷.
- **해결방안:** 사용자 "명세 써 줘" → "구현 맡겨". Opus 5.5 높음 하위 에이전트 약 2시간 39분.
  - 칸 이름으로 숨기기("`t_reveal` 알림은 안 묻기")는 16 을 보고 만든 사례 덧댐이라 버림. 다른 후보를 값(`alt`)으로 받아 코드가 LLM 없이 한 번 더 돌려 차이를 세고, 차이 없으면 숨김 · 목록이 바뀌면 두 값 고르기 질문 · 창만 바뀌면 그 차례를 차례 질문 길로.
  - 만든 사례(세션이 글 속 후보를 값으로 옮긴 답)로 메모 5 · 숨김 5 · 고르기 4(세션이 미리 센 넷과 같음) · 창 흔들림 2 → **볼 양 26 → 17**. 3반장 되돌이 바이트 같음(표 12-137, problem_log 86 이어서 13). 06ef269.

### 시행착오

## 문제 5: 띄우는 곳이 셋 — "너무 기형적인 구존데", 관리자 하나 + LangGraph 그래프(8-20)

- **원인:** 문제 1 의 동시 20 한도. 세션이 "실행기가 supervisor 를 나눠 내기 / 다시 읽기를 실행기 꾸러미로" 를 내자 사용자 "너무 기형적인 구존데" · "API 단독으로 실험해야하는데 그 구조가 맞니?" — 띄우는 곳이 세션 · supervisor 아홉 · 쪽지 대신 처리 셋이라 아무도 동시 개수를 모르고, "supervisor 가 작업자를 띄움" 은 Claude Code 에만 있는 동작이라 API 로 못 옮김.
- **해결방안:** 사용자가 낸 꼴 "관리자 1 + 읽기 여럿" + "랭그래프로 상태 관리하면 되지 않니".
  - 반장 관리자 하나는 라운드마다 결정만 파일로(영상 안 봄 · `set` 뺌), 꾸러미 띄우기 · 동시 수 · 재개 · 사용자 확인 멈춤은 LangGraph 그래프 하나(`paifu_graph.py`). 손 셋: `replay`(옛 답 베낌) · `session`(세션이 하위 에이전트로 채움) · `api`(Claude API).
  - 사용자 "깔고 구현 맡겨" → `langgraph-checkpoint-sqlite` 3.1.3 설치 · Opus 5.5 높음 하위 에이전트가 1,121줄. 범위는 사용자 "2반장만 보고 제대로 작동하는지 보는게 효율적이지 않니" 로 줄임.
  - 옛 실행기와 나란히: **103 파일 가운데 바이트 같음 98 · 실행 이름만 다름 5 · 다름 0** · 다시 읽기 18 모두 그래프를 지남 · 최대 동시 4(한도 4) · S6 도중 죽이고 이어도 두 번 채운 꾸러미 0(표 12-138). 01c012e.

### 시행착오

1. **세션 잘못 짚음 ①:** "관리자 하나엔 반장이 안 담긴다" 고 반대 — 관리자가 프레임을 직접 여는 경우의 어림(차례당 15만)이었고, 답 요약만 보면 라운드 1 약 4만 자(어림 1.5만 토큰).

3. 찾은 흠(안 고침): 새 `--visit` 실행에서 옛 실행기 재생이 S6 옛 답을 못 찾음(`read_root` 가 자기 자신).

## 문제 6: `api` 손(8-21) — 가짜 시험에서 같은 60분 실행을 세 번, 그리고 진짜 API 첫 한 판 1.75달러

- **해결방안:**
  - `paifu_apihand.py`(1,137줄): 꾸러미 `TASK.md` 를 그대로 첫 메시지로(지시문 안 바꿈) · 고정 도구 여섯 · 폴더 밖 쓰기 막기 · 꾸러미 한도 3달러 · 실행 한도 · 가짜 클라이언트 · 진짜 호출은 `--i-mean-it` 이 있어야. 섞어 돌리기 셋이 재생 기준과 103 파일 다름 0(표 12-141). 01c012e · HANDOFF 다시 적음 a4f5664.
  - 사용자가 크레딧을 넣고 "응 가 길로 진행해" → **진짜 API 첫 실행**(16:55 \~ 17:16): w14 한 판만 `api`, 나머지 여덟 판과 관리자는 재생. 끝까지 돎 · **1.75달러**(준비 읽기 1.56 · 순 읽기 0.19) · 캐시 읽기 219만 토큰 · 순 답 1/1 · 패보 9/9 재생 기준과 바이트 같음(표 12-142).

### 시행착오

1. **같은 실행을 세 번:** 맡길 때 "이미 돈 실행 자료를 베껴 쓰라" 를 안 줘서 하위 에이전트가 2반장 전체(약 60분, 대부분 코드 단계)를 세 번 처음부터 돌림. 사용자 "한판만 api 돌리면 된거 아니야? 나머지는 왜 돌려?" → "지금까지 실행했던 데이터로 대체했으면 됐잖아" → `fork --from <실행> --at <단계>`(끝난 실행을 베껴 그 단계부터 — 7초 + 이어 돌리기 479초, 처음부터는 약 2,000초).

3. w14 는 손패 주인 순이 하나뿐이라 읽기 질을 못 봄 — 실행 전에 그 점을 분명히 안 말해 사용자가 "한판의 한 순만 한거야?" 로 물음. 한 판 시험에도 여덟 판 재생이 붙어 시간 대부분이 코드 단계(→ 문제 7). 돈의 89% 가 준비 읽기.

## 문제 7: 관리자 LLM 을 뺌 — 판마다 판 LLM(orchestrator-workers) · 순 → 판 → 반장 조립(8-23 · 3-0)

- **원인:** 사용자 "패보 에이전트 api 실험을 진행할거야 … 하위 에이전트는 판단위로 맡고 각순마다 llm을 호출해서 순단위로 결과파일을 따로" → 관리자 설명을 듣고 "판별로 독립되어 있어서 의미가 퇴색되긴하네" → "멀티에이전트 패턴을 외부에서 검색해보고 우리에게 맞는 패턴 추천해봐".
- **해결방안:**
  - 세션이 외부 자료(Anthropic "Building effective agents" · 멀티에이전트 리서치 글, LangGraph 문서, Cognition "Don't Build Multi-Agents" 등)를 보고 **관리자 없는 꼴** 추천 → "고쳐". 첫 읽기는 코드가 나란히(sectioning) · 다시 읽기는 판 LLM 이 지휘(orchestrator-workers) · 검사 → 다시 읽기는 평가-개선 고리 · 판끼리 견주기와 질문 수 자르기는 코드. 판 LLM 은 띄우지 않고 도구만 부름 — 띄우는 곳은 그래프 하나 그대로.
  - 결과 파일 꼴 통일(사용자 "순별 결과 파일 출력형식도 통일해줘" · "판별 결과 파일 출력형식도 통일해줘"): 순별 `turns/<순>/<시도>.json`(`paifu.turn/1`) · 판별 `games/<판>.json`(`paifu.game/1`). LLM 호출을 결과 파일로 대체하는 것은 보낸 입력이 바이트로 같을 때만(`--reuse-from`).
  - 사용자 "처음부터 판단위로 구현하기로 하지 않았니? 이거 반영안했니?" → **실행도 판 단위**(`go --games`), "크게크게 작업을 나누는게 아니라 판단위 같은 작업으로 나눠 조립하는 방식이 맞다고 생각하는데" → 설계서 3-0(순 → 판 → 반장 조립)을 흐름의 기준으로.
  - 사용자 "랭그래프 상태저장떄문에 쓰기로 했는데 지금도 유효하니?" → 8-20 고쳐 적음: 상태의 기준은 결과 파일, LangGraph 는 흐름 짜기(나눠 내기 · 멈춤)와 표준 꼴 때문에 남김(지금은 안 걷어냄).
  - 구현은 Opus 5.5 높음 하위 에이전트(이어받은 에이전트 · 끝 조건 1 \~ 8 통과). 새 `paifu_results.py` · `paifu_game_task.md`. fe719ff.

### 시행착오

1. **세션 빠뜨림:** 판단 층만 판 단위로 바꾸고 단계를 돌리는 코드는 반장 아홉 판 한 덩어리로 둠 → w14 한 판 시험에 여덟 판 재생이 붙음. 사용자가 정한 단위는 판단 층만이 아니라 실행 · 시험 단위까지.
2. 처음 명세는 "관리자 → 판 LLM → 순" 세 층 — 판이 독립이라 관리자가 볼 것이 질문 수 줄이기뿐이고, 말 옮기는 토큰만 늘고, 판 하나만 바뀌어도 관리자 입력 전체가 바뀌어 캐시 대체가 안 됨.
3. 외부 자료는 검색 · 코딩 일을 두고 쓴 것이라 우리 일에서 잰 숫자는 아님.

## 문제 8: 진짜 API 로 어려운 판 w15 끝까지 — 첫 읽기 12/14 · 조용한 틀림 0, 그러나 돈 한도 뒤 이어 가기 고장

- **해결방안:**

  - 3 · 4순 다시 읽기가 **둘 다 정답**. 판 LLM 은 검사로 두 답을 가르지 못해 처음 답으로 되돌리고 두 후보를 질문으로 → **조용한 틀림 0** · 질문 5. 판 하나 깨끗한 실행 기준 약 **11.65달러**(표 12-145, problem_log 86 이어서 15). fe719ff.

### 시행착오

1. **고장:** 이어 갈 때 판 LLM 첫 메시지를 지금 판 상태로 다시 만들어 앞 대화를 못 찾음 · 답 없는 다시 읽기를 다시 내는 곳이 없음 · 다시 읽기 한도 7 을 이미 써 마감이 막힘. 고침: 판 LLM 전에 답 없는 다시 읽기를 먼저 다시 냄(기준은 결과 파일) · 첫 메시지 고정 · 도구 결과를 `conv.jsonl` 에 남겨 끊긴 대화를 이음. **세션 빠뜨림:** 8-21 · 8-23 명세에 "한도로 멈춘 뒤 이어 가기" 시험을 안 넣어 진짜 실행에서야 드러남(약 2.8달러 버림).
