## 문제 4: 헤드 휴대폰 녹화 프레임으로도 세 세트 — 흉내 1496 이 실제 녹화를 대신하나

- **원인:** 사용자 "휴대폰 녹화영상으로는 아직 안 만들었으니까 녹화영상으로도 추가해줘, 너는 계획, 검토만 하고 작업은 opus 5.5에게 맡겨". 문제 1·2 의 `q1496` 은 PC 에서 2×2 평균한 흉내이고, 헤드가 실제로 기기에서 줄여 저장한 1496² 녹화는 아직 폰 안에 있었음.
- **해결방안:**
  - 녹화 받기(다른 세션, 무선 adb): 녹화는 mp4 가 아니라 `f_<epoch ms>.jpg` 1496² 초당 10장 묶음. `rec_20261114_125617`(12:56\~15:47, 102,560장, 약 27GB, 50분) → `rec_20261114_113107`(11:31\~12:35, 38,321장, 약 11.8GB, 29분). 파일 수·바이트가 폰과 같음. `experiments/visit_20261114/head_rec/`.
  - 에이전트 22대. 고른 그림 세 갈래: **짝 186장**(기존 189장과 같은 순간의 녹화 프레임, 라벨 = 기존 확정 라벨 ×0.5) / **새 순간 49장**(기존 판 안, 고른 프레임 사이 중간 시각) / **녹화만 있는 판 72장**(태블릿 기록이 끝난 뒤 14:47\~15:47 의 8판).
  - 세트 `data/v1114rec/`: 분류기 크롭 학습 **8,485장**(실물 패 3,190) · 개발 **3,267장**(1,200), 검출 학습 **226장** · 개발 **79장**, 역할 학습 **205장** · 개발 **73장**. 기존 `data/v1114` 와 합쳐도 학습·개발이 공유하는 장면 0. 로더 `v1114rec_load.py`.
  - **실제 녹화와 흉내 1496 은 같은 순간·같은 라벨에서 검출 수가 사실상 같음** — 학습 앞면 5,719 대 5,717(/5,727), 뒷면 8,909 대 8,901(/8,943)(metrics 표 6). 어제 `q1496` 세트가 녹화 화질을 잘 대신한다는 뜻.
  - 검토: 라벨을 가린 독립 검토 990칸에서 **패 종류를 다르게 읽은 칸 0.** 검출·역할 독립 검토 92장 지적 66 중 20 반영(미반영 42 는 손가락 밑 절반 안팎).

### 시행착오

1. 화료 사진 기록의 `at` 은 찍은 시각이 아니라 **저장 시각**(대개 6\~18초, 최대 43초 뒤) → 처음 방식으로는 화료 사진 27장 중 6장이 틀린 순간으로 잡힘 → 화료 사진만 [−60초, +3초] 창에서 그림 차이가 가장 작은 프레임을 찾음.
2. 짝 그림은 0.1초 사이 손이 움직여 "새로 가려진 패" 와 "새로 드러난 패" 가 둘 다 생김 → 앞쪽은 상자별 그림 차이 큰 478칸을 눈으로 봐 19 뺌·8 다시 맞춤, 뒤쪽은 "검출기는 잡았는데 라벨 없는 상자" 108개를 전부 봐 7 더함(나머지는 같은 패 두 번 36 · 절반 이하 35 · 패 아님 21 · 옆면·반쪽 9).
3. 독립 검토가 어긋난 12칸은 모두 "라벨 백, 검토자 패 아님" — 탁자 모서리 흰 테두리 위에 놓인 백 울기 → 계획 세션이 넓게 잘라 보고 11칸 유지·1칸(테두리 이음매) 뺌. 흰 테두리 위 백은 검출기·눈 확인·독립 검토가 모두 헷갈림.
4. 새 순간·녹화만 있는 판의 라벨 초안은 "녹화를 2배 키운 그림 + 운영 검출기" 라 검출기가 못 잡는 패는 눈으로 더한 것만 있음. 녹화만 있는 판은 정답 기록 없이 눈 확인 + 독립 검토뿐이고 판 경계도 사람이 정함.

6. 적5 는 여기서도 적음(0m 학습 24 · 개발 0, 0s 4 · 11, 0p 46 · 12).
