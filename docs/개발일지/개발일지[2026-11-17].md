## 문제 1: 손패 기록을 재려면 정답부터 — 사용자가 확인 페이지에 적고, 첫 자동 채점은 화소 규칙 3/14 · Gemini 11/14

- **원인:** 어제까지의 시험 판 정답은 세션의 가린 읽기뿐이라, 무엇을 고쳐도 잴 수가 없었음. 사용자 "개선 방법 브리핑" → "정답부터".
- **해결방안:** 버림 하나 = 한 차례로 묶어 프레임을 넘겨 보며 적는 확인 페이지(`truthprep.py` · `truthserver.py` · `truthpage.html`). 사용자가 자동 판정 · 세션 읽기를 안 본 채 적음(계획서 "추가 8", problem_log 66번).
  - 범위: 사용자 "1반장은 연출용이라 2반장만 기록할게" → 11-14 2반장만. 3반장 쪽(n 판)도 안 적음.
  - r11 14차례: 사용자 답 ↔ Opus 5.5 둘째 읽기(답을 못 봄) 종류 14/14 같음. 이 정답으로 거꾸로 굴리면 **3번째 버림부터 매 순 손패가 하나로 복원**(`rebuild.py`).
  - 저장된 화소 규칙(11-16 값, 새로 안 돌림): 차례 전체 **3/14**, 답을 한 차례가 13 중 4뿐(표 12-24). 쯔모기리 6차례를 "모름" 으로 냄 — 이 판 화료자는 뽑은 패를 줄에 안 붙이고 쥔 채 버림.
  - 사용자 "제미나이 읽기도 시도해봐" → gemini-3.8-flash 에 차례 통째로(표 12-25, 기준은 "추가 9" 에 먼저): 종류 14/14 · 나간 칸 4/4 · 들어간 칸 2/4 · 차례 전체 12/14 → "일부". 판 하나에 입력 150만 토큰.
  - r19 · r14 정답이 생긴 뒤 지시문 그대로(표 12-26): **처음 보는 두 판 6/10**, 세 판 합 Gemini 17/24 · 화소 규칙 5/24. 판 하나가 통째로 맞은 것은 없음.

### 시행착오

1. 번호 세는 법을 사용자 제안으로 두 번 바꿈 — 들어간 칸은 "메운 뒤 번호" → **빈칸을 둔 번호**, 울기 뒤 나간 칸은 "울기 전 번호" → **뺀 뒤 다시 1번부터**. 같은 강 순서가 두 번이면 둘째에 b, "먼저 넣고 버림" 표시 추가. 모두 "그 동작 직전에 보이는 줄에서 센다" 로 모임.
2. 새로 드러난 동작: 버릴 패를 먼저 끝으로 빼 두었다가 버림(r14 2순 · r19 7순) → 정답을 패(`k_id`)와 자리(`k_pos`)로 나눠 적음(`truthnorm.py`).
3. 표 12-25 의 12/14 는 자리 기준이었음 — r11 9순 맞바꿈을 못 봐 패 기준으로는 **나간 칸 3/4 · 차례 전체 11/14** 로 고침(표 12-26).
4. r11 지시문의 참고 문구는 r11 정답을 본 뒤 쓴 것이라 그 판에 유리 — "된다" 가 아님. Gemini 틀린 둘 중 8순은 세기가 아니라 뒤 구간에 든 다음 차례의 끼워 넣기를 읽은 **차례 경계 틀림**. 확신도는 14개 모두 high.
5. 정답 24 중 고친 4건은 사용자 확인을 받았지만 읽기를 알린 뒤의 확인(가린 확인 아님).

## 문제 2: 과적합 없이 엮기 — 판독기 그래프를 고정하고 안 본 r12 · r17 에서 채점, A+B "일부" · B+C "쓸 만"

- **원인:** 사용자 "과적합되지 않고 랭그래프나 react 방식으로 문제를 해결할 수는 없을까". 판독기 하나로는 판 하나가 안 풀림.
- **해결방안:** 먼저 저장된 두 읽기(Gemini 한 번 묻기 · Opus 둘째 읽기)를 맞대 봄(`ensemble.py`, 새 호출 없음) — 둘이 갈리는 7차례 안에 Gemini 틀림 7 중 6. 다른 종류의 판독기끼리는 틀림이 덜 겹침.
  - 그래프 `pgraph.py`(계획서 "추가 10"): 판독기 A(Gemini 가 `look` 도구로 시각 범위를 불러 가며) · B(한 번 묻기) · C(Opus 에이전트 읽기 — Anthropic API 키가 없어 그래프 밖) → 리치 뒤 = 쯔모기리 규칙 → 일치면 자동 확정, 아니면 사람. 10:47 sha1 고정.
  - 안 본 r12 + r17 24차례(표 12-27): 혼자 A 20 · B 21 · C 23. **A+B 자동 21 · 조용한 틀림 2 · 사람 3(12%) → "일부" ❌. B+C 조용한 틀림 0 · 사람 3 → "쓸 만"** — 단 C 는 그래프 밖 · 비용 안 잼.
  - 사용자 "그럼 한 판에 얼마인 거야?" → 한 판(9 \~ 14차례) A + B 약 **3.3 \~ 4.4달러**, 내년부터 두 배(표 12-26 덧붙임). r12 2.92 · r17 3.17달러.

### 시행착오

1. r19 · r14 는 이미 본 판이라 그래프가 도는지 확인한 값(A+B 조용한 틀림 1 · B+C 0)일 뿐 — 시험은 새로 연 r12 · r17 만.
2. 조용한 틀림 둘(r12 2순 · r17 11순)은 본 판 r11 9순과 같은 동작 — **오른쪽 끝에 붙인 뽑은 패 둘레로 옆 패를 옮기거나 맞바꿈.** Gemini 둘이 같은 "정돈만" 으로 틀려 일치로 통과. 계획서 "조심" 에 미리 적은 걱정 그대로.
3. 차례 수는 피해를 줄여 보임 — 거꾸로 복원이라 r17 11순 하나로 뽑은 패가 9s → 4z 로 바뀌어 11차례 중 10차례 손패가 한 장씩 틀림. 모순도 정렬 어긋남도 없어 점검에 안 걸림.

## 문제 3: 패보 범위 확정 — 형식 · 재생 화면 · 점수 결과 화면 · 예시 10판 · 시작 손패 입력(앱, 커밋 전)

- **원인:** 사용자 "작혼 패보 같은 UI를 만들되 우리는 사용자 1명의 패보 + 모든 플레이어의 버린패를 기록하는걸로 하자" → **한 사람(hero)의 매 순 손패 + 네 자리 버림.** 다른 세 자리 손패 · 뽑은 패는 안 적음.
- **해결방안:**

  - 사용자 "기록기가 끝까지 돌면 점수계산해서 결과 화면 띄워줘" → 패보 재생이 끝 걸음에 닿으면 결과 화면(`paifu_score.dart`, `ResultScreen(viewOnly: true)`). r11 예시에서 리치 · 핑후 · 도라 3판 30부 3,900점 확인.
  - 사용자 "2반장 동1국 뿐만아니라 다른 대국도 기록에 넣어줘" → 예시 10판(r11 \~ r19 · r20, `paifu_examples.py`). 버림은 앱 기록기 출력 그대로(사람이 안 고침 — 표 12-29 의 남은 틀림 포함), 판 중 손패는 사용자 정답이 복원되는 r12 · r17 · r19 만.
  - 사용자 "시작 손패를 입력하면 패보에 적용해주는 기능" → `start_hand.dart`: 어느 뽑기 순서로 봐도 있는 패만 앞면(확정), 나머지는 뒷면 + 후보. 정답 있는 네 판에서 **다 정해진 순 24/47 · 확정 패가 정답과 어긋난 것 0**(표 12-35).

## 문제 6: 칸 상태 모형(사용자 제안) — 정답 형식 · 검산으로 남기고, LLM 출력을 동작 목록으로 바꾼 F 는 ❌
