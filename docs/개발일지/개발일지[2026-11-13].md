## 문제 1: 유국 창의 텐파이 자리를 사람이 일일이 체크함 — 헤드 사진으로 미리 켜기

- **원인:** 유국 창은 리치 자리만 미리 켜져 있음. 유국 때는 텐파이한 사람만 손패를 눕혀 공개하니 앞면 판정으로 미리 체크할 수 있을 것 같았는데, 테스트 세트(B·C·D + 10-31 + 11-07)에 유국 공개 사진이 한 장도 없음 — 매장 촬영이 전부 화료 버튼.
- **해결방안:** 테스트 원본 36장으로 합성 216장을 만듦(화료자 손패 줄을 다른 자리 방향으로 돌려 눕히고, 화료자 자리에는 세운 손패 줄). 지금 화료자용 규칙(1등 넓이의 1/2 이상)은 179/216 → 펠트 사각형을 0.05 넓힌 바깥을 지우고 절대 문턱 500px 로 보면 **207/216**, 자리 855/864. 유국 창에 반영: 창은 바로 열고 헤드 새 프레임 한 장을 판정해 **사람이 아직 안 누른 자리만** 텐파이로 켬(확정은 사람). 테스트 763 통과. 실제 유국 사진으로는 아직 못 잼.

### 시행착오

1. 합성할 때 처음엔 손패 칸의 픽셀 덩어리로 손패를 잡았는데 패산·팔까지 잡음 → 이미 있는 패 상자 라벨로 바꿈. 붙인 줄에 탁자 흰 테두리가 딸려 와 쐐기 모양이 생겨, 옮기는 화소를 패 상자 안으로 제한.
2. 비율을 빼고 절대 문턱만 쓰면 203/216. 남은 오탐을 합성 잔여물로 의심했지만 칸을 잘라 보니 아니었음 — 손패 칸이 사진 끝까지라 자동탁 흰 테두리 속 검은 홈·화면이 "흰 바탕 속 무늬" 로 세어진 것(노텐 자리인데 1,163px). 화료 때는 화료자 넓이가 훨씬 커서 비율 규칙에 묻혀 있던 잡음.
3. 펠트 밖을 그대로 지우면 노텐 오탐은 0 이지만 펠트 끝에 걸친 공개 손패까지 지움 → 사각형을 0.05 넓힘. 남은 9장은 팔이 펠트 끝을 가린 장면 등.
4. 사용자가 Projection Mahjong 논문(MTAP 2026, 유국 때 자리마다 미공개 / 노텐 / 텐파이 3분류)을 보고 반영을 물음 → 매장은 노텐을 엎는 사람과 세워 두는 사람이 섞여 있어 **앞면 여부만** 보기로 하고 분류기는 새로 학습하지 않음. 공개한 손패가 진짜 텐파이인지는 논문처럼 안 봄.
5. 기록을 켜면 유국마다 프레임·판정·사람이 확정한 값을 `<시각>_draw/` 에 남김 → 매장에서 모이면 이것으로 채점.

## 문제 2: 헤드 사진 양옆에 사람 몸이 많이 찍힘 — 1:1(정사각형) 촬영

- **원인:** 사용자 "양옆 사람 몸이 덜 나오게 정사각형만 찍고 싶다". 헤드는 4:3(4080×3060)이라 탁자 양옆 띠에 앉은 사람이 들어옴.
- **해결방안:** 테스트 40장(46회)을 잘라 서버 단독으로 비교. 지금 거치 높이 그대로 자르면 운영 모델 46 → **41/46**(모서리 울기가 정사각형 밖으로 잘림), 탁자 전체가 들어오게 거치한 것으로 흉내 내면 **46/46·606/606** 으로 원본과 같음. S25 Ultra 의 1:1 출력은 2992×2992 뿐이라(3060 없음) 2992 로 줄여 다시 재도 46/46. 헤드 앱바에 1:1 토글을 넣음(기본 끔) — 켜면 스트림 2992×2992 초당 15.2장 확인. 화소가 25% 적어 서버 판독은 0.87 → 0.73초.

### 시행착오

1. 134815 는 울기가 정사각형 안에 있는데도 놓친 줄 알았음 → 상자 좌표를 찍어 보니 x=3060 경계에 걸려 있었음. 분류 문제가 아니라 전부 잘림.
2. 첫 흉내는 사진 밖을 회색으로 채웠더니 울기에 白 이 더해짐(白 채우기가 회색 띠를 흰 패로 봄) → 정사각형을 사진 안으로 밀어 넣고 모자라는 곳만 어둡게 채워 다시 잼.
3. 사용자 "추적이랑 겹쳐 보기도 1대1로 가능하니?" → 추적의 강 장수 어림이 1:1 에서 **4/3 배**로 부풂. 패 한 장 크기를 4:3 사진 비율로 박아 둔 탓 → 프레임 비율을 넘기게 고쳐 4:3 과의 차가 중앙 3.87 → 0.12장. 리치봉 홈은 1:1 997 에서 55/56, 1496 에서 56/56(지금 1020 은 53/56).
4. 태블릿 배경이 새로 찍기 전까지 1:1 프레임을 4:3 틀로 잘라 보여 주고 있었음 → 미리보기 비율 그대로 그리고 "격자를 다시 맞추세요" 안내.
5. 사진을 잘라 만든 흉내라 실제 1:1 헤드 사진으로는 안 잼. 안 배운 조합 모델은 45 → 43/46(134815 는 원본부터 울기가 사진 끝에 붙어 있어 흉내 몫으로 봄).

## 문제 3: 자체 판독 모드에서 펠트를 못 찾으면 자동 맞추기가 늘 실패

- **원인:** 사용자 "자동 맞추기 자체 판독일 때는 못 쓰는데 서버 없이 태블릿에서 시도할 수 있게". 자동 맞추기는 펠트 네 모서리 → 실패하면 서버 `/v2/setup`(Gemini) 순서인데, 자체 판독 모드는 서버를 아예 막음(11-12). 격자가 안 잡히면 판 상태 추적도 안 돎. 매장 핫스팟엔 인터넷이 없음.
- **해결방안:** 서버에 이미 있는 탁자 기준점(가운데 기기, 없으면 패산)과 축 평행 격자를 기기 판독의 새 종류 `localsetup` 으로 붙임 — 새 모델·규칙 없음. 테스트 40장(PC, 같은 코드): 격자 **40/40**, 그 격자로 읽은 화료자 자리 답이 저장 격자 때와 40/40 같음(둘 다 32/40), 0.31 / 0.34 / 0.44초.

### 시행착오

1. 저장 격자와 선 차가 중앙 59\~74/1000 로 커 보였지만, 장면 격자가 손으로 그린 것이라 선의 뜻이 다름. 격자가 판독에 영향이 없는 것은 아닌지 대조로 150 밀어 보니 손패가 빠짐 → 비교는 유효.
2. PC 에서 돌릴 때 같은 폴더의 기기용 `onnxruntime` 대리 모듈이 먼저 잡혀 실패 → 그 폴더를 `sys.path` 맨 뒤로.
3. 대국 시작 직후(강이 없어 패산으로 잡아야 함)·태블릿 시간은 안 잼.

## 문제 4: 헤드를 놓은 자리가 판독에 맞는지 알려 주는 것이 없음 — 거치 점검

- **원인:** 사용자 "추가할만한 기능있을까" → 후보 일곱 중 "거치점검 넣어줘". 판독 실패 가운데 거치 탓이 있음(카메라가 밀려 손패 잘림, 문제 2 의 모서리 울기 잘림). 헤드 폰은 아래를 보고 있어 화면을 못 보니 태블릿에서, 인터넷 없이 돌아야 함.
- **해결방안:** 색만 보는 펠트 판독에 "펠트가 사진 변에 닿은 비율" 을 더해 셋을 판정 — 탁자 전체(5% 이상 닿으면 나쁨)·기울기(6° / 15°)·패 크기(펠트 한 변 2150 / 1600px). 문턱은 추측하지 않고 480장(40장 × 원본 + 변형 11종)에 점검을 돌려 저장된 판독 결과와 맞대 정함. 탁자 전체: 괜찮음 그룹 틀림 0/75·나쁨 3/44. 기울기: 괜찮음 2/112·주의 12/82·나쁨 56/76. 점검 104ms(노트북). 테스트 777 통과, 태블릿 설치. 실제 헤드 프레임에서의 판정은 헤드가 끊겨 못 봄.

### 시행착오

1. ❌ 처음 기준 "흰 테두리까지 사진 안" 은 원본 39/40 을 나쁨으로 봄. 실제 매장 거치는 펠트가 사진 세로의 89\~93% 라 테두리가 늘 밖인데 운영 모델은 다 읽음. 문제 2 의 "탁자 네 모서리까지" 를 4:3 에도 그대로 옮긴 탓 — 실패는 펠트가 사진 변에 닿은 사진에서만 났음.
2. 기울기 문턱을 예전 표대로 3°·10° 로 잡았다가 구간별로 세어 보니 3\~6° 0/41, 6\~10° 6/42, 15° 이상 56/76 → 6°·15° 로.
3. 패 크기 0.6배는 예전엔 "위험" 이었지만 지금 운영 모델로는 3/38 → 주의로 내림. 나쁨(1600px 미만)은 잰 적 없는 선이라고 적어 둠.
4. 원근 항목도 넣었다가 B·C·D 가 다 읽혀서 뺌. 자동 맞추기 때 12MP 디코딩을 한 번 더 하게 돼(태블릿 약 2.4초) 펠트 읽기와 합침.
5. 커밋할 때 다른 세션의 변경이 같은 파일에 섞여 있어 내 덩어리만 올림. `git apply --unidiff-zero` 가 검사를 통과하고도 한 줄 어긋나게 넣어 analyze 오류 218개 → 인덱스를 직접 만들고, 인덱스만 내보내 analyze·test.

## 문제 5: 유국으로 남은 리치봉 — "홈에 그대로 둔다" 는 가정이 매장과 달랐음

- **원인:** 10-30 에 넣은 "전판 유국으로 남은 봉은 이번 판 리치 증거로 안 쓴다" 는 봉이 그 자리 홈에 그대로 있다고 가정. 사용자 "유국 했을 때 리치봉을 그대로 끼워 두는 게 아니라 가운데로 모아 둔다". 옛 가정대로면 봉 주인이 다시 리치해 화료했을 때 진짜 리치를 버릴 수 있었음.
- **해결방안:** 가운데 봉이 헛 리치를 만드는지부터 봄 — 10-31·11-07 추적 프레임에서 가운데 봉 95장 헛 리치 0, 가운데 봉 + 왼쪽 홈 새 봉 11장은 왼쪽만 잡음. 사용자 "가운데로 고정" → 설정 없이, 병합에서 남은 봉 의심을 빼고 홈의 봉은 모두 이번 판 리치로. 테스트 760 통과, 작업 트리(커밋 전).

### 시행착오

1. 그림 번호와 프레임 번호를 같다고 보고 한 장을 "가운데 봉" 으로 잘못 짚음 — 그림을 보니 위 홈 안의 봉이었고 판정이 맞았음.
2. 사용자 "니가 직접 테스트 해볼래?" → 실제 프레임을 추적기에 흘려 보니, 유국을 **먼저 누르고** 봉을 나중에 옮기면 새 판 추적이 홈에 남은 전판 봉을 리치로 잡음. 추적 쪽 거르기(`riichiExcept`)까지 지운 것이 잘못 → 되살림.
3. 추적기는 한 번 잡은 리치를 판 끝까지 다시 안 봐서, 봉을 옮긴 사람이 다시 리치해도 못 잡음 → 처음부터 꽂혀 있던 봉이 홈에서 2프레임 빠지면 리치를 풀고 다시 지켜봄.
4. 처음 설명에서 약점으로 든 "같은 자리 연속 리치를 추적이 못 잡는다" 도 옛 가정에서 나온 말이었음.
5. 두 날·장면 4개·봉 1개뿐. 봉 2개 이상 겹침·실제 유국 직후는 매장 몫.

## 문제 6: 내일 매장 구성으로 2시간을 버티나 — 1시간 무충전 시험

- **원인:** 매장은 헤드 폰 핫스팟(인터넷 없음)·헤드와 태블릿 둘 다 충전 없음·헤드 1:1 녹화·태블릿 자체 판독 + 실시간 보기로 2시간 안팎. 어제 발열을 줄인 뒤 "충전 없이 배터리" 가 남아 있었음.
- **해결방안:** 기기 안에 셸 기록기(30초마다 배터리·발열·녹화 장수)를 띄우고 연결 없이 약 1시간. 헤드 **시간당 21.3%p**·발열 단계 2·녹화 42,652장 버림 0, 태블릿 10.5%p·단계 0·핫스팟 끊김 0·실시간 보기 초당 3.7장·지연 0 → **2시간은 버팀, 헤드는 80% 이상에서 시작.** 코드는 안 바꿈.

### 시행착오

1. 헤드를 노트북 USB 에 꽂으면 충전이 되고, 노트북을 핫스팟에 붙이면 세션이 끊김 → 기기 안 기록기로 재고 나중에 붙어 읽음.
2. 헤드 어두운 화면이 꺼진 채 저장돼 있었고, 태블릿은 헤드를 회사 와이파이 주소로 잡고 있었음(매장엔 없는 주소) → 둘 다 매장 전 확인 목록에.
3. "카메라 헤드 찾기" 가 핫스팟에서 두 번 다 실패. 처음엔 "듀얼 와이파이" 라고 잘못 설명했다가, 노트북과 묶인 **Wi-Fi Direct**(무선 adb 용)로 바로잡음 — 끊으니 찾음. 코드에서 왜 못 찾는지는 안 팜.
4. 사용자 "실시간 보기 속도 왜 줄어들었는지 확인해봐"(어제 8.4 → 3.7장): 헤드 아님(노트북에서 받으면 요청 16ms), 태블릿 부하 아님(겹쳐 보기를 꺼도 5.2장), 유력하다고 말한 Wi-Fi Direct 도 끊은 뒤 2.8장이 나와 결정적이지 않음 → 남는 것은 헤드 핫스팟 2.4GHz 링크. 5GHz 로 바꿔도 2412MHz 그대로라 확정 못 함. 지연 0·추적 3초 간격이라 기능 문제는 아님.
5. 책상 위 빈 면을 찍었고 도중에 렌즈가 가려져 판독 정확도는 안 잼. 측정 뒤 내가 메뉴를 닫으려 보낸 "뒤로" 가 태블릿 앱을 홈으로 내보냄(다시 띄움).

## 문제 7: 패보를 다시 꺼냄 — 계획서만 씀

- **원인:** 사용자 "겹쳐보기로 버린 패 순서를 기록 가능하니" → "토요일 녹화로 패보 가능하지 않을까" → "시작·끝 손패만 있으면" → "시작 손패에 숫자를 매겨 추적하면" → "쯔모기리는 AI 한테(LangGraph), RAG 는" → "매 순 평가, 체스닷컴 탁월수 같은 기능". 패보는 11-09 에 미구현으로 정한 것.
- **해결방안:** `docs/paifu_review_plan_1113.md` 로 정리(코드·측정 없음, 만들지는 미정). 패보를 네 수준으로 나눔(버림 순서 / + 쯔모기리 / 본인 손패 매 순 / 네 명). 위 카메라는 세운 패의 면을 못 봐서 시작·끝 손패로는 뽑은 패의 종류만 정해지고, 순서는 손패 칸을 따라가는 "번호 잇기" 가 안 끊겨야 함. 순서는 "먼저 재고, 그다음 만든다" — 내일 녹화 한 번으로 버림 채점·쯔모기리 눈 판정·번호 잇기 끊김 세기.

### 시행착오

1. AI 에이전트로 통째로 맡기지 않기로 함 — 버림·패 읽기·번호 계산·조립은 코드, 쯔모기리 판정만 AI. 주 흐름은 고정 순서, AI 에게 도구를 주는 것은 애매한 건을 다시 볼 때만. 첫 시험은 프레임워크 없이 스크립트로.
2. RAG 는 판정에는 넣지 않음(찾아올 문서가 없는 영상 판정). 맞는 자리는 패보가 쌓인 뒤의 복기 도우미.
3. 플레이 평가는 본인 손패만 있으면 됨. 탁월수는 "패효율로는 손해인데 종합 판단으로는 최선" 이라 패효율 층만으로는 실수로 찍힘.
