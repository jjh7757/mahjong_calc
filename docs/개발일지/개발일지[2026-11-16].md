## 문제 3: 패산 위 표시패가 2장(깡도라)이면 한 장만 읽음 → 옆으로 나란히 뒤집힌 패를 더함

- **원인:** r03(동 깡)의 패산 위 표시패는 5만·6만인데 앱 기록은 5만 1장. `read_wall` 이 "옆에 뒷면이 가장 많이 붙은 앞면 패" 를 점수순으로 세워 **1등 한 장만** 돌려줌(6만은 바로 옆 2등, 확신 0.95).
- **해결방안:** 사용자 "깡도라 읽기부터". 첫 장 옆으로 "한 줄 · 패 한 장 간격 · 같은 크기 · 줄 두 끝 바깥이 뒷면" 인 패만 더함(`local_read.wall_run`) — 첫 장 고르는 코드는 안 건드림. 11-14 패산 위 2장 사진 **0/3 → 3/3**, 첫 장 25/25 그대로·헛 추가 0. 테스트 세트 40장면 첫 장 40/40 그대로 + 20261031_165614 에서 동을 새로 읽어 정답(백·동)과 같아짐. 서버 pytest 220 통과(metrics 표 1-170, problem_log 63번).

### 시행착오

1. 처음엔 문제 2 의 역할 모델 약한 곳과 묶어 "역할 모델 몫일 수 있다" 고 봄 → 같은 사진을 다시 읽으니 역할 모델은 두 장 다 패산 표시패로 불렀고 `read_wall` 은 역할 모델을 안 씀.
2. 테스트 세트 181209 에서 안깡(뒷면·적5삭·5삭·뒷면)의 적5삭이 더해짐 — 깡도라 줄과 같은 모양 → 뒷면이 한 칸에서 끝나는 짧은 줄에 같은 패 2장이면 안 더함. **테스트 사진을 보고 넣은 조건**이라 테스트 세트의 헛 추가 0 은 깨끗한 평가가 아님.

## 문제 4: 동시 론(더블 론)에서 표시패 짝이 기록에서 빠짐 → 리치한 화료자끼리 같이 쓰기

- **원인:** r05 는 더블 론의 둘째 화료자 기록. 화료자를 읽고 나서야 아는 흐름(앞면 손패 2자리 → 자동 더블 론)에서는 짝 찾기가 "미리 아는 화료자" 일 때만 불려 **모든 화료자의 짝이 비었음.** 모델이 아니라 앱 규칙이 없던 것.
- **해결방안:** 사용자 "더블 론일 때 표시패를 같이 쓰는 앱 규칙부터 넣고 학습 계획 세워". `table_reader.dart` `sharedPair` — 화료자가 둘 이상이면 리치한 화료자에게 같은 짝을 줌(화료자 중 누구의 자리 띠에 있어도 됨), 리치 아닌 화료자에게는 안 줌. 테스트 2개(고치기 전 코드에서 실패 확인, r05 실제 응답 포함), analyze 깨끗·test 783 통과(4ae484d, problem_log 64번).

## 문제 6: 리치 → 일발 쯔모인데 일발이 빠짐 — 원인 둘, 둘 다 고침

- **원인:** 사용자 "편집영상 33분22초 부근에 일발이 빠졌어 원인 분석해줘"(11-14 2반장 동4국 1본장). 일발은 화료 사진으로는 알 수 없어 판 중 추적에만 기댐. 프레임 재생으로 둘을 찾음.
  - ① **리치봉 상자가 어긋남** — 11-14 일지 문제 2 그대로. 봉이 14프레임 찍혔는데 픽셀 판정 0번.
  - ② **격자를 맞춰도 울기 픽셀 추적이 일발을 지움** — 울기 추적 모서리 칸이 사진 끝까지라 **탁자 흰 테두리**가 칸의 절반. 노출이 조금 흔들려도 흰 면이 패 1.4\~2.4장 분량 바뀌어 "울기 늘어남" 으로 찍힘(아무도 안 운 판 3분에 11번).
- **해결방안:** 사용자 "둘 다 고치기"(앱 84e8959, problem_log 65번, metrics 표 10-2·11-3).
  - ① 펠트 없이 자동으로 맞춘 격자만, `FeltWatch` 가 처음 기준을 잡을 때 그 펠트로 만든 격자와 **리치봉 상자 중심**을 견줘 30 이상 어긋나면 다시 맞춤. 손으로 맞춘 격자는 안 건드림.
  - ② 울기 추적 칸을 펠트 안쪽으로 자름 + 일발 조건에 "리치 뒤 네 자리 버림 합 3장 이하".
  - 그 뒤 사용자 지적으로 **겹쳐 보기 판정으로 바꿈**(`lib/table/call_watch.dart`): 리치봉이 처음 보일 때·확정될 때 겹쳐 보기 판독을 한 번씩 돌려 기준(강 상자 수·자리별 강·울기 상자)을 잡고 화료 사진을 한 번 더 읽어 견줌. 자체 판독이 되는 기기에서만, 아니면 픽셀 그대로.
  - 재생 결과: 11-14 리치 추적 6/16 → **13/16**(2반장 0/8 → 6/8), 그 판 일발 ✗ → ✓. 테스트 10-31·11-07 은 리치 12/19 그대로, 헛 "울기 늘어남" 235 → 24. 겹쳐 보기 판정은 재생 30구간에서 참 3 모두 예·거짓 2 모두 아니오. analyze 깨끗, test 806.

## 문제 7: 패보 — 화료자 세운 손패 번호 잇기 → 🗑 접음, 그 뒤로도 적은 비용 판정을 더 재 봄

### 시행착오

1. 사용자가 헷갈린 대조표 두 장면을 바로 읽음 — r18 3순은 뽑은 패를 왼쪽 두 장 사이(3번째 칸)에 넣고 벌어진 틈을 양손으로 모은 것, n03 은 맨 끝에 붙였다가 그 패를 다시 버린 쯔모기리. 판정 둘은 다 틀림. 내가 "손이 덮어 영상으로는 못 가른다" 고 설명한 것이 틀렸음 — 걸림돌의 일부는 판정자의 읽기.
2. 사용자 "패보 하나 확인하는데 토큰 너무 많이 소모되면 실패한 서비스" → 픽셀 추적. v1 은 떨어뜨려 둔 뽑은 패 틈을 빈칸으로 세는 등 거의 다 틀렸고 두 판을 보며 v5 까지 다듬음 — 시험이 아니라 과적합 위험이 큼.
3. 검출기 상자로 바꾸자 나빠진 것을 "손 근처에서 한 장씩 놓친다" 고 짚음 → 사용자 "이건 색 덩어리 방식도 똑같은 거 아냐?" → **틀린 설명.** 화료자의 체크무늬 소매가 줄을 덮은 순간이었고 손 표시가 피부색만 봐서 못 잡음. 색 덩어리는 소매까지 패로 세어 우연히 멀쩡해 보였을 뿐.
4. "장수가 바뀐 깨끗한 프레임만 그림으로" 는 Sonnet 이 18차례 모름 — 장수가 바뀌는 순간은 거의 늘 손 밑.
5. 사용자 제안(안 잼): 겹쳐 보기 판독을 판 상태로 쌓아 "새로 생긴 한 장 = 이번 버림" 으로 찾기. "두 번 이상 보인 뒤에만 확정하면 순서가 꼬일 가능성" 도 사용자가 짚음.
6. 헤드 녹화가 1496 으로 줄여진 JPEG 낱장인 것을 사용자가 지적 — "일부러 너가 압축시킨 거야, 카메라 헤드 파일 따로 압축 지시 내린 적 없는데"·"왜 영상이 아니라 사진으로 저장한 거야?". 2×2 축소·낱장 저장은 헤드 녹화를 만들 때 내가 묻지 않고 정한 것. 동영상 인코딩 대안은 "지금은 두기". 원자료 화질을 줄이는 결정은 먼저 묻기로 함.
