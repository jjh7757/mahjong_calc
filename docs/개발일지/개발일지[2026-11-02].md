## 문제 1: Gemini 판독이 느리고 꼬리가 김

- **원인:** 운영 85d152f 에서 자리 판독 10.3 / 17.7 / 60.1초, 장면 전체 15.1 / 18.6 / 62.1초. 꼬리는 Gemini 생각 토큰이 정함. 공개 검출기는 라이선스 문제로 운영에 못 쓰고, 서버엔 GPU가 없음(t4g.small 2 vCPU).
- **해결방안:** 우리 사진으로 검출기(YOLO26n)·분류기(MobileNetV3 Small)를 직접 학습하고 onnxruntime 만으로 서버에서 돌림 → 운영 33f60ee + 앱 1c3eaf4, 장면 5.82 / 6.42 / 7.30초, Gemini 호출 0. 해결됨(자동 반영은 기본 끔으로 출발).

### 시행착오

1. 서버 응답에 단계별 시간을 넣고 넓은 구역 판독을 3번 → 1번 읽기로 줄임(85d152f 배포) → 호출 6 → 2, 속도는 그대로.
2. 자체 YOLO26n 1회차 → 처음 12/37이 나왔는데, 평가 코드가 세운 손패를 뒤집어 읽어 三을 二로 읽던 버그였음. 고친 뒤 "자체 먼저, 안 되면 Gemini" 26/37(Gemini 단독 25/37). 틀 잡기 실패는 대부분 장수 검사에서 떨어짐.
3. 1회차 검출을 눈으로 고친 라벨로 2회차 학습 + 틀 규칙 추가.
4. 운영과 같은 t4g.small 임시 컨테이너에서 onnxruntime 만으로 잼 → 사진 통째 검출 0.69 / 0.91 / 1.02초, torch판과 답 31/31 같음.
5. 강 끝·표시패도 자체 모델로 → 강 끝 Gemini와 같은 33/34, 자리당 0.19초(Gemini 3자리 한 호출 7.2초). 강 패는 뒤집혀 놓이기도 해 0°·180° 둘 다 읽고 확신 높은 쪽을 고르게 함(이게 11-08 3만 → 2만 오독의 통로가 됨).
6. 운영에서 그림자 판독(자체 모델로도 읽어 응답에만 실음)을 켬 → 넓은 구역 전처리가 +2.5초 늘어 끔. 메모리 최대 1054MB를 그림자 탓으로 봤는데 꺼도 1051MB라 원인을 잘못 짚은 것이었음. 대신 노트북에서 저장 사진으로 평가하는 도구를 만듦.
7. 운영 33f60ee 배포 뒤 앱 흐름 → 5.82 / 6.42 / 7.30초. 그런데 130743 리치를 놓쳐 2900점(정답 5800)으로 틀린 자동 반영 1건 → 자동 반영 기본 끔.
8. 분류기 실제 확률을 확신도로 쓰고 틀 실패 때 白을 코드로 채움 → 나눔 모델 앱 흐름 27/34 → 30/34(운영 Gemini도 30/34).

## 문제 2: 도라 표시패 정답이 11/19로 낮음

- **원인:** 처음엔 Gemini 읽기 문제로 보고 자체 모델 추가 학습을 검토함. 또 `dora_box` 가 null 인 걸 보고 "매장에서 왕패 경로가 안 쓰였다"고 결론 냈는데, 그 필드는 고정 구역 값이었음. 호출 기록으로 보니 25장 중 24장이 왕패 경로를 불렀음. 재생 값과 매장 당시 값을 섞어 본 실수.
- **해결방안:** 사용자 제안대로 판마다 상자를 들고 있지 않고, 화료 사진에서 자체 모델로 표시패를 찾는 `/v2/localdora` 를 만듦 → 운영 4a23391 배포. 리치 아닌 화료는 해결됨, 리치 화료 표시패는 진행 중.

### 시행착오

1. 사용자 지적("프레임 사진으로 테스트하면 된다")으로 추적 프레임 30장에서 패산 위치를 찾음 → 학습 없이 "앞뒤에 뒷면 색이 붙은 앞면 패" 규칙으로 29/30(0.16초), Gemini 29/30(6.35초).
2. 화료 원본 19장 → 리치 아닌 화료는 자체·Gemini 모두 9/9. 리치 화료 표시패는 자체 5/10이라 그쪽은 일단 Gemini 경로 유지.

## 문제 3: 판독 구역 격자를 설치 때마다 손으로 맞춰야 함

- **원인:** 안 맞추면 틀린 점수로 자동 반영됐고(25/34, 틀림 3), 카메라가 밀린 뒤 안 고치면 41.2초에 손패 5장이 틀림. Gemini 자동 맞추기는 패가 올라오기 전엔 0/10.
- **해결방안:** 모델 학습 대신 색으로 초록 펠트의 네 모서리를 찾아 격자를 계산(`felt_grid.dart`) → 앱 반영(36d157b), 앱 흐름 29/34·틀린 자동 0, 처음 맞추기 2.3초·서버 호출 0. 해결됨(실기기·다른 매장 확인 전).

### 시행착오

1. 펠트·기기 모서리 8점을 YOLO26n-pose 로 학습(캐글) → 프레임 2,259장이 사실 설치 8곳뿐이라 설치 단위로 나눠 평가. 독립 평가 세션이 내가 맞다고 본 기기 점 142/271장이 반사광으로 어긋났음을 찾음. 모델이 펠트 점을 1.3\~3% 틀려(패 폭 약 2.2%) 미채택.
2. 색 + 곧은 변으로 펠트 찾기 → 앱 흐름 30/34(사람이 맞춘 격자와 같음), 자동 반영 10 → 13, 카메라 이동은 약 18초 뒤 자동 복구.
3. 사용자 "과적합 아니니" → 안 본 삼각대 15장은 통과 10 중 틀림 3, 밝기를 반으로 줄이면 26 중 7이 틀린 채 통과. "못 찾으면 서버로 넘어가 나빠지지 않는다"던 설명이 틀린 채 통과하는 경우를 빼먹은 것이었음.
4. 사용자 제안 "상한·하한으로 모두 아우르는 고정 격자" → 앱 흐름 28/34·틀린 자동 2. 미채택.
5. 펠트 색을 사진에서 재고 변 바깥 띠를 검사하게 고침. 첫 구현은 펠트 색상 76을 98로 잡는 버그가 있었음 → 고친 뒤 틀린 통과 15 → 1, 어두운 사진 7 → 0, 앱 흐름 29/34·틀린 자동 0.
6. 사용자 "다른 테이블은 못 맞추는 거 아니니" → 다른 탁자 사진은 전부 거절·0/12. Gemini 자동 맞추기는 이 탁자에서 26/35(펠트 33/35)지만 다른 탁자 4장 중 3장에 격자를 냄 → 펠트 → Gemini → 손 순서로 잇기로 함.
