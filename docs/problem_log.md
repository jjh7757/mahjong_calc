# 문제·해결 기록 (이력서 재료)

이 문서는 이력서에 쓸 재료로 관리한다. 모델·도구 이름을 나열하지 않고, **어떤 문제를 어떤 제약 아래서 어떻게 풀었고 무엇이 바뀌었는지**를 적는다.
항목마다 아래 칸을 채운다. 새 문제를 만나거나 새 방법을 시도하면 항목을 더하고, 결과가 바뀌면 숫자를 고친다.

| 칸 | 적을 것 |
| --- | --- |
| 문제와 제약 | 무엇이 안 됐나. 데이터 양·품질 기준·시간·비용·장비 같은 제약 |
| 검토한 대안 | 선택지들과 각각을 버린 이유 |
| 선택과 근거 | 무엇을 골랐고 왜. 가능하면 근거가 된 숫자 |
| 평가 방법 | 평가 데이터를 어떻게 만들었고(정답은 누가 어떻게), 몇 번 반복했나 |
| 발견한 오류 → 개선 | 평가에서 드러난 오류 유형과 그에 맞춘 수정 |
| 변화 | 정확도·시간·비용·검수(사람이 고쳐야 하는 양)의 전후 숫자 |
| 운영·남은 것 | 배포 뒤 운영에서 한 일, 아직 안 된 것 |

상태: ✅ 해결 · 🔧 부분 해결 · ❌ 미해결 · 🗑 폐기. 자세한 숫자의 원본은 `experiments/vlm/RESULTS.md`(10/22), `experiments/field_20261024/NOTES.md`(10/24 이후 전부), `HANDOFF.md`(현황).

## 0. 프로젝트 한눈에

- **무엇:** 리치마작 점수 계산 앱(Flutter, Android). 1단계는 패를 손으로 넣어 점수를 내는 계산기, 2단계는 **테이블 위에 고정한 카메라로 화료 장면을 한 장 찍으면 손패·울기·도라·방총자·리치를 읽어 점수까지 자동으로 내고 대국 기록에 반영**하는 것. 국내외에 "손패 사진 → 점수" 앱은 많지만 테이블 전체 판독 + 기록 자동화는 상용 제품이 없었다(시장 조사 `docs/market_research.md`).
- **기간·역할:** 2026-10-22 시작, 1인 프로젝트. 기획·제품 결정·현장 실험(매장 촬영, 수요 확인)·정답 검수를 직접 하고, 구현은 AI 코딩 도구를 지휘해 진행했다. *(이력서에 쓸 때 본인 표현으로 고칠 것)*
- **제약:**
  - 학습용 라벨 사진이 없다(실제 패 사진 0장에서 시작). GPU 없음(서버는 EC2 t4g.small, CPU).
  - **품질 기준이 가혹하다:** 점수가 맞으려면 손패 13~14장 전부, 울기, 도라 표시패, 쏘인 사람, 리치 여부가 모두 맞아야 한다. 한 장만 틀려도 점수가 틀린다.
  - 사용자는 터치 없는 자동화를 원한다 → 틀린 결과를 사람이 고치게 하는 것 자체가 비용이다.
  - 비용·속도: Gemini 호출당 수 센트, 분당 호출 수 제한(운영 20회), 한 장면을 수 초 안에 끝내야 테이블에서 쓸 수 있다.
- **지금 결과(2026-10-25):** 같은 장면 반복 10/10, 서로 다른 장면(손으로 찍은 사진) 점수 정답 9/12, 장면당 7~20초, 장면당 약 $0.01~0.04. 자리 판독에 확대·참고 그림 도구를 붙이면 손패+울기 정답 60% → 90%(로컬 실험). 한 호출에 확대 토막 + 참고표를 넣으면 같은 시간에 50% → 95%(로컬 실험, 16번).

## 이력서 문장 초안

*(아래는 기록을 바탕으로 쓴 초안. 숫자는 본문과 같다.)*

- 사진 1장으로 마작 화료 장면(손패·울기·도라·방총자·리치)을 읽어 점수와 대국 기록까지 자동화하는 파이프라인을 설계·구현. 라벨 데이터 없이 시작해 VLM 기반으로 노선을 정하고, 촬영 조건·구역 분할·호출 설계를 바꿔 가며 장면 정확도를 20%(매장 1차) → 75%(장면 5개 재측정)로 올림.
- 라벨 사진이 없는 제약에서 합성 데이터 YOLO 와 VLM 을 같은 평가 세트로 비교해 VLM 을 선택. "모델보다 패가 몇 px 로 찍히느냐가 정확도를 가른다"는 것을 실험으로 확인해, 전경 대신 원본에서 구역을 잘라 보내는 구조로 바꿈.
- 위치 찾기 호출(장면당 18~27초, 결과가 호출마다 흔들림)을 없애고 사용자가 한 번 맞춘 격자로 칸마다 동시 호출하도록 재설계. 한 장면 60~70초 → 7~20초, 호출 수를 줄이면서 정확도는 올림(9칸 6/12 → 5구역 9/12).
- 모델이 통수·삭수 개수를 세다 틀리는 오류에 대해, 프롬프트 규칙(효과 없음, 18/24 vs 19/24)과 "확대 + 실물 참고 그림을 돌려주는 도구 호출"(효과 큼, 18/30 → 27/30)을 같은 조건으로 비교해 방향을 정함.
- 장면 지연을 호출별로 쪼개 "가끔 생기는 긴 모델 추론"이 원인임을 찾고, 모델 교체·추론 설정 대신 입력 설계(한 호출에 원본 해상도 확대 토막 + 실물 참고표)로 같은 시간에 자리 판독 정확도를 50% → 95%로, 동시 요청 경주로 장면 p90 지연을 35초 → 8초(시뮬레이션)로 줄임.
- 평가 체계를 직접 만듦: 촬영마다 정답 파일이 남는 흐름, 방식·높이·줌별 집계 스크립트, 같은 사진 반복 측정으로 "호출마다 흔들리는 오류"와 "진짜 못 읽는 오류"를 구분.

## 1. 인식 엔진 선택: 학습 모델이냐 VLM 이냐 ✅

- **문제와 제약:** 실제 패 사진이 0장. 기획은 자체 학습 YOLO 였지만 학습 데이터를 만들 수 없는 상태. 품질 기준은 "손패 13~14장 전부 정답".
- **검토한 대안:**
  1. 합성 데이터로 YOLO 학습 — 합성 사진은 잡지만 실제 매장 패에 전혀 전이되지 않음(패 글꼴·색·조명이 다름). 실제 사진 300장 라벨링이 전제.
  2. Gemini Pro — 합성 손패 패 단위 90.4%, 지연 평균 31초(최대 83초).
  3. Gemini 3.8 Flash — 패 단위 91%, 지연 17초, 적도라 12/12.
- **선택과 근거:** Flash + thinking low. 합성에서는 손패 전체 정답 4~5/12 로 부족해 보였지만, **촬영 조건을 맞춘 실제 사진(눕힌 손패를 위에서)** 3장은 13/13·14/14·13/13 전부 정답, 7~11초. 결정적 변수가 모델이 아니라 촬영 조건임을 확인하고 노선을 정함. 점수 계산은 기기 안 Dart 엔진이 하고 AI 는 사진만 읽게 해 모델 오류가 계산 규칙에 섞이지 않게 함.
- **평가 방법:** 합성 12장(156패, 기울기·원근·블러 포함) + 실제 사진 3장(정답은 직접 판독). 같은 입력으로 모델 3종 비교.
- **발견한 오류 → 개선:** 오류는 거의 전부 "개수 세기"(6통→4통, 6삭↔8삭). 글자 패는 안 틀림. 이 특성이 이후 모든 개선의 출발점.
- **변화:** 라벨링 300장 작업을 없앰. 서버에 GPU 불필요(CPU 인스턴스 유지).
- **운영·남은 것:** YOLO 코드 제거. 기록 `experiments/vlm/RESULTS.md`.

## 2. 패가 작으면 못 읽는다 → 전경 대신 구역 크롭 ✅

- **문제와 제약:** 테이블 전경 사진(패 한 장 50~75px)은 거의 못 읽는다. 서버는 긴 변 1568px 로 줄이고, Gemini 는 보낸 해상도와 관계없이 이미지를 일정 토큰 수로 줄여 본다 → 크게 보내도 소용없음.
- **검토한 대안:** 전경 그대로 / 해상도만 올리기 / 앱이 원본에서 구역을 잘라 보내기.
- **선택과 근거:** 방송·게임 캡처로 패 크기별 정확도를 재 **모델 입력에서 패 한 장 100px 이상**이 경계임을 확인. 앱이 12MP 원본에서 구역을 잘라 보내고, 거치 높이는 60~70cm(또는 2배 줌)로 안내.
- **발견한 오류 → 개선:** 격자로 바꾼 뒤 자리 구역이 커서 다시 패가 작아짐(4삭 안깡을 8삭으로 4/4 오독). 1568→3200px 로 올려도 동일 → Gemini 이미지 해상도 수준을 ULTRA_HIGH(토큰 약 +1.1k)로 올려 2/2 정답. "패 부분만 꽉 맞춰 자르기"는 흰 테두리 위 울기가 잘려 폐기.
- **변화:** 전경 0% → 구역 크롭에서 손패 100%(조건 충족 시).

## 3. 구역을 어떻게 찾나: 위치 찾기 호출 → 고정 구역 → 사용자 격자 ✅

- **문제와 제약:** 전체 판독에는 손패·강·왕패·울기의 위치가 필요. 카메라는 고정이지만 매장마다 다르다.
- **검토한 대안:**
  1. 서버 locate(모델이 상자 반환): 18~27초로 한 장면 비용의 절반, 호출마다 흔들려 울기·왕패 상자를 자주 놓침 → 장수 부족으로 계산 실패(10/24 매장 실패의 최대 원인). 생각 수준을 올려 모서리 퐁 3/3 으로 나아졌지만 불안정.
  2. 고정 구역: 첫 locate 를 재사용하고 움직임(펠트 IoU)·화료자(뒷면 비율)·도라(흰 덩어리)를 픽셀로 판정. locate 생략으로 10초대 가능했지만 넓힌 크롭에서 오독, 장수 안 맞으면 되돌아가야 함.
  3. 사용자가 선 4개를 한 번 맞추는 격자(사용자 제안): 모델 의존 없이 칸을 나눠 동시 호출.
- **선택과 근거:** 격자. 같은 사진 10회 반복 10/10, 7초. 모델이 "어디"를 찾게 하지 않고 "무엇"만 읽게 하는 쪽이 안정적이었다.
- **평가 방법:** 같은 사진 10회(흔들림 측정) + 서로 다른 장면 5개(일반화 측정).
- **변화:** 한 장면 60~70초 → 7~20초. 위치 찾기 호출 비용 제거.
- **운영·남은 것:** 격자는 기기에 저장, 앱에서 선을 끌어 조정. locate 는 격자를 끈 경우에만.

## 4. 격자를 얼마나 잘게: 9칸 → 5구역 ✅

- **문제와 제약:** 9칸(손패 칸·모서리 칸 분리)은 도라 표시패가 칸 경계나 손패 옆에 놓이면 어느 칸에도 안 들어가 못 읽음(장면 C·E), 가운데 기기 상자까지 맞춰야 함.
- **검토한 대안:** 9칸 유지 + 예외 처리 / 자리 4개(손패 + 그 사람 오른쪽 모서리, 바람개비) + 가운데의 5구역(사용자 제안).
- **선택과 근거:** 5구역. 자리 하나를 한 호출로 읽어(앞면 여부·손패·울기 전부·따로 놓인 패) 경계 문제가 사라지고 맞출 선이 4개로 줆.
- **평가 방법:** 장면 5개 × 사진 2장 × 2회, 완전 자동(화료자 지정 없음).
- **변화:** 점수 낼 수 있는 장면 B·C·D 6/12 → **9/12**.
- **기록:** 그림 `experiments/field_20261024/zones_proposal_*.png`

## 5. 손패와 울기를 나눠 보낼까 🔧

- **문제와 제약:** 자리 구역이 커 먼 자리 손패가 작다. 나누면 패는 커지지만 호출이 는다.
- **평가 방법:** 같은 장면·조건으로 통째 vs 나눠(각 12회).
- **결과:** 나눠 8/12, 통째 9/12. 먼 자리 손패는 좋아졌지만(A·E 0/4 → 4/4·3/4) 손패 칸만 보내면 오른쪽 손패를 "앞면 아님"으로 답하고(16회 중 14회), 없는 패(5통)를 지어냄. 호출·토큰 30~50% 증가.
- **선택:** 기본은 통째. 나눠 읽기는 옵션. 고정 카메라 사진에서 재검토.

## 6. 화료자(눕힌 손패) 찾기 🔧

- **문제와 제약:** 네 자리 중 누가 손패를 눕혔는지 사람 입력 없이 알아야 한다(터치 없는 자동화).
- **검토한 대안:** locate 답(흔들림) / 픽셀(뒷면 연보라 비율) / 모델에게 네 자리 모두 묻기.
- **선택과 근거:** 픽셀 먼저(0.1초, 무료), 못 정하면 네 자리를 모두 읽어 모델의 "앞면" 답으로, 그래도 안 되면 사용자에게 묻기.
- **발견한 오류 → 개선:** 문턱 0.03 에서 아래 자리 0.029 가 앞면으로 잡혀 후보 2명 → 0.01 → 격자 칸은 넓어 0.004. 왼쪽 자리는 칸에 패산 더미가 늘 들어가 앞면이어도 넘음(장면 C·E) → 모델 답으로 보완해 자동으로 맞춤.
- **변화:** C 0/4 → 3/4(자동). 대신 못 정한 장면은 호출 6 → 10, 입력 토큰 2배.
- **남은 것:** 연보라 뒷면 기준은 이 매장 자동탁 것. 다른 탁자는 기준 재조정.

## 7. 울기 판단 오류 ✅

- **문제:** 도라 표시패 3장(4통4통7만)을 울기로, 옆자리 모서리의 발 퐁을 화료자 울기로 붙임.
- **개선(순서대로):** 퐁·치·깡 모양이 아닌 묶음은 울기에서 빼 도라 후보로 → 울기는 화료자 오른쪽 것만 → 화료자 오른쪽 모서리는 위치 찾기와 무관하게 늘 따로 읽기.
- **변화:** 갤러리 10장 점수 정답 3 → 4 → 5/10. 5구역에서는 모서리가 자리 구역에 포함돼 규칙이 자연히 흡수됨.

## 8. 도라·뒷도라 구분 ✅ (안 하기로)

- **문제:** 모델이 둘을 사용자 기준과 반대로 읽는다.
- **선택과 근거:** 구분하지 않고 보인 표시패를 모두 도라 표시패로 센다. 리치 화료면 점수가 같고, 아닌데 짝으로 보이는 경우는 드물다. 오류 가능성을 없애기보다 영향이 없는 쪽으로 규칙을 바꾼 결정.
- **현장 관행 반영(2026-10-26):** 사용자가 매장에서 보니 리치 화료면 화료자가 도라·뒷도라 표시패를 자기 손패 옆으로 가져가 계산하고, 리치가 아니면 왕패에 그대로 둔다. 지난 사진 기록(리치 장면 C·E·10/24 매장은 손패 옆, 리치 없는 D 는 가운데)과도 맞았다. → 표시패를 "가운데 먼저" 고정으로 읽던 것을 **리치면 손패 옆 먼저, 아니면 가운데 먼저**로 바꿈(다른 쪽은 비었을 때만). 깡이면 도라 2장·뒷도라 1장처럼 홀수일 수 있어 짝 검사는 넣지 않음(사용자 결정). B·C·D 2회씩 점수 12/12·틀린 반영 0(리치 장면 C 는 손패 옆 7만·6삭으로 16000). 이 세트에서는 리치 장면의 가운데가 비어 있어 예전 규칙과 결과가 같았다 — 리치인데 가운데에서 엉뚱한 패를 읽는 경우를 막는 장치. 도메인 규칙을 사람(현장)에게서 얻어 판독 경로에 넣은 사례.

## 9. 리치 판정 ✅

- **문제:** 강의 가로 패(리치 선언패)는 프롬프트·스키마 4가지로도 0/6.
- **선택과 근거:** 자동탁 가운데 홈의 리치봉을 보게 프롬프트를 고쳐 6/6 → **리치는 리치봉만** 본다. 못 읽는 신호 대신 잘 읽히는 신호로 판단 근거를 바꿈.
- **남은 것:** 10/24·25 사진의 파란 막대가 실제 리치봉인지 확인(아래·위 두 자리로 읽힘).
- **발견한 오류 → 개선(2026-10-30):** 리치봉만 보면 전판 유국으로 남은 봉을 이번 판 리치로 읽고, 다른 사람 화료 때 1000점을 또 걷는다(사용자 지적). 대국 기록에 봉 주인을 남겨 그 자리만 다른 신호로 정한다. 사용자 결정: 그 경우에만 강의 눕힌 패를 보고, 사람에게 묻지 않는다. 모델 판독은 0/6 이었지만 YOLO 틀의 모양(가로가 세로의 1.15배 넘음)으로는 있음 14/16·없음 24/24(metrics 표 3-1, 처음엔 정답 표에 B 왼쪽 2통이 빠져 있어 "헛 잡음"으로 잘못 셌다 — 그림을 보고 고침). 강 전체를 믿을 수 있을 때만 "없음" 으로 치도록 패 수 검사를 더했다(1장만 잡힌 강 → 모름 → 확인). 이어서 상자를 그려 보니 놓침 2(비율 1.12)와, 한 패가 두 상자로 쪼개진 숨은 헛 잡음을 찾아 서버 판정을 비율 1.05 + 높이 0.6~0.8 + 겹침 제외로 고침 → 있음 16/16·없음 24/24(개발 세트로 정한 값이라 매장에서 다시 잴 것).

## 11. 지연 편차 🔧

## 13. 모델이 통수·삭수 개수를 틀린다 🔧

- **문제와 제약:** 남은 오류의 대부분(9삭↔6·8삭, 5통↔4통, 7삭↔6삭). 만수·자패·적도라·울기 모양은 거의 안 틀림. 멀리 작게 찍힌 자리에서 심함.
- **검토한 대안과 결과(같은 평가 세트, 같은 조건):**
  1. 프롬프트에 "손패 + 울기(깡은 3장) = 13장" 규칙: 규칙 있음 18/24, 없음 19/24. 장수 오류(패 빠짐)는 2 → 1 로 줄었지만 숫자 오독은 그대로. **효과 없음.** 화료패가 없는 장면은 평가에서 제외하고 "없을 수 있다"는 고지도 넣지 않은 조건.
  2. 패 종류별 참고 그림을 프롬프트에 항상 붙이기: 작게 찍힌 패에는 정보가 없고 비용만 늘 것으로 보고 보류.
  3. **"확대 + 실물 참고 그림" 도구:** 매장 사진에서 잘라 눈으로 확인한 패 그림(36종 205장)을 모아 두고, 모델이 헷갈리는 위치와 후보를 넘겨 부르면 그 부분을 원본 해상도로 키운 그림과 후보 패의 실물 그림을 돌려줌(멀티모달 함수 응답, 최대 3번). 참고 그림은 시험 장면이 아닌 다른 장면 것만 써 부풀림을 막음.
- **변화(장면 5개 × 2장 × 3회):** 손패+울기 정답 **18/30 → 27/30**, 손패만 19 → 29/30. 쉬운 장면은 도구를 거의 부르지 않음(0.5회). 시간 중앙값 9.5 → 13초, 입력 토큰 약 6.6배(2.9k → 18.9k).
- **보강 실험:** 참고 그림 205 → 293장(4삭 7장 포함)으로 늘려 두 번 다시 재도 24/30·24/30. 세 번 합쳐 도구 있음 75/90(83%), 없음 18/30(60%). 남은 실패는 4삭 안깡(앞면 2장만 보이고 작음)과 7삭→6삭으로, 참고 그림 수보다 작게 찍힌 패 자체의 한계.
- **실패 원인 분석:** 도구 있음 실패 15건을 모델이 실제로 받은 확대 그림과 함께 다시 봄. 거의 모두 **정답 정보는 원본 사진에 또렷이 있었다** — 참고 그림 부족이 아니라 모델이 도구를 쓰는 방식의 문제.
  - 확대 범위가 패를 자름(7건): 모델이 준 상자가 안깡 패의 위쪽 절반만 덮어 4삭 윗줄(막대 2개)만 보고 2삭으로 답함.
  - 확인을 안 함(5건): 틀린 7삭은 한 번도 확대하지 않음(첫 판독을 확신).
  - 후보에 정답이 없음(1건): 9삭을 확대해 놓고 후보를 [6s, 9p] 로 넘겨 9삭 그림을 못 받음.
  - 장수 2건, 구조(도라를 울기로) 1건 — 후자는 앱 규칙이 걸러냄.
  - → 모델 판단에 맡기던 것을 코드가 정하게 세 가지를 넣고 같은 조건으로 다시(30회):
    - **상자 넓히기(사방 50%):** 효과 분명. 울기 26 → 29~30/30(4삭 안깡 해결), 장면 A 3 → 5/6.
    - **후보 자동 확장(같은 수패 ±3):** 이득 없음. 손패 27 → 25, 참고 그림이 늘어 오히려 헷갈림, 토큰 1.5배.
    - **통수·삭수 확인 강제(2단계 판독):** 틀린 3건 중 2건을 고쳤지만 맞던 4건을 망침("고쳐라"는 지시가 과잉 수정을 부름). 시간·토큰 2배.
    - 합계: 24/30 → 25/30(세 가지 모두) · 24/30(확인 강제 뺌) · 22/30(상자만). 상자만으로는 안깡이 안 풀림 — 모델이 후보에 4삭을 빼먹어, 안깡은 상자 넓히기 + 후보 확장이 함께일 때만 풀렸다.
  - **평가의 함정:** 같은 계열 조건 6번이 22~27/30 으로 흔들려 30회로는 조건 차이가 우연과 구별되지 않았다. 6번을 합쳐 도구 있음 146/180(81%) vs 없음 18/30(60%) 로 판단.
  - **다수결(추가 호출 없이 기존 결과로 계산):** 같은 사진을 3번 읽어 패마다 다수결하면 도구 있음 81% → 89%, 도구 없음 60% → 70%. **실전 채택 안 함:** 호출마다 흔들리는 오류만 고치고 실전에서 문제인 체계적 오류(작게 찍힌 패를 늘 같은 쪽으로 틀림)는 못 고치는데, 모든 촬영의 비용이 3배. 대신 "화료 형태가 안 되거나 장수가 틀릴 때만 다시 읽기"와 "불확실한 패 표시", 근본적으로는 촬영 조건(고정 거치) 쪽으로.
  - 멀고 기울어진 자리(E)의 삭수는 어떤 조건에서도 같은 쪽으로 틀려 다수결로도 안 풀림 → 촬영 조건(높이·줌)으로 풀 문제.
- **운영·남은 것:** 로컬 실험만(`experiments/tile_tool/`). 서버 반영 여부 결정 전. 참고 그림은 이 매장 패 세트 것이라 다른 세트는 다시 만들어야 할 수 있음.

## 16. 시간은 그대로, 정확도는 50% → 95%: 한 호출에 "전체 + 코드가 자른 확대 토막 + 참고표" 🔧

- **문제와 제약:** 13번의 도구 방식은 정확도를 올렸지만 왕복 때문에 느리고(중앙 13~28초) 입력 토큰이 6~16배. 장면 시간은 가끔 수십 초가 걸리는 호출 하나가 정했다. 새 사진 없이 지금 사진(장면 5개 × 2장)으로 풀어야 했다.
- **원인 측정:** 한 장면의 호출 6개를 동시에 보내 호출별로 지연·토큰을 기록. 호출 대부분은 3~6초이고, 느린 호출은 전부 **모델의 생각 토큰이 많았던 호출**이었다(생각 0 → 4~6초, 3.7k → 40초). 같은 설정에서도 호출마다 0~3.8k 로 흔들림. 생각을 끄는 설정은 이 모델에서 무시되거나 거부됐다.
- **검토한 대안(같은 평가 세트, 조건마다 30~60회):**
  1. 생각 수준·예산·출력 상한 조절 — 끌 수 없음, 상한은 생각까지 잘라 답이 깨짐(7/30).
  2. 모델 교체 — 빠른 모델(생각 없음)은 3.5초로 안정적이지만 정확도 10/30 이하. 상위 모델(Pro)도 10/30. 공간 인식 특화 모델은 한 장면만 풀고 느림. **어느 모델이든 먼 자리의 같은 패를 같은 쪽으로 틀림** → 모델이 아니라 입력(패가 작게 보임)의 문제.
  3. **한 호출에 확대 토막 넣기:** 코드가 자리 사진을 세 토막(폭 40%, 겹침)으로 잘라 원본 해상도로 전체 사진 뒤에 붙이고, "무늬 개수는 토막에서, 장수·위치는 전체에서" 라고 역할을 나눔. 도구 방식에서 모델이 확대할 곳을 잘못 고르던 문제(13번 실패 분석)를 코드가 늘 전부 확대하는 것으로 없앰.
  4. 이 패 세트의 통수·삭수 1~9 실물 참고표 한 장 추가(시험 장면의 패는 빼고 만듦).
  5. 참고표를 전체 34종(만수·자패·적5 포함)으로 — 60회씩 나란히: 통수·삭수만 56/60, 전체 50/60(ULTRA_HIGH 로 보내도 52/60). 칸이 작아져 안깡을 오독하고, 해상도를 올려도 "앞면 아님" 오류가 늘었다. 틀리지 않는 패의 참고 그림은 도움이 아니라 방해 → 틀리는 종류만 보여 준다.
  6. **다른 패 세트의 정면 사진 한 장으로 만든 표** — 무늬 색·1삭 모양이 다른 세트인데 56/60, 매장 패 표는 같은 시각 55/60(누적 93%), 표 없음 47/60. 표는 "이 패 세트의 모습" 이 아니라 "무늬 개수·배치를 세는 기준" 으로 쓰인다 → 매장마다 표를 다시 만들 필요가 없어 운영 부담이 사라짐.
- **선택과 근거:** 3 + 4. 지금 방식 30/60(50%) → **57/60(95%)**(다시 재 56/60, 합쳐 113/120), 시간 중앙 6.8 → 6.4초 그대로. 토막만 50/60(83%), 참고표만 18/30. 토막을 기본 해상도로 보내면 18/30 이라 "토막의 해상도 수준"이 결정적. 생각 없는 모델은 같은 입력에서도 15~16/30 → 정확도는 생각에서 나오고, 꼬리 지연은 그 대가.
- **꼬리 지연:** 생각 길이는 못 줄이므로 요청 방식으로 다룸. 자리 호출의 27%가 10초를 넘어 "늦으면 하나 더(헤지)"는 두 번째도 늦을 확률이 높다 → **처음부터 두 개를 보내 먼저 온 답(경주)**. 실측 지연 분포로 1만 번 시뮬레이션: 장면 p90 34.6초 → 8.3초, 중앙 8.2 → 6.0초.
- **덤 — 비용 없는 다시 읽기:** 경주는 답이 둘이라, 먼저 온 답이 코드 검사(앞면이고 13~14장)에 걸리면 다른 답을 쓴다. 95.0% → 97.9%. 지금 방식에서는 효과 없음(오류가 장수는 맞는 숫자 오독) — 입력을 고쳐 오류 유형을 바꾼 뒤에야 검사가 쓸모 있어짐.
- **평가 방법:** 정답은 사진을 직접 보고 정한 손패·울기(13번과 같은 세트). 손패와 울기가 모두 맞아야 정답. 1등 조건과 기준 조건은 60회씩 두 번 나눠 재 재현 확인. 지연은 호출별 실측 분포에서 뽑아 시뮬레이션.
- **변화:** 자리 판독 정확도 50% → 95%(경주+검사 98%), 장면 시간 p90 34.6 → 8.3초(시뮬레이션), 입력 토큰 장면당 약 2.7배.
- **덤 2 — 틀린 답은 늦게 온다:** 손패를 "앞면 아님" 으로 비운 오답은 전부 25~47초(생각이 길어진 호출). 경주는 먼저 온 답을 쓰므로 이런 오답을 저절로 거른다.
- **남은 실패 분석 → 수정(60회씩):** 모델의 생각 요약을 받아 원인을 확인.
  - "앞면 아님"(손패를 통째로 비움): 비스듬한 사진에서 눕힌 패의 연보라 두께를 보고 "세워져 있다" 며 프롬프트의 "세워져 있으면 false" 를 적용 → 정의를 "그림이 보이면 true" 로. **오류 12/300 → 0/120.**
  - 토막마다 따로 읽어 적게 하는 스키마: 모델이 생각을 아예 하지 않게 되어 꼬리 지연은 사라졌지만(최대 42 → 17초) 숫자 오독이 늘어 52 → 47/60. 출력에 적는 단계가 생각을 대신하면 생각만큼 고치지 못한다 → 버림.
  - 애매한 규칙(도라 표시패를 적을지) 정리: 생각이 길어진 호출이 그 고민을 하고 있었지만 정리해도 꼬리는 그대로 → 원인이 하나가 아님.
  - 앞면 정의 + 규칙 정리: 52 → **55/60**.
- **경주의 함정:** 먼저 오는 답은 생각을 덜 한 답이라 숫자를 더 틀린다. 경주가 정확도를 올린 것은 느린 "앞면 아님" 오답을 걸러서였고, 그 오답을 프롬프트로 없애자 경주는 정확도를 약간 내주고(91.7 → 88.8%) 시간만 사는 장치가 됐다. 한 수정이 다른 장치의 효과를 바꾸므로 조합마다 다시 재야 한다.
- **100% 에 가깝게(시간은 그대로):** 정확도 목표를 "틀린 채 자동 반영되는 비율"과 "사람에게 묻는 비율"로 나눠 설계. 코드 검사(텐파이·화료 형태)가 남은 오류의 60%를 잡고, 3번 동시에 읽어 검사를 통과한 답 둘이 일치하면 반영·아니면 확인 질문 → 자동 반영 95%, 틀린 채 반영 2%, 확인 5%, 장면 시간 중앙 7.2초(한 번 읽기 6.4초). 만장일치로 하면 틀린 채 반영 0% 대신 확인 17%. 호출을 4번으로 늘리면 우연한 오답 일치가 늘어 오히려 나빠짐 — 남은 오류는 "가끔 같은 쪽으로 틀리는" 패라 투표만으로는 0 이 안 된다.
- **서버에 넣고 앱 흐름으로 재 봄(만장일치판, 20회):** 앱 기준 틀린 채 자동 반영 0, 점수 정답(B·C·D) 9/12 → 11/12. 그러나 자리 판독만 보면 만장일치인데 틀린 답 2회(E 3삭→2삭, 세 요청 모두) — 따로 잰 60회로 한 시뮬레이션은 요청끼리 독립이라 가정했는데, 같은 순간 보낸 요청은 같은 쪽으로 틀릴 수 있었다. 이번엔 앱의 장수·화료 형태 검사가 막았다 → "여러 번 읽기"와 "규칙 검사"는 서로를 대신하지 못하고 겹쳐야 한다. 대신 장면 시간 중앙 18.6초로 느려짐(세 답을 다 기다림, 화료자를 못 정한 장면은 12호출).
- **판독 실패를 규칙으로 메우기:** 강 끝 판독이 가끔(1.4%) "강 없음" 으로 답해 화료패를 못 찾고 계산이 막혔다. 다시 읽는 대신, 손패가 한 장 모자랄 때 대기패를 계산해 "못 읽은 자리가 하나·대기패가 하나" 면 그 자리가 그 패로 쏘였다고 정하고, 아니면 후보만 묻게 함. 저장된 판독으로 다시 합쳐 B·C·D 점수 11/12 → 12/12, 추가 호출·시간 0. 모델 출력을 다시 받지 않고 도메인 규칙(대기패)으로 빈칸을 채운 사례.
- **평가 세트 정리:** 점수까지 정답을 매길 수 없는 사진(화료패가 사진에 없는 A·E)을 평가에서 빼고 B·C·D(6장)로 다시 집계. 지금 방식 75% → 확대 토막만 96%, 토막 + 참고표 93~94%. 참고표의 이득은 거의 다 빠진 먼 자리 몫이었다 — 평가 세트 구성에 따라 "효과 있음"의 결론이 바뀐다. 먼 자리 + 화료패가 있는 사진을 새로 모아야 한다.
- **운영·남은 것:** 로컬 실험만(`experiments/speed/`). 서버에서 토막·참고표·경주를 하면 앱은 바뀌지 않는다. 참고표는 다른 패 세트 것으로도 같은 효과(6번) → 표 하나로 매장 공용. 손으로 찍은 10장 기준이라 고정 카메라에서 재확인 필요.

## 17. GPU 없이 공개 YOLO 모델 재검토 ⏸ (Gemini 만 쓰기로, 학습 데이터가 쌓이면 다시)

- **문제와 제약:** VLM 은 호출마다 돈·시간(중앙 6.4초, 꼬리 46초)이 들고 결과가 흔들린다. 처음에 YOLO 를 버린 이유는 "학습 사진이 없다" 였는데, 그 사이 남이 실제 사진으로 학습해 공개한 모델이 생겼다. GPU 는 없다.
- **검토한 대안:** 공개 모델 중 가장 최신(2026-07, 구역 분할 → 패 검출 → ResNet-50 분류의 3단 구조, YOLO26)과 손패 사진용 YOLO11(2025-09) 두 개를 학습 없이 CPU 로. YOLO11 은 첫 시험 뒤 사용자 판단으로 접음.
- **평가 방법:** 평가 세트 B·C·D(사진 6장, 사용자 결정)에서 Gemini 와 같은 정답(화료자 손패 + 울기)으로 찾은 장수·남는 패·통째 정답·시간.
- **변화(측정):** 사진당 0.2~0.7초(Gemini 보다 10~30배 빠름, 호출 비용 0). 패 단위로는 85~92% 를 찾지만 손패 통째 정답은 0~1/6(Gemini 34/36, 94%).
- **발견한 오류:** 남는 패 대부분이 오독이 아니라 크롭 안의 손패 밖 진짜 패(도라·옆 패) — VLM 은 "손패만" 을 문맥으로 고르지만 검출기는 보이는 것을 다 센다. 분류 자체는 강하고, 실패는 검출 단계(먼 자리, 겹친 구역의 중복)와 학습 패 세트 차이(적5).
- **하이브리드(YOLO 먼저, 검사 통과만 반영, 실패는 VLM):** 손패 줄 고르기 + 장수·텐파이 검사. 자동 반영 0~1/6, **틀린 채 반영 0**. 넘어간 11건 중 8건은 검출 누락·중복으로 장수가 안 맞았고 3건은 진짜 오독을 텐파이 검사가 잡음 → **검사는 안전장치로 충분하고 병목은 검출**.
- **역할을 바꿔 — YOLO 를 판독기가 아닌 검증기로:** 지금 서버는 VLM 을 3번 동시에 불러 만장일치를 본다(비용 3배). VLM 1번 + YOLO26 과 "모순 없음"(YOLO 가 본 패가 전부 VLM 답 안에 있음)이면 반영, 모순이면 VLM 2번 더 → 저장된 VLM 판독 36회로 시뮬레이션. **VLM 호출 3 → 2회(⅓ 절약), 자동 반영 87%·틀린 반영 0 그대로.** 시간은 못 줄임(엇갈리면 추가 호출이 순차라 꼬리가 길어짐, p90 25 → 38초). 검출 누락이 치명적이던 단독 판독과 달리, 검증기는 놓친 패를 모르는 것으로 둘 뿐이라 약점이 덜 드러난다. 다만 엇갈린 3/6장은 전부 YOLO 쪽 오류(조각 크롭 중복 등)였고, 틀린 VLM 답도 그 사진에 있어 "YOLO 가 틀린 답을 거르는 힘" 은 아직 검증되지 않음.
- **구역 나누기를 맡김(사용자 조작 없애기):** 사용자가 첫 촬영마다 선 4개를 맞추던 격자를, YOLO26 구역 모델이 첫 사진에서 정하게 함(강·리치봉 = 가운데, 자리마다 손패·울기 상자, 선은 그 사이 한가운데). 앱 판독 흐름 그대로 재니 자리 판독 12/12·틀린 반영 0·점수 10/12(수동 11/12·6/6), 사진당 0.6초. 실패 2회는 격자 내용이 아니라 **수동 격자에 맞춰 둔 픽셀 앞면 판정 기준값**이 바뀐 구역에서 어긋난 것(오른쪽 자리를 앞면으로 봐 방총자 강을 안 읽음) — 자동화 한 단계를 바꾸면 그 단계에 맞춰 둔 다른 기준값이 드러난다.
- **단독 판독 개선:** 실패를 단계별로 쪼개 보니 분류기는 강하고 **검출 전 단계(각도·구역)가 대부분**이었다. 손패 윤곽 기울기 보정, 구역 마스크, 색(펠트 위 흰 면) 후보를 만들어 **정답 없이 장수·텐파이 검사로 후보를 고르기** 등을 넣어 B·C·D 통째 정답 2/6 → 3/6. 탁자가 40° 기운 매장 거치 사진(평가 세트 밖 참고)에서는 같은 개선이 손패 재현율 64 → 87%·통째 0/18 → 9/18 로 크게 효과를 냈지만, 축에 맞춰 찍은 B·C·D 에서는 24각도 검색이 B 의 강을 손패로 골라 오히려 나빴다 → 사진 구도에 따라 맞는 방법이 다르다.
- **운영 서버에서 시간(2026-10-26):** 운영과 같은 EC2 t4g.small(arm64 2코어·2GB)에서 onnxruntime 만으로 — 격자 자동 설정 5.1초(구역 모델 1번 1.0초 × 5), 검증기 한 자리 2.8초(패 0.6 + ResNet-50 14장 2.1), 최대 메모리 약 440MB. 처음엔 분류기를 14장 한 번에 돌려 700MB 상한에서 OOM → 나눠 돌림. 격자는 카메라 고정 뒤 한 번이라 5초면 충분, 검증기는 Gemini 와 동시에 돌리면 시간에 안 보이지만 2코어를 다른 앱과 나눠 쓴다.
- **사양을 올리기 전에 모델을 가볍게(int8, 2026-10-26):** 정적 양자화(보정은 평가 밖 사진). 처음엔 출력층까지 양자화해 확신도가 0 으로 뭉개져 아무것도 못 찾았고(좌표·확신도가 한 텐서), 정사각형 고정 입력이 가는 손패 크롭을 여백 속에 작게 넣어 패를 1~2장만 찾던 것(앞 서버 측정에도 숨어 있던 문제)도 발견해 직사각형 입력으로 고침. 패 모델은 int8 에서 무너져(일치 37%) fp32 로 두고 구역·분류기만 int8 — 구역 상자 일치 86%, 분류 일치 92%, 끝까지 손패 70/78(fp32 64/78). 서버: 격자 자동 설정 5.1 → 3.7(직사각형) → **1.75초**, 검증기 2.4 → **0.9초**, 최대 메모리 443 → 216~272MB — **사양을 안 올려도 지금 컨테이너 상한(512MB) 안에 들어간다.**
- **결정(사용자):** 지금은 Gemini 만 쓰고, YOLO 는 우리 촬영 기록이 학습 데이터로 쌓이면 다시 검토. 공개 모델은 판독 정확도에서 VLM 에 못 미치고, 보조 역할(격자 자동·검증기)의 이득은 작은데 라이선스 위험이 있다. 속도 이득(판당 17초 → 약 1.5초)은 검출기가 혼자 읽을 만큼 정확할 때만 생긴다 — 그 조건을 만드는 건 모델이 아니라 데이터.
- **모델 키우기 검토:** 공개 가중치는 전부 nano(이전 커밋의 다른 모델도 nano), 학습 코드·데이터 비공개 → medium 은 우리 사진으로 직접 학습해야 함.
- **운영·남은 것:** 로컬 실험(`experiments/yolo/`). 가장 쓸 만한 것은 구역 자동 설정과 검증기. 단독 판독이 의미 있으려면 우리 사진(촬영 기록 label.json)으로 미세 조정해야 한다(무료 GPU). 라이선스 확인 결과(`docs/license_check.md`): HaseLab 모델은 라이선스 표기 없음, Ultralytics 는 학습한 모델까지 AGPL-3.0·SaaS 는 Enterprise 라는 입장 → 운영에 넣으려면 HaseLab 허락이 먼저이고, 상업 서비스라면 AGPL 이 아닌 도구로 만든 우리 모델이 가장 깔끔하다. 회신 전에는 운영에 넣지 않는다.

## 18. 화료자를 픽셀로 못 정해 네 자리를 다 읽음 ✅

- **문제와 제약:** 화료자(손패를 눕힌 자리)를 기기에서 픽셀로 먼저 정해야 그 자리만 읽는다. 기준은 자리 구역의 연보라(뒷면) 비율이었는데, 왼쪽 자리처럼 패산이 같이 들어가면 앞면이어도 비율이 넘어 못 정했고(장면 C), 구역이 넓어지면 엎은 자리가 앞면으로 통과하기도 했다(자동 격자 D). 못 정하면 네 자리를 모두 3번씩 읽어 Gemini 호출이 2배가 넘는다. 기기 안(isolate)에서 수십 ms 로 끝나야 한다.
- **검토한 대안:** (1) 뒷면 비율 기준값 조정 — 6장의 값이 겹쳐 가를 수 없음(C 앞면 0.026 vs 엎은 자리 0.011~0.033). (2) 흰 면 비율 — 테이블 흰 테두리가 섞여 무의미. (3) YOLO 로 판정 — 앱에 모델을 넣지 않는다는 원칙. (4) **패 면의 무늬**: 앞면 패는 흰 면 안에 검정·빨강·초록 무늬가 갇혀 있고, 흰 테두리·연보라 패산·엎은 손패에는 갇힌 구멍이 없다.
- **선택과 근거:** (4). 흰 덩어리에 갇힌 흰색 아닌 구멍의 넓이를 자리별로 재고(가장자리에서 흰색 아닌 칸을 채워 닿지 않은 칸), 뒷면 비율로 한 자리가 정해지고 무늬도 있으면 그대로, 아니면 무늬 1등이 2등의 2배 이상일 때 그 자리. 못 정하면 예전처럼 네 자리 읽기(틀린 자리를 고르는 것보다 비용이 드는 쪽이 낫다).
- **평가 방법:** Python 으로 먼저 특징을 확인(B·C·D 6장 화료자 1등, 2등과 2.5배 이상)한 뒤, 앱 Dart 코드를 실제 축소본에 그대로 돌려 수동·자동 격자 12/12, 그다음 에뮬레이터 앱 흐름과 서버 로그로 요청 수를 확인.
- **변화:** 화료자를 한 자리로 정한 비율 8/12 → 12/12(C 0/4 → 4/4, 자동 격자 D 두 자리 → 한 자리). C 한 판 Gemini 호출 18 → 8회. 점수 12/12 그대로. 판정 시간 에뮬레이터 0.24 → 0.40초. 시간(벽시계)은 거의 그대로 — 동시 호출은 가장 느린 것이 정하고, 원래 화료자(먼 자리) 판독이 가장 느렸다. 이득은 비용.
- **운영·남은 것:** D 는 1·2등 차가 1.9배(2등이 앞면 울기 3장)라, 울기가 많은 장면에서 뒷면 비율도 실패하면 무늬로도 못 정할 수 있다. 무늬 기준은 이 매장 패(흰 면·검은/빨강/초록 무늬) 기준.

## 19. 장수 힌트로 Gemini 생각 시간 줄이기 ❌ (빨라지지 않음)

- **문제와 제약:** 장면 시간은 가장 느린 호출이 정하고, 느린 호출은 Gemini 가 가끔 생각을 수천 토큰 하는 것(끌 수 없음). 경주·출력 상한은 쓰지 않기로 함(사용자) → "정보를 더 줘서 고민을 덜게" 만 남음.
- **가설:** 기기가 센 장수(손패 쪽 앞면 N장, 울기 묶음 M개)를 프롬프트에 넣으면 먼 자리 장수 세기 고민이 줄어 꼬리가 짧아진다.
- **평가 방법:** 기기 세기 코드를 만들기 전에 **정답 장수를 힌트로** 넣어 효과의 상한부터 봄(완벽한 힌트로도 안 빨라지면 만들 필요가 없다). 서버 /v2/seat 와 같은 조건(확대 토막 3 + 참고표 + v3a), B·C·D 자리 크롭 60회씩, 같은 시간대에 나란히(`experiments/speed/bench.py seat --cond v3a_now,v3a_hint`).
- **변화(측정):** 힌트 없음 / 있음 — 정답 56/60 → 59/60, 시간 중앙 5.9 → 7.7초, p90 18.6 → 24.2초, 30초 넘은 호출 2 → 4, 생각한 호출 15 → 20. 최대는 109 → 42초지만 한 번 튄 값. **꼬리가 줄지 않았다.** 정확도 +3 은 전부 한 사진(B k28, 9삭 → 6삭)이라 장수 힌트로 설명되지 않는 종류 오독 — 흔들림으로 봄.
- **발견:** 옛 기록의 긴 생각 요약을 보면 고민거리는 장수가 아니라 "패산 옆 앞면 패가 도라인가", "세워진 건가 눕힌 건가" 같은 정의 문제였다(v3a 프롬프트에서 이미 정리). 지금 남은 긴 생각은 원인이 다른 곳에 있다.
- **선택:** 기기 장수 세기·틀린 힌트(+1) 측정은 하지 않음. 정보 추가로 꼬리를 줄이는 다른 안(강 끝 위치 좁히기 등)은 같은 방식(정답 정보로 상한 먼저)으로 시험.

## 20. AI 모델 없이 패 종류 맞히기 — 템플릿 매칭·특징점(SIFT/ORB)·비전 임베딩 검색 ❌ (Gemini 에 크게 못 미침)

- **문제와 제약:** Gemini 판독은 느리고(꼬리 30~40초) 돈이 들고 같은 사진을 다르게 읽는다. 패는 34종(+적5)뿐이니 "온전한 패 그림과 비교해 가장 비슷한 것" 이면 학습 없이 기기 안에서 ms 단위로 될 수 있다(사용자 제안). 판독은 (1) 한 장씩 찾아 자르기 (2) 무슨 패인지 고르기로 나뉘는데, 공개 YOLO 시험(17)에서 병목은 (1)이었다 → (2)만 먼저 싸게 확인.
- **검토한 대안:** (a) 픽셀 비교(흑백 상관, HOG, HOG+무늬 색), (b) 위치·크기를 조금씩 움직이며 비교(안쪽 면 + matchTemplate), (c) 사전학습 비전 모델 임베딩으로 이미지 검색(DINOv2 small/base, CLIP — 요약 벡터와 위치별 패치 특징 둘 다). 전부 학습 없음.
- **평가 방법:** 격자로 자른 패 크롭에서 가운데 패의 흰 면을 잘라 세움(opencv, `experiments/template/faces.py`). 시험 = 평가 세트 B·C·D 손패 78장, 기준 그림 = 시험 장면 사진이 아닌 매장 크롭(A·E·매장 촬영 Q, 다른 B·C·D 장면) + 집 패 정면 세트. 강 크롭은 뺌 — 갤러리 사진들이 같은 판을 시간 차를 두고 찍은 것이라 **장면끼리 같은 강 패가 겹쳐 49/49 로 새는 값**이 나왔다(처음 숫자에서 발견).
- **변화(측정, 손패 78장):** (a) 19~27장(25~35%) → (b) **49~53장(63~68%)**, 집 패 세트만 기준으로 써도 53장(다른 세트로도 같은 수준) → (c) 17~24장(20~30%), 패치 특징도 15~23장. 한 장 25~100ms(CPU). 비교: Gemini 자리 판독은 손패·울기 통째 94%(장 단위는 더 높음).
- **발견한 오류:** 비스듬한 오른쪽 자리 B 가 가장 약함(10~17/26, 정면에 가까운 D 는 22/26). 만수끼리(2·3·4만 → 8만) — 아래 "萬" 이 같아 위 숫자 한 획 차이를 픽셀 비교가 못 잡음. 임베딩은 "마작패 한 장" 이라는 큰 뜻은 잡지만 획 하나 차이를 뭉갬 — 학습 없는 일반 특징은 같은 종류 안의 세밀한 구분에 약하다.
- **선택:** 판독에 쓰지 않음. 패 장 단위 63~68% 면 14장 손패를 통째로 맞힐 확률은 거의 0. 이 계열이 쓸 만해지려면 우리 패 크롭으로 작은 분류기를 학습해야 하고(17 의 결론과 같음: 조건을 만드는 건 모델이 아니라 데이터), 그래도 자르기(1)는 따로 풀어야 한다.
- **추가 시험(2026-10-26 저녁, 사용자 제안 "정면 기준 그림 + 구도 펴기 + 템플릿/SIFT·ORB"):** 같은 시험(손패 78장)·같은 기준 그림 조건 4가지로 (d) 특징점 매칭(`feature.py`: SIFT·ORB, 비율 검사 + RANSAC 호모그래피 inlier 수가 가장 많은 종류) — SIFT 31~38장(40~49%), ORB 36~48장(46~62%, 집 패 정면 세트만 기준일 때 48장). (e) 흰 면을 회전 대신 네 꼭짓점 원근 펴기(`--warp`) — 이웃 패 흰 면과 붙어 꼭짓점이 어긋나는 일이 잦아 오히려 같거나 나쁨(SIFT 21~39, ORB 40~43장). AKAZE 는 opencv 5 본체에 없어 뺌. 반복 무늬(통수 동그라미·삭수 막대)는 특징점이 서로 아무 데나 짝지어져 9통↔5삭·9삭↔9통, 만수는 "萬" 획이 특징점을 차지해 → 8만으로 몰림. 특징점이 템플릿(b)보다 나은 조건은 없었다.
- **고정 카메라 상한(참고, 평가 세트 안):** 갤러리의 장면별 사진 두 장은 같은 판을 카메라만 조금 옮겨 찍은 것 → 다른 사진의 같은 패를 기준 그림에 넣으면 (b) **78/78**. 하지만 이건 "같은 패·같은 자리" 를 다시 찾은 것이라 너무 낙관적. 현실에 가까운 조건 — 같은 매장 패·같은 카메라지만 **시험 패가 놓였던 자리는 빼고** 다른 자리의 같은 종류만 — 은 **50/78(64%)**: 같은 종류가 여러 장인 B·D 는 21/26 으로 오르지만 만수가 한 장씩인 C 는 8/26 으로 떨어짐(같은 각도의 다른 숫자 만수가 더 비슷하게 나옴). 유사도가 패 내용보다 **보는 각도·외곽**에 끌린다는 뜻 → 카메라를 고정하고 기준 그림을 등록해도 자리마다·종류마다 다 모아야 하고, 그래도 숫자 한 획 구분은 못 함.
- **시간:** 실제로 쓰면 종류별 기준 34장 비교라 템플릿 패 한 장 수~수십 ms(기기 안 가능). 시험에서 오래 걸린 건 기준 300~400장 전수 비교 × 조건 4 × 방법별 반복 때문(SIFT·ORB 는 파이썬 전수 짝짓기로 패 한 장 1~4초).
- **운영·남은 것:** 로컬 실험만(`experiments/template/` — `match.py` 픽셀, `match_shift.py` 위치·크기 찾기, `feature.py` SIFT·ORB, `embed.py` 임베딩, `CEIL=1` 은 고정 카메라 상한·다른 자리 조건, 로그 `log_*.txt`; 가중치는 HF 캐시, `timm` 설치). 촬영 기록 label.json 으로 크롭이 쌓이면 같은 평가로 작은 분류기(미세 조정)를 다시 잰다.
- **추가 — 외부 제안 "ResNet 특징 + 패마다 기준 3~5장 + 점수 차로 애매한 패만 Gemini" 확인(2026-10-27):** 같은 시험에서 15~28%(템플릿 63~68% 보다 나쁨). 점수 차로 절반을 넘겨도 남은 패 정답 36% 안팎, 99% 정답이 되게 거르면 남는 패 0.5~6% → 손패 13장이 다 안 넘겨질 확률 ≈ 0 이라 속도 이득도 없음. 기준 3·5장·전부 차이 작음. 어려움은 조명이 아니라 획·무늬 개수 차이와 각도 — 사전학습 특징이 배우지 않은 차이. 남은 길은 같은 카메라·같은 자리 기준 사진(기록상 같은 자리 100%·다른 자리 64%) 또는 우리 크롭으로 학습한 분류기.


## 21. 3번 읽기 안전장치를 유지한 채 체감 시간 줄이기 🔧 (시뮬레이션까지)

- **문제와 제약:** 자리 판독 3번 동시 + 만장일치(틀린 채 반영 0 을 위한 안전장치)는 셋 중 가장 늦은 답을 기다려 장면 중앙이 한 번 읽기의 거의 2배. 경주·출력 상한은 쓰지 않음(사용자), 정확도를 깎는 안은 안 됨.
- **검토한 대안:** (a) 토큰 확률(logprobs)로 패마다 확신도를 받아 1번 읽기 + 확신 낮은 패만 묻기 — 3번 읽기 없이 같은 안전장치. (b) 3번은 그대로 보내되 검사(장수·텐파이/화료형)를 통과한 두 답이 같아지는 순간 결과를 먼저 보여 주고, 셋째 답이 오면 확정(다르면 확인 질문으로 바꿈).
- **평가 방법:** (a) gemini-3.8-flash 에 `response_logprobs` 로 한 번 호출(`experiments/speed/logprob_probe.py`). (b) 추가 호출 없이 쌓인 v3a 판독(B·C·D 사진 6장 × 16회, 같은 입력)과 장면 호출 기록(`scene_base.json`)에서 2만 번 뽑아 시뮬레이션(`experiments/speed/provisional.py`).

## 25. 무늬를 코드로 세어 Gemini 오독 잡기(검증기) 🔧 (로컬 실험, 판독 흐름엔 안 넣음)

## 26. 뒷면 색 과적합 — "뒷면 = 연보라" 가정 없애기 ✅ (앱 반영, 서버 운영 배포 131275a)

- **변화:** 묶음 시간 중앙 7.4 → 7.6초, p90 15.8 → 15.4초, 최대 24.9 → 22.9초, 정답 48/48 둘 다 — 차이 없음. 생각 0 인데 늦은 경우는 같은 요청 셋이 똑같이 늦는 것(13.18/13.18/13.19초 등)이고 priority 에서도 그대로 생겼다.
- **선택과 근거:** 넣지 않는다. 꼬리의 원인은 대기열 순서가 아니라 (1) 사진에 따른 생각과 (2) 같은 요청 묶음이 함께 늦는 것 — 둘 다 등급으로 안 줄어든다. 비용만 2배.

## 29. 울기를 미리 읽어 두고 화료 때는 손패만 읽기 — 사진과 문구를 같이 바꿔야 한다 🔧 (전제 확인, p90 −35%)

- **문제와 제약:** 다음 실험(테이블 위 고정 카메라)에서 게임 중 사진을 받아 울기를 미리 읽어 두면, 화료 때는 손패만 읽어 빨라지지 않을까(사용자 아이디어). 판 상태 추적을 만들기 전에 전제부터 확인. 장비 없이 지금 사진으로, 정확도를 깎으면 안 됨.
- **검토한 대안:** 화료 사진의 자리 크롭에서 울기 모서리를 잘라 내고 (a) 문구는 그대로, (b) 끝에 "울기는 이미 읽었다" 한 줄, (c) 손패만 읽는 문구·스키마로 다시 짜기(울기 줄·칸 삭제, "울기는 잘라 냈으니 손패 줄이 13장보다 적을 수 있음"), (d) (c) + 울기 수에서 나온 손패 장수.
- **평가 방법:** 울기가 있는 B·D 4장, 지금 크롭과 같은 시각에 나란히, 각각 두 회차 120회씩. 운영 자리 판독과 같은 요청. 생각 요약으로 원인 확인(`experiments/speed/seat_nomeld.py`).
- **발견한 오류 → 개선:** 처음엔 (a)(b)만 재서 생각한 호출이 7 → 26/120 으로 늘었고, 생각 요약("10장인데 울기가 안 보인다")을 근거로 "정보를 빼면 모델이 더 고민한다, 울기는 화료 사진에 그대로 두자" 고 결론 냈다. **사용자 지적: 프롬프트를 못 짠 것.** 실제로 울기를 잘라 낸 사진에 "오른쪽 모서리까지 읽어라, 손패는 보통 10~14장, melds 칸" 이 그대로 남아 지시와 사진이 어긋나 있었다. 문구를 사진에 맞게 다시 짠 (c)로 재니 결과가 뒤집혔다.
- **변화(120회씩, 두 회차 방향 같음):** 정답 120/120 셋 다. 지금 → (c) → (d): 중앙 5.5 → 5.2 → 4.9초, **p90 14.1 → 9.2 → 8.1초**, 최대 61.8 → 40.2 → 29.6초, 긴 생각(1000토큰 넘음) 11 → **0** → 2번. (c) 의 최대 40.2초는 생각 0 인 호출(같은 요청 묶음 지연, 28). 장수까지 알려 주는 (d) 의 추가 이득은 작고 흔들림 범위.
- **선택과 근거:** 판 상태 추적에서 울기를 미리 읽고, 화료 사진은 울기를 잘라 낸 손패 전용 문구로 읽는 설계가 의미 있다(자리 판독 p90 약 −35%, 정확도 그대로). 장수 안내는 넣지 않거나 나중에 다시 잰다. 교훈: **입력(사진)을 바꾸면 지시(문구)도 같이 바꿔야 공정한 비교다** — 어긋난 문구가 만든 고민을 "정보가 빠져서" 로 잘못 일반화했다.
- **남은 것:** B·D 4장뿐, 자르는 위치는 손으로 정함(실제로는 추적이 울기 위치를 알아야 함). 미리 읽은 울기가 틀리면 화료 판독이 고칠 기회가 없으므로 울기는 여러 프레임 다수결로 확정해야 한다. 고정 카메라 사진으로 다시 잰다.

## 30. 확실한 판독은 사람 손 없이 반영 — 되돌리기를 먼저 만들고, 확인 기준은 저장된 판독으로 정하기 ✅ (앱 반영)

- **문제와 제약:** 판독이 맞아도 매번 "대국에 반영" → 시트 확인 → 기록을 눌러야 했다(사용자: 터치 없는 자동화를 원함, 단 정확도를 잰 뒤). 자동으로 넣으려면 틀렸을 때 되돌릴 길이 먼저 있어야 하고, 틀린 채 반영은 0 이어야 한다.
- **검토한 대안:** (a) 결과 화면에서 바로 기록 후 "취소" = 되돌리기, (b) 결과 화면에서 10초 카운트다운 후 기록, 그 전엔 취소. (a) 는 기록 뒤 화면의 점수 이동판이 바뀐 판(국·친이 넘어간 상태)으로 다시 계산돼 미리보기가 틀린다 → (b). 기록 뒤에도 테이블의 "마지막 취소"로 되돌릴 수 있다(같은 날 만든 기록 되돌리기: 기록마다 직전 판 상태를 저장).
- **평가 방법:** 저장된 운영·로컬 앱 흐름 판독 B·C·D 60회(prod·prod2·last3·last3yolo·seat3, 각 12)에 앱과 같은 규칙을 적용해 자동/확인/틀린 반영을 셈.
- **발견한 오류 → 개선:** 처음 규칙 "플래그가 하나도 없을 때만" 은 **60회 모두 확인으로** 빠졌다 — 판독이 근거를 알려 주는 설명용 플래그("강 끝 패가 하나라 론으로 봤습니다", "울린 손패라 사진 리치 무시", "사진 리치 → 리치봉 자동")가 거의 모든 장면에 붙기 때문. 플래그를 **설명용(근거)** 과 **확인용(방총자 후보 여럿·화료패 추정·장수·확신도·동시 론)** 으로 나눠 확인용과 판독 경고(자리 판독 3번 엇갈림)만 막도록 고침.
- **변화:** 자동 반영 0/60 → **58/60, 틀린 반영 0**, 확인 2(확신 낮은 패 + 엇갈림 1, 장수 불일치 1). 사람 손: 판독마다 버튼 3번(반영·시트 기록·닫기) → 0번(10초 기다림) 또는 "지금 반영" 1번.
- **운영·남은 것:** 거치 화면 더보기에서 끌 수 있음(기본 켬). 파오 역만·동시 론은 늘 사람이 확인. 근거는 갤러리 6장의 반복이라 새 조건(먼 자리·다른 패 세트) 사진에서 다시 재야 한다. 되돌린 화료의 촬영 기록 label.json 은 남는다.

## 31. 결과 음성: 기기 TTS → 미리 만든 음성 파일, WAV 끝 C2PA 를 소리로 읽던 잡음 ✅ (앱 반영)

- **문제와 제약:** 작혼처럼 결과 화면에서 "쯔모 → 역마다 하나씩 → 등급" 을 읽고, 역 한 줄은 그 말을 다 읽은 뒤 띄운다(사용자 요청). 기기 TTS(웹, Windows 한국어 음성)는 "리치" 같은 짧은 말도 시작 지연 포함 1.5~1.9초라 배만 손(역 6개) 전체가 **13.3초** 걸려 점수가 늦게 떴다. 기기마다 목소리·속도도 다르다.
- **검토한 대안:** (a) TTS 말하기 속도 올리기 — 지연은 그대로이고 플랫폼마다 속도 단위가 다름, (b) 읽을 말이 정해져 있으니(역 47·도라 장 수 28·등급·론/쯔모 = 86개) 미리 만든 음성 파일 — 지연 없음, 같은 목소리, 오프라인. 직접 녹음도 같은 파일 이름으로 바꿔 넣을 수 있다 → (b). 생성은 Gemini TTS(`gemini-3.8-flash-tts`, 이미 쓰는 키), 파일이 없으면 TTS 로 대신 읽는다.
- **평가 방법:** 만든 파일을 Gemini 로 받아써서 원래 말과 비교(`tool/check_voice.py`), 길이 측정, 웹에서 재생 순서·시각 기록.
- **발견한 오류 → 개선:** ① 스타일 지시문("energetic announcer…")을 말 앞에 붙이니 목소리 5개 중 3개가 지시문까지 읽음 → 말만 보내고 느낌표로 힘을 줌. ② "도라 2" 를 "도라 투" 로 읽음 → 숫자를 한글로(도라 둘, 사배 역만, 십삼면). ③ 단어 하나가 1~1.5초에 파형 끝이 가장 큼 → 응답이 맨 PCM 이 아니라 **WAV + 끝에 C2PA(Google 서명 출처 표시) 덩어리**였고 통째로 PCM 으로 읽어 헤더·C2PA 가 끝 잡음이 됨. 그 잡음 때문에 무음 자르기가 안 되고 음량 맞춤도 잡음 기준이라 말소리가 작았다 → WAV 의 data 청크만 읽음("리치" 1.05 → 0.68초). ④ 문맥 없는 받아쓰기는 마작 용어를 일상어로 적음("량페코" → "양배추", 86개 중 64개 불일치) → 용어 목록을 같이 주니 불일치 2개(뒷도라 4 숫자 빠짐, 창깡)만 남았고 다시 만들어 86/86 일치.
- **변화:** 배만 손 연출 13.3초 → **6.2초**(웹, 클립 사이 틈 5ms), 클립 평균 0.98초, 86개 897KB.
- **운영·남은 것:** 같은 날 목소리 5개(Kore·Zephyr·Leda·Puck·Fenrir, 4.3MB)로 늘리고 룰 설정에서 고르게 함(+ 기기 음성). 새 4개 344개 받아쓰기 불일치 6 → 다시 만들어 5 해결, Leda "창깡" 은 3번 다시 만들어도 "잠깐" 으로 받아 적힘(받아쓰기 쪽 혼동일 수 있음, 귀로 확인 필요). 한 목소리만 다시: `python tool/make_voice.py --voice <이름> --force` 후 `check_voice.py assets/voice/<이름>`. 말 목록을 바꾸면 `dart run tool/voice_lines.dart` 로 lines.json 을 다시 뽑는다(테스트가 어긋남·빠진 파일을 잡음). 실기기 재생 지연은 아직 안 잼.

## 31. 과적합 확인 → 개발/테스트 세트 분리, 기운 탁자 펴기 🔧 (실험, 앱 미반영)

- **문제와 제약:** 갤러리 B·C·D 6장(장면 3개)으로 규칙·문턱·프롬프트를 고르고 같은 6장으로 점수를 냈다(12/12). 10/24 매장 삼각대 사진 15장(정답 앎)에 앱 흐름을 그대로 돌리니 손패 0/15 — 사용자 지적 "과적합 아니냐". 매장 사진은 탁자가 약 25° 기울어 축에 평행한 격자 선 4개로 자리를 못 나눔(사람이 맞춘 격자 1/4, YOLO 자동 격자 0/14).
- **결정(사용자):** B·C·D = 개발 세트, 매장 15장 = 테스트 세트(규칙을 고치는 데 안 쓰고, 다 만든 뒤 한 번만). 새 방법은 B·C·D 를 합성으로 바꿔 개발.
- **검토한 대안:** (a) 카메라를 탁자와 평행하게 거치(장비·매장 조건에 달림), (b) YOLO 자동 격자(기운 사진에선 축 평행 선의 한계 그대로), (c) **펠트 네 모서리로 사진을 펴고 표준 격자 하나로** — 카메라 위치가 바뀌어도 격자를 다시 맞출 필요가 없다.
- **평가 방법:** 개발 = B·C·D 원본 6 + 합성 기울기 18(±10~25°·원근, 매장 사진을 보지 않고 정한 값). 테스트 = 매장 15장 한 번. 앱 판독 흐름 그대로(노트북 Windows, 같은 판독 서버 코드).
- **변화:** 합성 기울기 점수 2/18 → **18/18**(틀린 반영 0). 테스트 세트 손패 0/15 → **8/15**, 점수 0/10 → **7/10**. 펴기 비용 약 3초(다시 인코딩 포함 — 앱에선 줄일 수 있음).
- **발견한 오류:** 테스트 세트에서 **틀린 반영 2/15** — 자동 반영 조건(자리 판독 만장일치 + 병합 플래그)이 리치봉·도라·적도라처럼 점수에 영향을 주는 가운데 판독을 검사하지 않는다(12:29 12000 → 7700, 14:03 적5만 → 5만). 개발 세트(60회)에서 틀린 반영 0 이던 안전장치가 일반화되지 않았다는 것 — 개발 세트에 이런 실패 유형이 없었다.
- **이어서(같은 날, 개발 세트로만):** 판독 확신도로 리치봉·적도라 실수를 잡으려 했으나 개발 세트에서 리치봉은 있으면 늘 0.9·없으면 답 없음, 5 패는 적5든 아니든 0.99 — **확신도에 신호가 없다**. 규칙에서 나온 장수 검사(표시패 0장, 리치인데 뒷도라 안 보임)만 자동 반영 조건에 넣음(개발 비용 96회 중 1회). 리치봉을 아예 못 본 경우·적5 오독은 여전히 못 막는다 → 추가 판독을 개발 세트로 실험(축소·흐림·회전 변형 포함): 리치봉 3번 읽기 90/90·세 답 늘 같음, 5 패 재확인 0/72 틀림·헛경보 0 — **개발 세트에선 그 실수가 아예 안 생겨 잡는 능력을 잴 수 없다**. 테스트 세트 같은 조건(비스듬한 거치·먼 자리)의 새 개발 사진이 필요. 사용자 요청으로 테스트 세트에서 한 번 잼(규칙 안 고침): 리치봉 3번 읽기는 15/15 앱 답과 같아 확인 0, 5 패 재확인은 적5 오독 4장을 4/4 같이 틀리고 헛경보 4/9 → **둘 다 채택 근거 없음**. 대신 개발 세트 규칙 논리로 넣은 도라 장수 검사가 12:29 의 틀린 자동 반영(7700)을 막음 — 이번 테스트 실행 틀린 반영 0.
- **운영·남은 것:** 펴기는 실험(앱 미반영). 다음: 자동 반영에 리치봉·도라·적도라 확신 조건 추가(개발 세트·새 사진으로 정하고, 테스트 세트는 다시 재기 전에 사용자에게 묻기), 펴기를 앱 촬영 흐름에 넣기(편 이미지에서 바로 자르기). 근거: `experiments/rectify/README.md`.
